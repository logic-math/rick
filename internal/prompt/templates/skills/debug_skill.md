# skill:debug-skill（三阶段科学调试体系）

## 铁律

```
没有根因调查，不得提出任何修复方案。
症状修复是失败。随机修改是制造新 bug。
```

**声明触发**：遇到任何非预期行为，必须先声明：
> "I will use skill:debug-skill."

声明后，严格按照准备阶段 → 阶段一 → 阶段二 → 阶段三顺序执行，**不得跳过**。

---

## 准备阶段：debug/ 目录与文件约定

### 目录创建

在**当前工作目录**（项目根目录）下创建 `debug/` 目录：

```bash
mkdir -p ./debug
```

### Bug 编号规则

- **全局递增**，不按 task 重置
- 扫描 `./debug/bug*.md` 找到最大编号 N，下一个用 N+1
- 文件命名：`bug{n}-{简要描述}.md`（例：`bug3-concurrent-race.md`）

### bug*.md 文件格式规范

每个 bug 文件**第一行**必须是 YAML frontmatter（Rick 框架提取摘要的唯一来源）：

```markdown
---
summary: "并发竞态导致数组越界，已通过 sync.Mutex 修复"
status: "✅ 已解决"
---

## 阶段一：源码推理法
...

## 阶段二：增量调试法
...

## 阶段三：科学实验法
...

## 结论
...
```

**必填字段**：
- `summary`：一句话描述根因 + 最终状态（例：`"nil pointer dereference in parseTask，已通过空值检查修复"`）
- `status`：当前状态

**合法状态值**：
- `"✅ 已解决"` —— bug 已修复，测试全部通过
- `"🔄 进行中"` —— 调试进行中（仅临时状态，最终必须转为已解决或无法修复）
- `"❌ 无法修复"` —— 有扎实论证说明 bug 在当前约束下无法修复，需要人类决策

**终止状态约束**：任何 bug.md 最终必须以以下两种状态之一结束，**不得悬置**：
1. `status: "✅ 已解决"` —— bug 已修复，测试全部通过
2. `status: "❌ 无法修复"` —— `## 结论` 章节包含扎实论证，不可空置

## 阶段一：源码推理法（Source Code Reasoning）

**上限：3 次尝试**

### 触发 review debug agent：建立假设时

在阶段一建立假设时，启动 **review debug agent**（subagent）：
- 输入：相关源码 + 测试输出 + 已有 debug 记录
- 任务：大范围读取源码，输出假设列表（每条包含观察证据 + 推断 + 建议）
- **角色约束**：只输出分析，不执行任何改动，不写文件，输出后即退出
- 详见下方「review debug agent 协议」章节

### 主 Agent 执行循环

每次尝试前必须确认：`git diff` 输出为空（工作区干净）

```
FOR each attempt (max 3):
  ASSERT: git diff == clean
  1. 基于 review debug agent 输出的假设，选择优先级最高的一条
  2. 明确声明："我认为根因是 [X]，理由是 [Y]"
  3. 做最小代码改动验证该假设
  4. 运行测试：
     - ✅ 通过 → 确认根因，进入修复提交流程
     - ❌ 失败 → git checkout . 回滚，记录到 bug{n}-xxx.md 阶段一记录
  5. 若尝试 3 次仍失败 → 进入阶段二
```

### 阶段一记录格式

在 `bug{n}-xxx.md` 的 `## 阶段一：源码推理法` 章节追加：

```markdown
### 尝试 {M}
- 假设：[假设内容]
- 改动：[最小改动描述]
- 结果：❌ 失败 / ✅ 通过
- 回滚：git checkout . （失败时）
```

## 阶段二：增量调试法（Incremental Debugging）

> 前提：阶段一 3 次尝试均失败

### 触发 review debug agent：简化复现步骤时

在阶段二简化复现步骤时，启动 **review debug agent**（subagent）：
- 输入：测试输出 + 源码 + 阶段一记录
- 任务：产出最小复现建议和基线方案（每条包含观察证据 + 推断 + 建议）
- **角色约束**：只输出分析，不执行任何改动，不写文件，输出后即退出

### 基线判断逻辑

```
1. 检查 git log 历史：是否存在"当前 bug 不存在"的最近提交？
   → 找到：该 commit 为基线，运行 git bisect 或手动 checkout 确认
2. 无历史基线：能否构造"最小配置"让 bug 消失？
   → 找到：该最小配置为基线
3. 仍无基线：跳过阶段二，直接进入阶段三
```

### 增量调试步骤

```
1. 从基线出发，逐步添加改动
2. 每次添加一个变量，运行测试
3. 找到引入 bug 的最小改动 → 该改动指向根因
4. 确认根因后进入修复流程
5. 若仍无法确认 → 进入阶段三
```

## 阶段三：科学实验法（Scientific Method）

> 前提：阶段一 + 阶段二均失败，或阶段二无基线跳过

**上限：5 次实验循环**

### 触发 review debug agent：两个触发点

**触发点 A：简化复现时**（同阶段二触发点，若阶段二未运行则在此触发）

**触发点 B：建立错误传播链假设时**：
- 输入：相关源码 + 所有已有 debug 记录 + 实验观测数据
- 任务：分析错误传播链，产出传播路径假设（每条包含观察证据 + 推断 + 建议）
- **角色约束**：只输出分析，不执行任何改动，不写文件，输出后即退出

### 运行时观察工具

**AI 自行安装使用，禁止 mock**：

| 语言 | 工具 | 安装方式 |
|------|------|----------|
| Go | delve | `go install github.com/go-delve/delve/cmd/dlv@latest` |
| Go | pprof | 内置，`import _ "net/http/pprof"` |
| Python | pdb | 内置，`import pdb; pdb.set_trace()` |
| Python | py-spy | `pip install py-spy` |
| 通用 | strace/ltrace | 系统工具，`sudo apt install strace` |

**使用原则**：
- 使用真实运行时工具，不替换为 mock
- 在关键路径插入断点或日志，精确定位错误传播链
- 每次实验有明确假设，观测后记录结论

### 实验循环

```
FOR each experiment (max 5):
  1. 基于 review debug agent 的传播链假设，设计实验
  2. 明确声明："实验 {K}：验证 [假设]，方法 [观测工具+手段]"
  3. 安装/配置观测工具
  4. 运行实验，收集数据
  5. 记录到 bug{n}-xxx.md `## 阶段三：科学实验法` 章节
  6. 判断：
     - ✅ 找到根因 → 进入修复流程
     - ❌ 假设排除 → 更新传播链分析，下一轮实验
```

### 超限处理（5 次后仍未解决）

**停止所有尝试**，执行以下操作：

1. 在 `bug{n}-xxx.md` 的 `## 结论` 章节写入（不可空置）：
   ```markdown
   ## 结论

   **已尝试的方法**：
   - [方法1]、[方法2]...

   **已排除的假设**：
   - [假设1 + 排除依据]、[假设2 + 排除依据]...

   **当前约束与边界**：
   - [约束1]、[约束2]...

   **建议人类决策的方向**：
   - [方向1]、[方向2]...
   ```

2. 更新文件顶部 frontmatter：
   ```yaml
   ---
   summary: "根因是 [X]，在 [当前约束] 下无法修复"
   status: "❌ 无法修复"
   ---
   ```

3. 向人类呈现 bug 文件路径，等待人类决策。

## review debug agent 协议

### 定义

review debug agent 是在调试特定触发点由主 Agent 启动的 subagent，职责是**深度分析**，不执行任何修改。

### 启动时必须加载 SENSE 方法

agent 启动后**立即**读取：

```
{{sense_skill_path}}
```

按 **S → E → N** 三阶段结构化分析 bug 信息后再输出假设，保证假设有 SENSE 方法论支撑：
- **S（Subject）**：还原问题现状、期望、差距
- **E（pErspective）**：多视角分析根因候选，逆向追踪数据流
- **N（judgmeNt）**：为每个假设提供可证伪的验证方法

### 输入

- 相关源码片段（调用链上的关键文件）
- 测试输出（完整错误信息和堆栈）
- 已有 debug 记录（`./debug/bug{n}-xxx.md` 已记录内容）

### 输出格式

每条假设包含三个字段：

```markdown
### 假设 {N}
- **观察证据**：[从源码/错误信息中观察到的事实]
- **推断**：[基于 SENSE S→E→N 的推断]
- **建议验证方法**：[最小改动或最小复现步骤]
```

### 角色约束

- ✅ 只输出分析和假设列表
- ✅ 可以读取文件（源码、测试输出、已有 debug 记录）
- ❌ 不执行任何改动
- ❌ 不写入任何文件
- ❌ 不运行测试
- ✅ 输出假设列表后即退出

## 完整 bug 文件示例

```markdown
---
summary: "goroutine 并发读写 map 导致 concurrent map writes panic，已通过 sync.RWMutex 修复"
status: "✅ 已解决"
---

## 阶段一：源码推理法

### 尝试 1
- 假设：任务状态更新未加锁，多个 goroutine 并发写同一 map
- 改动：在 updateTaskStatus 中添加 mutex.Lock()
- 结果：✅ 通过

## 阶段二：增量调试法

（阶段一已解决，跳过）

## 阶段三：科学实验法

（阶段一已解决，跳过）

## 结论

阶段一尝试 1 成功定位并修复根因：goroutine 并发写 map 未加锁。
通过 sync.RWMutex 保护所有 map 读写操作，全部测试通过。
```

## 反模式（遇到立即停止）

| 反模式 | 正确做法 |
|--------|----------|
| 没形成假设就随机修改代码 | 先触发 review debug agent，再基于假设改动 |
| 叠加修复：第一个没用直接加第二个 | 一次一个假设，失败则 git checkout . 回滚 |
| 修复症状（捕获异常/加 if）而不是根因 | 追踪到根因再修复 |
| 每次尝试前不检查 git diff | 每次尝试前必须确认 git diff 为空 |
| bug.md 不写 frontmatter | frontmatter 是 Rick 框架读取的唯一来源，必须写 |
| bug.md 以 "🔄 进行中" 状态结束 | 必须转为 ✅ 已解决 或 ❌ 无法修复，不得悬置 |
| 超限后继续尝试 | 超过 3/5 次上限立即停止，写结论，等人类 |
