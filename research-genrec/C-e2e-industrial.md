# 调研简报：方向 C——端到端 / 自回归工业生成推荐与规模化（HSTU/LRM 系）

> 调研日期：2026-10-26 ｜ 覆盖论文 5 篇，全部抓取到原文（arXiv abs 页 + HTML 全文），无"未能获取"项。

## Summary

2026 年工业生成推荐的重心已从"能不能生成"转向"能不能规模化、低成本地落地"。五篇论文给出互补答案：腾讯 **TGR** 给出"生成式排序 → 端到端生成 → 推理注入"的全栈路线图并在多个场景全量上线；**LoopGR**（腾讯 TGR 系列）用循环深度开辟参数高效的新 scaling 维度；美团+武大 **MTGenRec**（KDD 2026）解决 GRM 百卡级分布式训练的三大工程瓶颈；Meta **Kunlun**（KDD 2026）把推荐 MFU 从 17% 提到 37%、首次为"序列+上下文联合建模"建立可预测 scaling law；**Deco** 把"思考"（读历史）与"拼写"（逐码写 SID）分离，将 beam search 外包给轻量解码器换取 3.2–8.6× 吞吐。

## Findings

### 1) TGR：从生成式排序走向统一生成与推理（腾讯 PCG，arXiv 2609.00986，2026-09-01）

**① 思考背景**：工业推荐十年来的蓝图是"召回→粗排→精排→重排"级联、各阶段由独立优化的 DLRM 驱动。作者观察到该蓝图面临三个无法在其内部"调优掉"的结构性矛盾：(i) 碎片化 DLRM 受内存带宽限制、MFU 低、无 LLM 式 scaling law，加参数不再换质量——HSTU/OneTrans 虽以生成范式破局，但自注意力成本随序列长度平方增长，被迫靠序列预压缩/截断牺牲跨字段细粒度交互；(ii) 阶段化优化与逐级候选截断碎片化决策，逐点打分忽略列表内商品间依赖与位置效应；(iii) ID 共现模式匹配缺乏语义、世界知识与推理，冷启动/长尾/模糊意图受限，而每请求执行推理（文本 CoT 或多步 latent rollout）又超出工业延迟预算。

**② 要解决的核心问题**：一句话：在腾讯 PCG 数亿 DAU、数千万至数亿候选、每阶段数十毫秒 P99 延迟的约束下，如何沿"可扩展统一序列建模 → 端到端列表生成 → LLM 推理注入"三个耦合方向把级联推荐系统性推进到生成范式。之所以难：生成式排序的平方注意力与跨字段交互不可兼得；端到端逐商品自回归解码整页在实时约束下太慢；LLM 推理按请求执行延迟不可承受，离线预计算也只转移而非消除成本——三条既有路线各有硬伤，需要协同设计。

**③ 如何解决**：TGR 栈分三路：(1) TGR-GenRank 的 CCFormer——统一特征 token 化 + 可扩展 Transformer 骨干，特征场分离交叉注意力让用户/行为序列/目标商品 token 沿语义定向流交互，子空间 token 混合 + 层次化序列压缩使长序列建模次平方，同时保留逐商品多任务打分以便 drop-in 替换现网排序器；(2) TGR-GenRec 两条路线：BARGE（next-token 范式）用商品上下文感知注意力、层次化路径重排与正交双路解码，弥平多 token 商品扁平化导致的"商品边界丢失"与早期前缀错误的"语义漂移"两大缺口；HiGR（next-slate 范式）用 PCRQ-VAE 前缀结构化语义 ID + 粗到细层次化 Slate 解码器（全局规划/局部生成分离）+ ORPO 列表级多目标对齐，一次性生成整个列表；(3) TGR-Reason 用 LatentRec 训练 Think 模型，离线物化"reason tokens"（推理增强语义 ID），在线以层级对齐提示注入解码，无需请求时推理 rollout。

**④ 结果亮点**：TGR 已部署于腾讯新闻、视频、网文等流量服务数亿用户。CCFormer 以约 HSTU 一半 GFLOPs 可预测扩展、训练快 2.21×，5 个 A/B 场景全部显著提升、2 个全量（视频 +3.57% CTR；广告 +1.71% 收入）；BARGE 离线 Hit@5 超 OneRec 10.2–16.9%，以不变参数/beam/延迟全量后 +0.60% CTR、+1.70% 阅读时长；HiGR 整页质量 +15.9–21.3%、推理加速 5×（P99<50ms），线上最高 +1.22% 观看时长、+1.73% 播放量；TGR-Reason 冷启动新用户 Hit@1 +477.8%，线上 +1.75% 有效消费、新用户曝光→转化 +13.09%。

### 2) LoopGR：经循环深度的参数高效生成推荐扩展（腾讯 PCG + 中山大学，arXiv 2610.34157，2026-10-25）

**① 思考背景**：生成式推荐把推荐重构为语义 ID（SID）的自回归生成，实证显示良好 scaling 行为；但与 LLM 不同，推荐系统部署在严格得多的模型规模与推理成本约束下，核心矛盾不是"增加计算"而是"如何把有限预算在交互历史建模与目标 SID 生成之间分配"。现有架构沿"编码器-解码器 → OneRec-V2 懒解码器"演进，逐步把计算从历史建模转向目标生成，暴露共同冲突：富有表达力的上下文需在生成前深度编码，高效解码又把上下文当固定条件；且计算深度与层数强耦合，更深的上下文精炼必然带来成比例参数与显存开销。Looped Transformer 虽能解耦深度与参数，但难以区分对长历史与目标 SID 的两类异质计算，且循环步直接增加推理延迟。

**② 要解决的核心问题**：一句话：如何设计一个能在"上下文建模"与"目标 SID 生成"之间动态组织计算的生成推荐骨干，使计算深度可伸缩而不按比例增加参数量，并支撑严格 serving 预算下的低延迟推理。此前未解决：推荐侧循环深度几乎空白（LoopCTR 仅面向判别式 CTR，非自回归生成）；无限制循环与延迟预算冲突，缺少推荐特定的循环结构与预算压缩手段。

**③ 如何解决**：LoopGR = 编码器 + 共享生成解码器 + 轻量共享上下文更新器的层次化循环深度：编码器将历史 SID 初始化为上下文记忆；高层循环反复重访目标 SID 预测，每次高层循环内嵌套低层循环——轻量更新器（默认 GRU 实现、模型无关）以 BOS 隐状态导出的预测感知 query 与循环条件逐步精炼上下文，初始记忆作残差锚点保证多轮稳定。解码器参数全程共享，深度靠循环而非层数获得。推理侧提出循环轨迹自蒸馏（RTSD）：先训高预算教师，学生以减半预算初始化，损失同时对学生各级预测分布与教师对应轨迹点做 KL 对齐、对相邻步一阶差分（演化方向）做余弦对齐，使低预算学生复现高预算精炼过程。

**④ 结果亮点**：Amazon Beauty/Sports/CDs 三数据集 12 项指标中 8 项最优（Beauty R@5 较最强基线 +2.4%，Sports R@5 +5.4%），且仅用标准 RQ-VAE SID 即超 RPG/ActionPiece 等精细解码设计；腾讯工业数据集上 R@5 0.5691 全面超过 TIGER（0.5465）、BARGE（0.5477）与 OneRec-V2 式懒解码器（0.5180）；相比代表性编码器-解码器基线性能更优且模型最多缩减 52%。确立"循环深度"为生成推荐新的 scaling 维度。

来源：[arXiv:2610.34157](https://arxiv.org/abs/2610.34157) ｜ [HTML 全文](https://arxiv.org/html/2610.34157v1)

### 3) MTGenRec：美团生成推荐模型的生产训练系统（美团 + 武汉大学，KDD 2026，arXiv 2505.12663）

**① 思考背景**：GRM（稀疏 embedding 表 + HSTU/MMoE 等稠密 Transformer 的自回归推荐）在美团被证明精度优于 DRM——能以自注意力建模用户完整行为序列，但复杂度随序列长度平方增长、训练成本高；而业务每天生成 TB 级行为日志，训练必须跟上数据生成速度。TorchRec 是 SOTA 的 PyTorch GRM 训练系统，但作者识别出两大根本局限：❶静态 embedding 表无法处理动态表项与容量扩张——新用户/新商品/商家改菜单需实时增删 embedding，静态表只能退化为默认 embedding（损精度）或过度预分配（浪费显存）；❷查找时重复 ID 被多次传输致通信冗长，表合并又需人工配置。此外 GRM 必须保留完整变长序列（不能像 LLM 那样截断/填充），造成 GPU 间显著负载不均。

**② 要解决的核心问题**：一句话：为工业 GRM 构建高效可扩展的分布式训练系统，同时解决动态特征 ID 实时增删、变长全序列跨 GPU 负载均衡、embedding 查找通信开销三大矛盾。难点在于现有系统（TorchRec）面向 DRM 生态设计，在"稀疏表模型并行 + 稠密模型数据并行"的混合策略下，动态哈希表、ID 去重与序列均衡分桶需要端到端协同设计而非单点修补，此前无 GRM 专用方案。

**③ 如何解决**：MTGenRec 基于 TorchRec 构建：(1) 动态哈希 embedding 表——MurmurHash3 + 开放寻址 + 分组并行探测（定理证明奇数步长可遍历全部槽位），键（ID→指针）与值（向量）解耦存储、chunk 化分配，负载因子 >0.75 时键结构倍增扩容，支持实时增删；(2) 自动表合并——FeatureConfig 统一接口按 embedding 维度等模式自动合并，动态表用位运算（高 k 位表标识）生成全局唯一 ID；(3) 两阶段 ID 去重——ID 通信前后各去重一次，消除重复 embedding 向量传输；(4) 动态序列分桶——按目标 token 数动态调批均衡 GPU 负载。整体沿用混合并行、All-to-all 查找交换与异构后向更新，端到端同步训练 HSTU+MMoE（top-k 专家聚合）交叉熵目标。

**④ 结果亮点**：在美团 2 亿真实用户序列上评估：训练时间较 TorchRec 最多缩短 2.44×（整体 1.6–2.44×），超 100 卡（最多 16 节点 128 张 A100）仍近线性扩展；消融显示动态序列均衡带来 1.75× 吞吐、ID 去重 +53%；GRM 以与 DRM 相近训练成本取得离线 CTCVR GAUC +2.88pp，外卖平台上线后订单量 +1.22%、在线 PV_CTR +1.31%；系统已支撑美团多个应用、日处理数亿请求。

来源：[arXiv:2505.12663](https://arxiv.org/abs/2505.12663) ｜ [KDD 2026 全文（DOI 10.1145/3770854.3783925）](https://doi.org/10.1145/3770854.3783925) ｜ [HTML 全文](https://arxiv.org/html/2505.12663v3) ｜ 交叉核对：[recarch 资料页](https://jdding.github.io/recarch/en/systems/meituan-mtgenrec-2025/)

### 4) Kunlun：以统一架构设计建立海量推荐的 Scaling Law（Meta，KDD 2026，arXiv 2602.10016）

**① 思考背景**：scaling law（性能随算力投入的可预测幂律关系）是 LLM 资源规划的基础，但推荐系统一直难以建立——尤其是必须同时建模序列用户行为与非序列上下文特征（用户属性、广告元数据、上下文信号）的系统：业务与基础设施的深度依赖使这些特征无法像 LLM 那样"只留序列"。作者诊断出根因是"糟糕的 scaling 效率"：联合建模 SOTA（Interformer 类）模块 MFU 仅 3–15%（LLM 为 40–60%），源于异构特征空间导致的小 embedding 维、不规则张量形状与内存瓶颈算子；同时所有组件等比扩容收益递减——不同层与事件类型受益于不同计算模式。scaling 效率 = 每 FLOP 算法收益 × 硬件利用率，二者须同时优化。

**② 要解决的核心问题**：一句话：为"序列 + 非序列联合建模"的海量级推荐系统建立首个可预测的 scaling law（NE 随 log 算力呈稳定直线下降）。此前未解决：HSTU 等序列-only 路线不处理强上下文特征；Interformer 等联合建模路线 MFU 过低，扩大算力时无法形成可预测的幂律行为，投入被内存等待与冗余层浪费。

**③ 如何解决**：Kunlun 在 Interformer 框架上做模型-效率协同设计，每层两个块：Kunlun Transformer 块（GDPA 增强的个性化 FFN + 多头自注意力）与 Interaction 块（权重生成、HSP、全局交互）。低层模块优化把算子从内存瓶颈改为计算瓶颈：GDPA 把 PFFN（由非序列特征生成权重的序列变换）重构为多头注意力式算子，像 FlashAttention 一样融成单 kernel（PFFN 块 MFU 最高 6×），残差连接使 PFFN 可多层堆叠；HSP 用可学习种子做层次化压缩替代 PMA 随机查询，高效摘要 T>1000 长序列；滑窗注意力获得线性复杂度。高层计算重分配：CompSkip 隔层跳过交互块（利用深层推荐模型的层冗余）；Event-level Personalization 按事件类型重要性（点击强于曝光）配置维度、窗口等资源；另引入 ROTE 旋转时间编码融合时间间隔信息，使模型垂直（层数）与水平（宽度）均可扩展。

**④ 结果亮点**：NVIDIA B200 上 MFU 从 17% 提升到 37%，scaling 效率较 SOTA 翻倍，确立联合序列-非序列建模的首个可预测 scaling law（1–6 层每层呈可预测的对数收益）；消融：滑窗注意力 +31.1% QPS/−29.5% FLOPs，CompSkip −43.1% FLOPs/+35% QPS，事件级个性化 +13% QPS/−11% FLOPs；已部署于 Meta 多个主要广告模型，topline 指标 +1.2%。

### 5) Deco：把"思考"与"拼写"分离的高效生成推荐（arXiv 2610.32980，2026-10-23）

**① 思考背景**：语义 ID（SID）生成检索已在大型 Web 平台落地：每个商品编为 K 个码的 SID，trie 约束 beam search 逐码生成候选。作者发现标准自回归接口要为 SID 长度 K 付两次钱：T 个商品的历史以 TK 个码 token 进入骨干，而 beam search 每一步都跑完整骨干，返回 B 个候选需 O(BK) 个骨干 decode token——后者常占主导（beam 宽 100 时 beam search 占生成时间高达 91%，即使有 beam 共享历史缓存），且随骨干变大、SID 变深、候选预算变大持续恶化。仅压缩输入（FusedGR 把每商品融成单 token）只省 prefill，O(BK) 解码瓶颈原封不动；投机解码需骨干验证草稿，并行/单遍解码又放弃自回归与 trie 约束，均非解。

**② 要解决的核心问题**：一句话：如何把"读历史"（偏好建模/思考）与"拼标识符"（逐码拼写 SID）分离——重型骨干只做一次前向，整个 trie 约束 beam search 外包给轻量解码器，同时精度不降。难点：固定大小的"概念"是否足以承载用户意图（长历史、重复消费场景）、以及如何让不看历史的轻量解码器单独达到全骨干精度——此前无人证明这条路可行。

**③ 如何解决**：Deco 的骨干一次前向：融合历史（每商品一个 token，MLP 把 K 个码 embedding 融成单向量），从最后隐状态线性映射出紧凑 next-item concept（M=2 个向量，M=1–8 差异不大）；一个轻量 KV-cache 解码器（默认 2 层×256 宽，骨干为 8 层×640）仅以 concept + 已生成前缀为条件跑完整 trie 约束 beam search——concept 是两阶段唯一接口，解码器从不看历史、不留骨干缓存，每用户 serving 状态仅约 1 KiB。SID、trie、自回归分解均不变。训练仅需交叉熵（Deco-CE：骨干/fuser/解码器联合稠密训练，一次前向监督所有位置）；可选全骨干教师蒸馏（等效于只在 trie 合法后继上的 teacher-informed label smoothing）；针对音乐等重复消费域加历史 copy 指针直接取回历史商品，混合分布仍在 trie 上精确分解。

**④ 结果亮点**：7 个数据集（Amazon 2014/2023、MovieLens-25M 子集、Yambda 音乐流）上精度持平或超过全骨干基线与融合输入教师；生产式服务管线 50ms p95 预算下吞吐 3.2–8.6×（batch 128 时 2.8–5.1×）；生成 1000 个候选比教师生成 100 个还快；换 1.5B 参数 LLM 骨干仍达 69M 教师的吞吐且精度更高（3B 骨干时较 FusedGR 加速 16×），证明外包 beam search 让更大候选池与更大骨干变得可行。
