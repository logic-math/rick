# teach_2：三阶段的【输入】如何喂进同一个 Transformer——输入侧的统一与差异

> 回合 loop_8 · 引用 research_1.md（结论 2、3）· 信源等级 A（arxiv §4.1/§4.2）

## 发生了什么 / 这件事的样子

上一节说了 V2 把三阶段并进同一个因果 Transformer，共享的是「用户上下文的编码」。这一节落到输入端，看一个请求进来时，三阶段各自喂进去的是什么。

V2 把输入劈成两半（research_1 结论 3，A）：

- **S（共享行为序列）**：append-only 的用户行为历史，与候选无关。无论召回哪个 item、精排哪个候选，这段历史都一样，所以每请求只编码一次，成为那份共享用户上下文。
- **NS_r / NS_p / NS_f（阶段专属候选 token）**：召回、粗排、精排各自关心的候选，由**各自持有的 tokenizer** 生成 stage token，附加到共享上下文上去读它。

同一个 backbone，三阶段喂进去的「用户侧」是同一份，「候选侧」是三套各自的 token。

## 这个领域里它长什么样

先看「各自 tokenizer」意味着什么。三阶段的候选规模、特征粒度不同：召回面对全库、粗排面对召回候选、精排面对存活候选，它们关心不同的特征。于是每个阶段用自己的 tokenizer 把候选压成 token，而不是共用一套（research_1 结论 3，A）。统一发生在「共享 S + 共享 backbone」，不发生在「候选如何被 tokenize」。

再看出现在粗排与精排之间的一处关键差异——**压缩粒度**：

- 粗排把特征子集压成**单个候选 token**（research_1 结论 3，A）；
- 精排用**多个 token**，作者明确说压成一个会抹掉特征异质性（research_1 结论 3，A）。

粗排是筛子，它只需要一个粗分数，牺牲特征内部结构换省算力是划算的；精排要做精细排序，候选特征之间的差异不能揉成一团，所以拆成多个 token 保留结构。这不是两个方案之争，而是同一个 backbone 里的一把「粒度旋钮」：阶段越靠后、排序越精细，候选 token 粒度越细。

还有一条时间约束：stage token 只 anchor 到**请求时刻可见的行为前缀**，不读未来（research_1 结论 3，A）。也就是说候选 token 读共享上下文时，只能看到这个请求发生之前的历史，符合因果。这一条和上一节的「因果 Transformer」是一回事，但在输入侧的具体含义是：候选 token 的「座位」被固定在请求时刻。

最后一层是参数侧，帮助把「共享的到底是什么」钉死：混合参数化里，行为 S-token 共享同一套 Q/K/V 与 FFN 权重，各阶段 NS-token 用各自 token-specific 的 Q/K/V 与 FFN（research_1 结论 2，A）。落在输入上就是——S-token 和 NS-token 不但来源不同，连读取它们的权重也不同：共享的权重属于 S-token，阶段专属的权重属于各阶段的 NS-token。

一个常见误区：把「统一输入」理解成三阶段喂同一份输入、用同一套 tokenizer。事实是 S 共享、NS 各持 tokenizer；统一的是底座，差异的是候选侧。

## 张力与视角

这一节能看到两股力量在输入侧对撞：

- **省算力**这边：S 编码一次、三阶段复用；粗排单 token 把候选压成一个向量。做得越「少」，越便宜。
- **保特征**这边：精排多 token 保留特征异质性，各阶段 tokenizer 保留自己关心的特征。做得越「细」，越准。

有意思的是这两股力量在粗排和精排之间留下了不同的落点：粗排偏「省」，精排偏「细」。同一个 backbone 不抹平这种差异，反而用「各自 tokenizer + 粒度可调」把它显式化。

换一个视角（你的推理引擎视角）：输入端这张图，决定了下游能否复用。S 每请求编码一次、候选 token 各自读它——这正是一份可复用的上下文缓存；NS token 各自 anchor 到可见前缀、不读未来，意味着编码不依赖未来信息，缓存不必等后续 token 才成立。输入侧的形状，直接决定了 KV cache 复用的边界。

## 启示性追问

1. 粗排单 token、精排多 token，这个「粒度差异」在你看来是被什么主导的——是候选规模差、特征异质性，还是「排序精度要求」本身？如果你让精排也压成单 token 省算力，最可能先坏在哪一维？什么观察会让你反转这个判断？
2. 承接你上一节的判断「三个模型共享了一个编码器」：在输入侧细看后，共享的是 S-token 的行为序列（及其 Q/K/V、FFN 权重），而 NS 各阶段自持 tokenizer、各自权重。这个细看之后，你原来的「共享一个编码器」还成立吗？「共享」的边界是不是比「一个编码器」更窄？什么证据会让你改口？
3. stage token 只 anchor 到请求时刻可见前缀、不读未来——从推理引擎的角度，这一条给你带来什么（缓存、流式、批处理），又拿走什么？如果某个阶段放宽成可读未来，什么场景值得付这个代价？
