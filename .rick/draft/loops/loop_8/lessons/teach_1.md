# teach_1：OneTrans-V2 要解决的问题，以及「一个 Transformer 服务三阶段」到底长什么样

> 回合 loop_8 · 引用 research_1.md · 信源等级 A（arxiv §1/§4/§5，V1 论文 2510.26104）

## 发生了什么 / 这件事的样子

工业推荐系统里，一个请求通常走三级级联：召回 → 粗排 → 精排，候选逐级收缩，每一级是一个独立训练的模型。V2 论文里作为基线的那套级联是：召回 202 GFLOPs、粗排 4 GFLOPs、精排 69 GFLOPs，合计 275 GFLOPs（research_1 结论 11，A）。每个阶段各自编码用户、各自建模特征交互、各自训练——同一个用户在同一个请求里被三套模型各读一遍。

OneTrans-V2 做的事不是再造第四个模型，而是把这三个阶段表述成**同一个因果 Transformer 的三个任务**：把与候选无关（candidate-independent）的用户行为序列，每个请求只编码一次，得到一份「共享用户上下文」；召回/粗排/精排三阶段各自往这份上下文上附加自己的候选 token 去读它，阶段之间互相 mask。服务路径仍然是召回→粗排→精排，候选仍然逐级收缩（research_1 结论 1，A）。

一句话：V2 统一的是「用户上下文的编码」，而不是「替换掉级联流程」。

## 这个领域里它长什么样

先分清两级「统一」，它们不是一回事。V1（2510.26104）做的是 model-level 统一——把序列建模和特征交互并进单个排序模型，GMV +5.68%；V2 做的是 cascade-level 统一——把三阶段三任务并进同一个 backbone（research_1 结论 11，A）。你关心的「如何用一个 Transformer 同时服务三阶段」，指的是 V2 这层。

它的形状可以拆成两条边界，理解这两条边界就抓住了架构：

**边界一：候选无关 vs 候选依赖。** 用户行为序列对候选是无关的——无论最后召回哪个 item，这段历史都一样。于是它被编码一次，成为共享用户上下文。而召回、粗排、精排各自关心的候选不同（不同规模、不同特征粒度），所以每个阶段在上下文之上**附加自己的候选 token** 去读取它。上下文是共享的，候选 token 是阶段专属的（research_1 结论 1、3，A）。

**边界二：阶段之间相互 mask，只经共享上下文互影响。** 三阶段不会互相看见对方的 token；它们唯一的交汇点是那份共享上下文（和共享 embedding）。所以这不是「三个模型拼在一个壳里」，也不是「一个头打天下」，而是共享底座 + 阶段隔离（research_1 结论 1，A）。

要让异构 token 真能共用一个 backbone 而不抹平各阶段的特征差异，V2 沿用了 V1 的**混合参数化**：每层块内，行为 S-token 共享同一套 Q/K/V 与 FFN 权重；各阶段的 NS-token 用各自 token-specific 的 Q/K/V 与 FFN（research_1 结论 2，A）。换句话说，共享的是「编码行为的那些层」，各阶段读上下文时用的是自己的参数。

一个常见误区值得先摆正：作者**明确拒绝了** OneRec 式「用端到端生成直接替掉级联」的路线——因为排序阶段依赖丰富的候选特征，替掉级联会丢掉这些特征（research_1 结论 1，A）。V2 保留级联，是把「重复编码」的浪费去掉，而不是把「分级筛选」这个结构去掉。

## 张力与视角

这件事里至少有两股相反的力量在拉扯：

- **统一**这边：编码一次省算力、三阶段共享同一份用户表征、知识能互相流动——V2 线上同硬件 QPS 提到 3.2×，其中 1.53× 就来自共享上下文（research_1 结论 12，A）。
- **隔离**这边：三阶段特征异构、训练目标不同、候选规模差几个数量级，硬合并会互相污染。于是用 mask 和 token-specific 参数把阶段隔开，只留下共享上下文这一个交汇点。

换个角度看，这份架构图的要害是「在哪里切一刀」：作者把共享放在**用户上下文的编码层**，把隔离放在**候选 token 与阶段参数层**。这刀切在哪，决定了它是「真统一」还是「三个模型套一个外壳」。

## 启示性追问

1. 如果你接手做这件事，你会先统一哪一层——共享用户上下文的编码，还是共享 backbone 的参数？换句话说，你更相信浪费在「重复编码」还是「各自建模」？什么证据会让你改主意？
2. 阶段之间相互 mask、只经共享上下文互影响——在你眼里，这是「一个 Transformer 统一了三阶段」，还是「三个模型共享了一个编码器」？这个判断取决于你拿什么当「统一」的判据，说出来。
3. 作者拒绝端到端生成、保留级联，理由是「排序阶段依赖丰富候选特征」。这个理由在你看来是硬约束，还是一个可以被工程化解的借口？什么观察会让你反转？
