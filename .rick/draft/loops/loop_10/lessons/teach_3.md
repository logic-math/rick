# 模块3 · 共享 context 的统一架构：一次编码，怎么只读而不被破坏

承接你上一节的原话——「把共享上下文提取出来，各自阶段生成独立 token，再拼接上去」。这句话的骨架是对的：共享 + 独立。这一节我们跟着作者走一遍，看他怎么把这两个词拆到能落地的粒度，以及你的直觉在三个细节上需要修正。

## 作者面对的那个难题

先回到作者站的位置。他想要的是「一份 user context，三阶段复用」，但马上撞上一堵墙：三阶段对这份 context 的需求是冲突的。召回要生成候选、粗排要单 token 轻量打分、精排要多 token 富特征打分（research_4.md §四.11，A）。同一份表示，被三种互相拉扯的消费方式拽着。如果他直接给每阶段各来一套独立模型，就又退回级联碎片化；如果他逼三阶段共用一套参数，冲突就会在权重里互相污染。所以问题不是"要不要共享"，而是"共享到哪一层为止"。

## 第一步：先划清"什么天然能共享"

作者没有一上来就设计 token 和掩码，他先做了一件事：在一个请求里，什么东西对三阶段、对全部候选都成立？

答案是用户行为序列 S=(s1,…,sL)——按到达顺序 append-only 的历史事件。注意它的定义里明确排除了候选 item 和非序列特征：候选特征分属三阶段 NS_r/NS_p/NS_f（research_4.md §一.1，A）。为什么这么切？因为候选随请求、随阶段变（召回候选是生成的、粗排候选是召回的 top-K、精排候选是粗排存活者），而行为序列在一次请求内对全部候选、三阶段都不变。所以「候选无关」不是作者随手加的形容词，它是"唯一可跨级联共享的部分"的判据。

这一步对应你直觉里的「提取共享上下文」——成立。而且它给了我们一把可复用的刀：一个东西能不能跨阶段共享，先问它是不是候选无关的。

## 第二步：共享之后，冲突怎么表达——独立的是参数，不是 token

共享 context 定了，冲突没消失，只是被推进了一层：三阶段要读同一份 C_u，但各自要往里面加不同的东西。你的直觉说"各自阶段生成独立 token"——方向对，但"独立"这个词要修。

看作者的实际做法（Fig.2(b)，research_4.md §二.4/5，A）：每个 stage token 走自己的一套 Q/K/V + FFN；行为 token 是同质的，共享一套 Q/K/V + FFN。关键在"token 级"三个字——独立的是参数（权重入口），不是 token 本身，更不是"每阶段一个独立的表示向量"。

为什么这个粒度重要？因为 backbone 的层、残差、归一化、MoE 全部共享，只是按 token 类型分流权重。如果你做成"每阶段一个向量"，你就没法让精排的多 token 各自表达异质特征；如果你做成"每阶段一个独立 backbone"，你就把共享丢掉了。token 级参数是中间那一个刻度：数据照常 append 在 context 后，权重按 token 类型走不同入口。

顺带一个 GQA 的边界（research_4.md §二.6，A）：stage token 和行为序列之间只要 KV head 数、head dim 一致，query head 数可以不同。这印证了"独立"落在参数入口，而不是落在 backbone 结构上。

## 第三步：你直觉里缺的那一层——怎么保证只读

「再拼接上去」这件事，单独看是成立的：token 确实 append 在 context 后。但如果只有拼接、没有掩码，会发生什么？

stage token 之间会互看（粗排看到精排的特征）、不同 exposure 之间会互看（上一个曝光看到下一个）、更糟的是 behavior token 会被 stage token 反向修改——context 一旦被改，就再也无法"一次编码、三阶段只读"了。

所以作者补上了阶段可见性掩码，四条规则（Fig.2(c)+§4.1，research_4.md §三.7，A）：
① 行为 token 在 S 内 causal attend（保持序列的因果性）；
② stage token 只 attend 可见的行为前缀（到 anchor）+ 自己 + 同 stage/exposure 中前置 token；
③ 不同 stage/exposure 互相 masked；
④ behavior 从不 attend stage token。

这里藏着整个设计最巧的一步——anchor（research_4.md §三.8，A）。stage token 锚定在"请求时间戳前最后到达的行为 a_e"，只读 a_e 前缀；同请求各 exposure 共享 anchor；新行为 append 不改旧前缀。这样，编码一次之后，每个 exposure 看到的还是它在线上那一刻本来会看到的东西——"一次编码只读"从一个愿望，变成了被 mask 强制保证的机制。

注意一个隐含的代价判断：规则④把 context 对 stage token 设成"只读"，等于主动放弃了"用精排候选反向更新用户表示"这条路。作者认为这条路不值得走，因为那样会毁掉一次编码只读带来的算力与一致性收益（research_4.md §三.8，A）。这个取舍，正好也是留给你追问的地方。

## 第四步：候选特征 token 怎么挂——召回是个例外

你的直觉"各自阶段生成独立 token"在粗排、精排身上成立：候选特征 token 化之后挂到 context 后，粗排压成单 token、精排保持多 token（research_4.md §四.11，A）。

但召回是例外：它没有候选 token。因为召回不是"给候选打分"，而是"生成候选"——NS_r 被概括成一个 CTX token 接在 S 后，自回归生成决策前缀→SID，beam search 产出 top-K 交粗排（research_4.md §四.10，A）。候选不是挂上去的，是解码出来的。

这个例外不是边角料，它反过来照亮了「候选无关」的定义边界：只有当候选是"外部给进来、需要打分"时，才谈得上"候选 token 挂载"；一旦候选是模型自己生成的，共享 context 就只是生成的上下文，而非评分的输入。

## 有形收益：一个可带走的判断框架

以后你在自家栈看到任何一个"共享 context"设计（包括你落地时自己设计的），就用三问验它：

1. 共享的部分，是候选无关的吗？（不是，共享就会在候选随阶段变化处崩）
2. "独立"落在哪个粒度？token 级参数，还是 per-stage 表示/backbone？（后者要么丢共享、要么丢表达异质性）
3. 有没有 visibility mask 保证 context 只读、各阶段互不可见？（没有，一次编码只读就是一句空话）

三问都过了，才是"共享而不破坏分层"；差一问，设计就有一处会漏。

## 追问（先自己答，再往下读）

1. 如果把"独立"从 token 级参数改回你原来的"每阶段一个独立表示向量"，精排的多 token 富特征异质性会最先在哪个环节暴露问题？——什么会让你改变判断：如果你能举出一个场景，per-stage 单一向量也能表达精排所需的多 token 异质特征，且代价更低。

2. 掩码规则④把"context 对 stage token 只读"写死，等于放弃"用精排候选反向更新用户表示"。如果反过来允许 context 被精排反向修改，你会损失什么、又可能换来什么？——什么会让你改变判断：如果你能在某个场景证明"反向修改 context 带来的质量收益"超过"一次编码只读带来的算力与一致性收益"。

3. 召回没有候选 token（候选是生成的），粗排/精排有候选 token。这个不对称，说明"候选无关"这个定义的边界划在哪？——什么会让你改变判断：如果你能设计出一种把召回也表达成"对候选打分"的等价方案，且不丢生成式检索的好处，那这个不对称就不是本质的。

4. anchor 取"请求时间戳前最后到达的行为 a_e"，新 append 不改旧前缀。这个选择的代价是什么？——什么会让你改变判断：如果你能给出一个"旧前缀应当随新行为更新"、且收益超过"编码一次只读"的具体场景。
