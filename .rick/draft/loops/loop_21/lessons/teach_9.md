## 0｜从你的两句话切入（认知强制裁决位）

**a 的裁决位**（autotune 之后还有空间吗/在哪）：你的原话——「这就需要下钻到下一层 IR 去做新的优化才行。不同的 IR 就是不同的优化空间，优化是无止境的。」强直觉，而且**比课文还抽象一层**：你说的是原理（每层 IR＝一个优化空间），本课的案例恰好是这个原理的一次实例化，原样挂上去——

- Helion 的 autotune 在 Triton 层搜 tile/warp——你已熟悉的「kernel 配置空间」，这一层确实搜过了
- 编译链再往下走：Triton → PTX → SASS。**PTX→SASS 那一段的优化器叫 ptxas**，它内部有控件（寄存器分配／指令调度／codegen 启发式）——这些控件的**默认值从未被搜索过**（R1，A）。你的「下一层 IR」，在本案例里就是这一格
- 「优化是无止境的」接本课的量级规律：每层都有空间，但**已高度优化的层只剩 2-7%**（§6）——无止境 ≠ 每层都两位数

**b 的裁决位**（怎么判断一组开关真的好）：你的原话——「保持评估 benchmark 不变，对所有开关进行一次测试，拿到统一度量的指标去判断。」前半句两件都对：固定基准（不变＝同一对照组）✓、统一度量（指标同口径才可比）✓。断点在「**一次**测试」三个字：单次测量。回你第 2 课的 0.5% 噪声锚点：锁频理想条件下计时单次噪声就有 ~0.5% 级，任何频率漂移/温度/共存负载都往上叠——而本课要判的开关组合间差距是 **2-7%**，其下半段（1-3%）与噪声同处一个量级域。一次测试判不动这个量级的差：你测到的 3%，可能是 2.8% 的真差，也可能是 0.5% 的真差被噪声吹出来的。

判真三要素（锁频控制变量／重复采样／显著性检验）在新语境下原样落地——**CompileIQ 的 verifier 就是这个配方**：do_bench 锁频＋重复采样＋Welch t p<0.05 与 Cohen's d>0.2 双闸（§3 详拆）。**这是本课最重要的时刻：你第 2 课的判真语言跨语境复用**——从「调参噪声」语境搬到「编译器开关」语境，一字不改。你在 b 里已经自发给出了前两件（固定基准＝控制变量、统一度量＝同口径指标），缺的第三件（重复与显著性），恰是本课案例里配得最全的一段。

## 1｜控制空间：ptxas/NVCC 内部控件——默认值从未被搜索

期望与现状先分清：期望＝「已 autotune 到最优」的 Helion kernel 还能更快；现状＝autotuner 已在 tile/warp 空间搜过一遍。差距不在 kernel 源码层，在它下面那层编译器——结构关系，先图后文（你的模型＋本课挂位）：

```
你的模型：每层 IR ＝ 一个优化空间（下钻无止境）
本案例实例化：

  Triton 源码（Helion kernel）
    · 优化空间：tile / warp 等 kernel 配置
    · 搜索者：Helion autotuner —— 已搜过 ✓
        ↓ 编译
  PTX（NVIDIA 中间表示：虚拟寄存器 / 虚拟指令）
        ↓ ptxas（PTX→SASS 编译器）—— 本课的搜索层
    · 内部控件：寄存器分配 / 指令调度 / codegen 启发式
    · 默认值＝编译器工程师的硬编码启发式
    · 「默认值从未被搜索过」← CompileIQ 的搜索对象
        ↓
  SASS（sm_100 上实际执行的机器码）
```

控件是什么（概念级，不进 ISA）：ptxas 把 PTX 的虚拟寄存器/虚拟指令落到具体硬件时，要做三类决策——**寄存器分配**（变量放哪个寄存器、占几个、何时溢出到 local memory）、**指令调度**（指令发射顺序与依赖距离）、**codegen 启发式**（分支/向量化的内部策略）。这些决策不是无参数的：内部有开关与权重，NVCC/ptxas 暴露出一部分控制面。关键事实（R1，A）：**这些默认值是编译器工程师定的启发式，从未经过系统性搜索**——工程上合理（默认值要对所有 workload 稳妥），但对你的特定 kernel 未必最优。

洞察矛盾：**「已最优」是个条件最优**——autotune 选出的最优 tile/warp，是「ptxas 用默认控件」这个条件下的最优。条件本身从未被搜索，所以它是一个未探索维度；条件一变，已选出的配置未必还是赢家。§5 的联合论证从这条根上长出来——上层的选择改变下层的最优点，空间之间不独立。

## 2｜RSI loop 三件套：proposer／verifier／产物

用第 1 课的部件语言把整个系统一图挂起：

```
搜索空间：ptxas/NVCC 内部控件组合（含「空串」＝全默认）
    ↓
proposer＝CompileIQ（NVIDIA）进化搜索
    · population 育种：generations × pool_size（代数 × 种群规模＝搜索预算）
    · Booster Pack：预调好的 ACF 目录——先验工件注入搜索起点
    → 产出候选：一组控件组合（写成 ACF 文件）
    ↓
verifier＝三层 gate（§3 详拆，本课判真主体）
    · 正确性：对参考实现 allclose
    · 计时：do_bench（锁频）
    · 统计过滤：Welch t p<0.05 ＋ Cohen's d>0.2
    ↓
产物＝ACF（可移植文件，--apply-controls，CUDA 13.3+）
    ↓
Helion 端：autotune_search_acf —— ACF 当 autotuner 的额外维度，
    与 tile/warp 联合搜索（§5）
```

proposer 机制两层（R1，A）：① **进化搜索**——把「一个控件组合」当个体，population 育种：pool_size 个候选同代评测、择优繁殖变异，跑 generations 代；不需要梯度也不需要训练，只靠 verifier 反馈当适应度（与 AlphaEvolve 系同族的「进化/遗传」策略，谱系图搜索策略簇）。② **Booster Pack**——预调好的 ACF 目录，搜索不必从零起步，从已知好工件开始。这一件与你第 7 课 z.ai 的优化骨架库**同族**：预先收集的优化工件目录注入搜索当先验——家族特征是「**搜索从资产开始，不从零开始**」。

## 3｜verifier 详拆：正确性 gate＋锁频＋统计过滤（你第 2 课的语言，一字不改地长在这里）

三层 gate 逐层（R1，A）：

1. **正确性 gate**：候选编译产物对参考实现 allclose——数值不对直接淘汰。这是最浅形态的防线：fast-but-wrong 在这里死掉，根本进不了计时
2. **计时：do_bench＋锁频**——do_bench 你第 6 课在对策语境见过（Triton 计时协议）；锁频防 DVFS 频率漂移：控制变量要素落地
3. **统计过滤：重复采样后过双闸**——**Welch t 检验 p<0.05**（两组均值差异非噪声的置信门槛）＋ **Cohen's d>0.2**（标准化效应量，差异够不够大）。你的双闸合取语言直接适用：**p 管「是不是碰巧」，d 管「值不值得」——两个都过才算赢**。第 2 课已解锁的语义，这里只报位置：它们就长在 verifier 第三层

有效性证据的顶格形态（nvfp4_gemv，数字 §6 给满）：runtime 收益 4.7%，**独立复测 p≈0、d≈2.5**——翻译成你的语义：差异显著到接近满格置信（不是碰噪声），效应量 2.5 个标准差级（两分布几乎不重叠）。注意「独立复测」四个字：不是博客自己测一遍就完，是另跑一遍复测。

## 4｜产物 ACF：你的工程世界（配置文件／可提交工件／版本化）

ACF（Advanced Control File）＝编译器控件的**可移植文件**形态（R1，A）：

- **内容**：一组 ptxas/NVCC 控件设置（绑定目标硬件与 toolkit 版本）
- **用法**：`--apply-controls`（CUDA 13.3+）——编译期施加，kernel 源码不动
- **性质**：可提交进 git 仓库、可版本化、可 code review、跨人复用

放进你的工程世界：ACF 之于编译器调优，＝配置文件之于服务部署（config-as-code）。区别于「在某台机器上调好的一次性实验」：搜索是离线事件，工件是持久资产。z.ai 把优化沉淀成骨架库（第 7 课），CompileIQ 把优化沉淀成 ACF——同一个动作：**把搜索结果物化成可提交工件**。

**空串默认项**：搜索候选里永远包含「空串」＝不施加任何控件（全默认）。

## 5｜联合 vs 串行两段式：为什么必须一起搜（本课论证高潮）

行业惯行是两段式：先把 kernel 配置调到最优，再考虑编译器层。博客的关键论据（R1，A）：**串行调参会锁死在「默认控制下选出的 kernel 配置」局部最优**。先图后文：

```
串行两段式（惯行）：
  第 1 段｜固定控件＝默认 → autotune 搜 tile/warp → 选出 C*
  第 2 段｜固定配置＝C*  → 搜控件 → 选出 A*
  产物 (C*, A*)——但 C* 是「默认控件下」的赢家：
    · C* 在非默认控件下未必还是赢家
    · 第 2 段只能在 C* 的邻域里搜，回不到「别的 C × 非默认 A」
  ⇒ 两段式锁死局部最优

联合搜索（Helion autotune_search_acf）：
  空间＝(tile, warp, ACF) 三元组联合
    · ACF 是 autotuner 的额外维度，与 tile/warp 同轮枚举
    · 每个三元组过同一 verifier，全局比较
  产物 (C**, A**)——不受「先到者锁定」约束
```

论证一层：两段式把联合空间**按时间切成两半，各自取条件最优**——但条件最优的乘积不等于联合最优。C* 是在「A＝默认」条件下赢的；完全可能存在 C′：它在默认控件下输给 C*，却在某个 A′ 下反超 C*×A*。两段式永远访问不到 (C′, A′) 这个格子——第 1 段已经把 C′ 淘汰了。这不是「搜得不够久」的问题，是**搜索顺序的结构性遮蔽**：多跑几代也回不来。

这也给你的 §0a 模型补上最后一格：每层 IR 是一个优化空间，但**空间之间不独立**——上层的选择改变下层的最优点，所以「逐层各自最优」≠「栈上最优」。你的层级模型＋这一条，就是完整的联合搜索论证。

留白二（你来推/复述）：用你自己的话把「两段式锁死局部最优」讲一遍——第 1 段选出的赢家是在什么条件下赢的？被它淘汰的配置，有没有可能在别的条件下反超？

## 6｜有效性证据＋量级规律＋Caveats

证据给满（nvfp4_gemv W4A4 decode GEMV，GB200/sm_100，R1，A）：

- **runtime 目标**：1.047×（4.7%）——独立复测 p≈0、d≈2.5（§3 已拆语义）
- **NCU 指标当搜索目标**（多目标）：occupancy 21.60→21.76%，换 runtime 1.75-2.0%；Pareto 双目标：6.9% runtime＋4.5pp L1TEX（81.51→85.96%）——控件搜索不只买 runtime，还能买硬件计数器指标（occupancy/SOL，你 #11 infra 深度梯最底格附近的语言；目标函数本身可选）
- **双 shape 联合 ACF**：1.05×／1.01×——一个 ACF 同时服务两个 shape，各自有效（联合搜索在 shape 维度上也成立）

量级规律（博客口径，A 但为**经验规律非定律**）：**已高度优化的 kernel 2-7%；未充分优化的 kernel 两位数**。回接你 §0a「优化是无止境的」：每层都有空间，但深度与残差反相关——越往下越接近物理极限，剩的是最后几厘米。这也是为什么基线口径是判真的第一道门：naive 基线上的加速声明近乎无意义（待裁决 7，你已裁决接受——你的原话「baseline 不能以 pytorch 原生实现对比，这个值没有实际价值」；本博客的价值恰在于它从高度优化基线起步）。

Caveats（官方自述，R1，A，逐条）：

1. **ACF 硬件＋toolkit 特定**：sm_90 的 ACF 用于 sm_100 可能**出错而非仅变慢**
2. **每个 ACF 乘法放大搜索成本**：联合空间＝tile×warp×ACF 候选数的笛卡尔积——所以搜索必须**离线跑，跑完把 ACF pin 进仓库**复用；运行侧只剩施加控件，没有搜索
3. **收益 workload 特定**：nvfp4_gemv 的 4.7% 不自动外推到别的算子/shape

留白三（你来推）：为什么跨架构是「出错」而不是「变慢」？提示：控件作用的三类决策（寄存器分配/指令调度/codegen 启发式）都以目标架构的资源模型为前提——sm_90 与 sm_100 的寄存器文件/调度约束不同。一个为前者调好的分配与调度方案，压到后者身上，最可能出什么类的事故？为什么这类事故的结局更可能是「编译不过/产物错误」而不是「只是慢一点」？

serving 放大缺口（R1 Gaps）：2-7% 的 kernel 收益在 serving 端到端层的放大效应**无公开数字**——博客只有单 kernel 案例。你第 8 课的落差管线（灰度放量/端到端效果验证/推全）在这篇里同样缺席：这是路线 3 整条线的公共缺口，不是本篇独有的短板。

立场层（已裁决，引用不作事实教）：博客说服段——decode 循环里连续运行的高价值 kernel × 大 fleet，底部几个百分点在那个规模上复利（待裁决 6）。你裁决接受，且加了边界：「优化多少要看具体问题」。这一句边界正是把 2-7% 接到美团语境的正确姿态：量级规律给预期，workload 特定性给边界。

## 7｜原创视角：serving 配置面的「默认值从未被搜索过」（判断权在 human）

编译器世界的命题：ptxas 控件默认值＝工程师硬编码启发式，从未被系统性搜索。同一命题平移到你的 serving 栈——**哪些默认值从未被搜过？**候选清单（只罗列，判断权在你）：

- 调度参数：continuous batching 的 batch 上限／调度策略／抢占阈值
- 批处理配置：chunked prefill 尺寸／token budget 切分
- 编译 flag：torch.compile mode、cudagraph 捕获范围与禁用清单
- 内存：allocator 配置（PYTORCH_CUDA_ALLOC_CONF）／KV cache 布局参数

判据就是你裁待裁决 6 时给的那句「优化多少要看具体问题」：高价值路径（decode 主导×fleet 连续运行）上的默认值优先搜，边缘路径不值得。Booster Pack 的对应物也在这条线上：你的优化资产（骨架库/已验证配置）能否预注入搜索当起点——「搜索从资产开始」这条家族特征（第 7 课 z.ai 骨架库 ↔ 本课 Booster Pack），在美团侧的形态是什么，留给第 21 课整合时判断。

## 8｜本课关键概念清单＋费曼引导

1. **控制空间**：ptxas/NVCC 内部控件（寄存器分配/指令调度/codegen 启发式）——默认值＝硬编码启发式，从未被搜索；「已最优」＝默认控件下的**条件最优**，条件本身是未探索维度
2. **RSI 三件套**：proposer＝CompileIQ 进化搜索（population 育种 generations×pool_size；Booster Pack 预调 ACF 目录当先验）→ verifier＝allclose gate＋do_bench 锁频＋Welch t p<0.05 ∩ Cohen's d>0.2 → 产物＝ACF（--apply-controls，CUDA 13.3+，可提交/版本化/复用）
