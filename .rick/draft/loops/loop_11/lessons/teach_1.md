# 第一课 · 级联为何留、为何合

## 先给那句话，后面全是它的展开

OneTrans-V2 改的是级联的「实现方式」——三个各自训练、各自编码的模型，换成共享一套 user context、按 stage token 隔离的一个 backbone；它没改的是级联本身——召回把候选从千万级压到千级、粗排再压、精排最后用最丰富的特征精判，这个三段漏斗原封不动。

一句话：**改「怎么实现」，不改「要不要级联」。** 下面每个词都落到论文事实上，也落到你自己那套粗精融合上。

## 级联为什么存在——先把它放回它诞生时解决的问题

级联不是谁规定出来的，它是对一个物理矛盾的回应：候选规模、特征丰富度、算力预算，三者不能同时要。全量候选千万到亿级，如果每个候选都用最丰富的特征、最深的模型过一遍，算力直接爆掉。所以只能走漏斗：候选多的时候用便宜的东西——轻量特征、简单模型、每个候选极少的算力——把候选砍掉一大半；砍到只剩几百个，再把省下的算力集中，用丰富的交叉特征和深模型精判。

召回、粗排、精排，本质是同一个「用算力换精度」策略在三个候选规模档位上的三档分档（research_1 · A，§1 的级联前提）。这就引出关键事实：级联的存在，是为了解决「特征丰富度 vs 判别候选规模效率」之间的矛盾——候选规模大时判别单位成本必须低、特征必须贫；特征想富，候选就得先被压小（judgment，你的直觉 1 原话）。这个矛盾在生成式推荐里目前没被解决，所以级联仍有存在必要（V1，你已接受）。

## 为什么不删级联——V1 比「保留」更深一层

端到端生成路线（OneRec）想一步到位、绕开漏斗直接生成最终 item。作者的立场是：不行，移除候选特征会显著降低推荐质量（research_1 · A，§1/Figure 1；V1）。注意这句话的精确含义：作者反对的不是「统一」，而是「删级联、删候选特征」。他把「级联要保留」和「三模型各自独立」拆成了两件事——前者必须留，后者恰恰是要消灭的。这是理解全文的第一个分叉点。

## 级联自己带来的四类成本——「合」的必要性从这里来

既然级联要留，问题就变成：传统「每阶段一个模型」的实现方式，自己制造了什么代价。论文 §1 给了四类（research_1 · A，#4）：

1. **工程重复**——三套模型各自训练、各自上线、各自调参维护，工程面和系统面是三份。
2. **行为序列重复编码**——同一个用户行为序列，召回编码一遍、粗排一遍、精排一遍，同一段序列被重复烧三次算力。
3. **孤立优化致跨阶段不一致**——各阶段优化各自目标，召回找回的东西粗排未必认，粗排留下的精排未必认，三段的「品味」对不齐。
4. **容量碎片化**——总算力、总参数量被切成三个互不相通的池子，谁也不能单独吃下整份预算去 scaling。

四类的共同根源是同一个：三模型各自独立。所以「合并」是消除它们的自然方向——消除重复、恢复一致性、把碎片容量重新拼成一个池子。

到这里张力已经成形：级联必须留（V1），但级联的传统实现必须改（四类成本）。留什么、改什么，就是全部问题。

## 合并不等于把三个模型拼成一个——陷阱在这

最直接的合并是：把三个模型的参数塞进一个文件，或者共用一个编码器。但这会踩回 V1 的坑——如果把阶段专用的候选特征也「共享」掉，等于变相删掉了级联的隔离价值。所以合并的关键，是你直觉 1 的原话：**谁共享，谁隔离**（judgment）。

作者给的边界（research_1 · A，#5，§4.1）：

- **共享**：user context——用户行为序列每请求只编码一次，三个 stage 都读它。这是消除「重复编码」的落点。
- **隔离**：stage-specific token + visibility mask——每个阶段保留自己专用的特征 token，且各 stage token 只对共享 context 和自己的 token 可见，看不到别的 stage token。这是保留「阶段专用性」的落点。
- **混合参数化**：候选相关特征不共享，各阶段保留自己的候选特征（承前作 OneTrans）。这是 V1「不移除候选特征」的落点。

于是「一个 backbone 三级联」的全景是：一个因果 Transformer，输入一段用户行为序列 → 编码一次成 shared user context → 召回 task 读 context + recall token，自回归生成语义 ID；粗排 task 读 context + prerank token + 候选特征打分；精排 task 读 context + rank token + 候选特征打分。visibility mask 挡住跨 stage 的 token，保证每个 stage 只能用自己的专用 token 和共享 context。级联的漏斗逻辑——先粗筛、再细筛、最后精判——由「哪个 stage 读哪些 token、用什么特征」来承担，而不是由三个独立模型来承担。

## 回到那句话

现在可以收口。OneTrans-V2 改的是级联的实现方式——把「三个模型」这个载体，换成「一个 backbone + 共享 context + stage token 隔离」；它没改的是级联本身——漏斗还在、候选特征还在（V1）、阶段专用性还在（隔离）。

拿你自己的粗精融合来对照：你们已经把精排和粗排的算力复用做了一部分，那是「共享」方向上的半步（judgment 直觉 3）。OneTrans 相对你的增量不是「更彻底地共享」，而是把「召回」也拉进同一个共享 context，同时用 token 隔离保住三个阶段的专用性——共享和隔离是同一件事的两面，缺一面就不是它。这也正是它相对 MTGR 的延伸方向：MTGR 统一的是单阶段排序，OneTrans 统一的是全级联（research_1 · B，#12）。

## 三个追问（把你的判断逼出来）

1. 你现在的粗精融合里，粗排和精排各自还留着什么「阶段专用特征」？如果并进一个 backbone，你会先坚持隔离哪一类、先愿意共享哪一类——什么证据会让你把某个特征从「必须隔离」改判为「可以共享」？

2. 美团召回现在还走多通道。级联的原始矛盾「特征丰富度 vs 候选规模效率」在你们召回端具体由什么承担——通道规则、轻量模型，还是别的？如果召回也要并进统一 backbone，你判断召回端最不能放弃的一样东西是什么——什么情况下你会改变「它不可放弃」这个判断？

3. 四类重复成本里，你美团现在最痛的是哪一个？若要推动同事一起做全级联统一，你会先拿哪一类成本的实测数据去说服——如果实测出来这项成本远小于你的直觉，你会换哪条说服路径？
