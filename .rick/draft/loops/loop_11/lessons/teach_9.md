# 第九课 · 如何复现 OneTrans-V2：模型结构 / 部署 / 端到端全流程

## 承上：前八课讲完了「为什么」，这一课问「从哪开始搭」

前八课把原理（一至五）、落地与收益口径（六、七）、推动与原创（八）过了一遍。你在 judgment 里最初那句诉求「我要在实际工作中应用」到这里才落到最直接的动作上：动手搭。第六课你已经看到起点不零——美团已有粗精融合（精排复用粗排部分算力，judgment 直觉 3）、MTGR 已全量且被这篇论文引（research_1 · B，#12）。

动手前有一件事必须先做：**把「论文给了什么」和「我按行业惯例补齐了什么」分开。** 这两类东西在实现时长得很像（都是一段代码），出问题时命运完全不同——论文给的那部分出问题，说明你抄错了；行业惯例补的那部分出问题，说明它从来没有人替你验证过。第七课的纪律是「幅度只能自己量」，它的前一步是：知道自己手里哪些是纸、哪些是脑补。

先纠一处前两轮材料里的错。模块九文案（以及前几轮事实版图）写的是「部署拓扑、KV cache、SID 索引论文无工程细节」。research_3 直读全文后更正：**论文有 §5 Serving and System Optimization**（§5.1 在线管线 + §5.2 解码优化、kernel、精度）（research_3 · R7 事实更正，A）。这个更正不是细节——它把「照论文能搭到什么程度」的上界从「架构级」抬到了「架构级 + 部署机制级」。本节把 §5 一并算进「论文已给」。

## 作者给的是机制，不是规模——这条线他自己划的

复现的人第一眼要找的是「多大模型、多少层、多少专家」。论文一律用符号：块数 N、宽度 d、专家数、序列长度、beam 宽 k、top-K（research_3 · #3，A）。他给的是几样别的东西，而且给得相当具体：

- **规模只有三档标签与算力**：L=662 GFLOPs/请求、S=239（≈L 的 36%）、XS 比 L 训练便宜 46×；原三模型级联合计 275 GFLOPs。
- **训练配置却很细**：BF16、per-GPU batch 2048、16 GPU、λ_r=0.1/其余 λ=1、蒸馏 τ=0.5、EMA 0.9999、稀疏侧 AdaGrad lr=0.1、稠密侧 AdamW(β1=0, β2=0.99999, ε=1e-5, wd=0.01)。
- **若干结构线索**：SID 三层每层码本 8192；四维决策前缀占 2 个 token 位。

（读法，非论文逐字）：**他划的线是「机制给全、规模自选」。** 机制决定「你搭出来的东西是不是 OneTrans」，规模决定「你搭出来的是哪一档」。前者不给，你的复现就不成其为复现；后者给死，反而让不同容量点的读者对不上自己的场景——第三课那条「设计是容量的函数」（V3 你已接受）在这里落到了复现上：规模必须由你自己的容量点定。

不过「机制给全就算可复现」这句本身带着一个悬着的判断，values.md 里留着待裁决（V10）。**这张清单的分层，我按的是一个可核对的文本标准：论文是否给出了足以照着实现的结构与机制描述。** 若你改用「能否复现出同一组数值」做标准，同一篇论文会从「层①为主」变成「层②为主」。这条标准由你定。（V7、V8、V9 也仍挂着，各自改这张清单与流程图的读法；本节只标出它们会改什么，不当代你裁决用。）

## 三层清单

### 层① 论文已给：可照着搭到架构级 + 部署机制级

**结构（§4.1 + Fig.2(c) + Eq.1）**：行为 token 在最前、因果自注意力、全序列共享一套 Q/K/V+FFN；每个 exposure/阶段的 stage token 追加其后、用各自专属 Q/K/V+FFN（混合参数化）；召回的追加顺序为 CTX → DT^p → DT^d → SID_0..2。mask 规则：stage token 只能看锚点 a_e 之前的行为前缀 + 自身 + 同阶段同 exposure 更早的 token；跨阶段 / 跨 exposure 互屏蔽；**行为 token 永不看 stage token**——最后这条是「一次编码、三阶段共读」在实现上的根（research_3 · #1，A，[论文已给]）。

**候选 token 预算（§4.2.2）**：粗排把 NS_p ⊂ NS_f 压成**单个候选 token**（每候选预算最紧）；精排保留 NS_f 的**多 token**（压掉会掉排序保真度）（#2，A）。

**召回解码（§4.2.1 + §5.2）**：① 枚举决策的**全部合法组合**，在缓存 ℋ=(𝒮,CTX) 上**一次前向**打出 log P(z|ℋ)；② 每个前缀分加 βφ(z)；③ **一条 beam search 同时扩展前缀与 SID 码**，按 Eq.4 联合打分，返回 top-K 给粗排（前缀分高但引不出好物品的会被压过）；④ 前缀因各维词表小、乘积小到一次前向能打完，被折叠成**单个打分步**，业务偏移就作用在这步（#4/#5，A）。

**两段式 top-k（§5.2）**：先留每 beam 最好的 k 个扩展，再选全局 top-k——结果集与原全局 top-k **完全一致**，每步候选池从「beam 宽 × 词表」降到「每 beam k」（#6，A）。

**SID 取回语义（§4.2.1）**：多物品可共享同一 SID，**凡映射到被检索 SID 的物品全部返回**——这句蕴含「必有 SID→物品 映射结构」，但结构本身没写（#7，A）。

**KV cache / GQA（§4.3 + §7.6）**：共享行为序列的 KV cache 算一次被三阶段 stage token 读、**召回时在 beam 间广播**；它的大小同时决定每步 cross-attention 的显存与访存；GQA 按组数等比缩小且质量基本不变；只需 KV 头数与 head dim 在 stage token 与行为序列间一致，query 头数可不同（#12，A）。

**训练组织 SNT（§4.4 + §7.9）**：mini-batch 按**用户窗口**组织（一窗口 = 一用户一段时间的全部曝光）；序列每窗口只编码一次；每 exposure 保留 request 身份、时间戳、task 身份、阶段特征与标签，但**不带序列副本**；每 exposure 锚定 a_e 只读其前缀（同 request 共享锚点）；序列 append-only ⇒ 旧前缀编码与锚点持续有效；窗口**按天切**、不跨评估日（#8，A）。

**请求相对 RoPE（§4.4 Eq.11）**：exposure 的 query 旋 t_e、行为的 key 旋 t_i，注意力项只依赖 (t_i − t_e)；同 exposure 内相对旋转抵消、**行为自注意力不变**；key 旋转只依赖自身时间戳 ⇒ 旋转后的 key 算一次可被所有请求与阶段复用；多个固定时间周期覆盖长短期（#9，A）。

**在线管线骨架（§5.1）**：在线请求 → 𝒮_u 先过共享因果 Transformer 产出**可复用 user-context cache C_u** → 同一 C_u 供召回/粗排/精排消费；召回 = C_u + NS_r 做 DCGR 解码；粗排/精排是对同一 C_u 的**非自回归候选打分**；候选集仍逐级收缩（#10，A）。**并且论文明说：虽然联合训练成一个 Transformer，serving 仍遵循原 召回→粗排→精排 级联，每阶段只执行自己的候选侧计算**（#11，A）。

**系统优化清单（§5.2）**：stage token × 共享序列的注意力用 FlashAttention 风格 kernel、**自带 stage visibility mask**、一次调用覆盖某用户全部候选、不 padding 不物化注意力矩阵；QKVG 融成无 bias GEMM 且输出原地消费；QKNorm 用偏移寻址 RMSNorm kernel；SwiGLU 的 gate+up 合并为一个 GEMM；隐藏向量 16B 对齐以发射 128-bit 向量化 load（#13，A）。

**精度取舍（§5.2）**：serving 默认 **FP16**（推荐侧浮点特征需保值域与精度），把占 TransBlock 约 **2/3 FLOPs 的 SwiGLU GEMM 下推 FP8**；另有一个训练做不到的融合——gate-up+down+scaled residual 合成单 kernel（serving 无反向、不需中间激活）（#14，A）。

**加速数字（§7.9；自述、不可独立验证）**：两段式 top-k → 吞吐 **19.7×**、单请求 beam 搜索延迟 **2.3×**（改前该步占召回推理时间 **94%**）；前缀单步打分 → 延迟再降约 **30%**、累计解码 **27.6×**；精排相对已部署精排 0.58× →（kernel fusion）1.66× →（FP8）**2.16×**；三阶段共享 C_u 再叠 **1.53×**；合计端到端 **3.2× QPS**（#15，A）。**机制可照搭，倍数不可照抄。**

读这张图有三个地方值得停一下：

## 从哪开始搭：四条可切入的路线（并列，判断权在你）

- **甲 · 从「共享 context + mask」切片起步**（层①最密、半径可控）：不碰召回、不换架构族，先把「序列编码一次、粗精两阶段读同一 context、各自 stage token 与 mask」做出来，用你自己的流量测两件事——重复编码占多少算力、质量掉不掉。机制全在层①；「值不值得」的答案只能从你自己的数里来。
- **乙 · 从「决策前缀 + 软偏移」切片起步**（机制在层①、在线部分在层③）：召回保持打分式，把「走哪个目标」从外部路由改成模型预测的决策前缀，再加 β 软偏移（第四课的乙/丙落点）。β 的具体取值在层②，标定要你自己做。
- **丙 · 从系统侧切片起步**（层①，但依赖 V8/V9 待裁决）：两段式 top-k、kernel 融合、精度下推这三样不依赖建模收益、可独立量化，论文也给到机制级（§5.2）。它算不算「复现」的一部分，取决于你把哪些工程投入算进这件事的价值里（V8/V9 待你裁决，我不替你定）。
- **丁 · 从训练组织切片起步**（层①、不动在线、代价最低）：SNT 按用户窗口切 mini-batch、序列每窗口只编码一次，先离线验证「训练提速 / 存储下降」在你家数据上成不成立（论文自述 4.4× / −95%，层②不可照抄）。第六课把「按天切窗 vs 你们评估口径」列为未明（research_1 · R7），这个卡点正好在这一格被逼出来。

四条互不排斥，差别在「先改在线还是先改离线、先拿建模收益还是先拿系统收益」。哪条先动，取决于你手里的人力与能承受的回滚半径——这是你的判断。
