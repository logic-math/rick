# 第五课 · 凭什么继续 scaling

## 承上：骨架搭完了，接下来问「它能长多大」

前四课把结构讲完整了：级联要留、只改实现方式（第一课）；一个 backbone 里共享表示、隔离 token、半共享权重（第二课）；一致性来自联合训练 + 精排→粗排蒸馏，而整套设计是容量的函数（第三课）；召回被并进同一个模型，「走哪个目标」从外部路由变成模型预测的决策前缀 + 在线偏移（第四课）。

到这里 OneTrans-V2 的「结构」已经齐了。但你在判断里留的那句话还没被接住——你说它要解决的是「级联范式下工程效率低、计算重复等问题，这些系统性问题导致模型无法继续 scaling up 的扩展」（judgment 直觉 2）。「合」把结构收成了一件；**凭什么合完之后就能接着往上长**是另一件事。这一课只追这一件：scaling 的阻碍从哪来，三个引擎各解除哪一段。

## 作者手里的问题：统一本身不给效果，给效果的是容量

先把因果掰直：把所有阶段并进一个 backbone，**本身不带来任何指标收益**。它带来的是被腾出来的一条通道——原来想涨容量，要三份模型一起涨、三份序列各编码一遍、三份超参各调一遍（第一课的四类重复成本）；这些重复消掉之后，容量第一次变成一根**可以单独往上推的轴**。

所以作者的问题不是「怎么更省」，而是反着问：**腾出来的这根轴，怎么才推得动。** 看它的参照系不该是「模型能力」，而是一笔边际成本的账——每涨一单位容量，要付多少算力、多少轮超参搜索、多少训练期的重复编码。第三课讲过的 D=f(C)（设计是容量的函数）说的是「换容量要换设计」；这里问的是「这根轴本身，工程上到底扫不扫得动」——扫不动，f(C) 就只是纸上一根曲线。

（V4 你已接受的那句「为……更广泛转型提供了生产级基础」，分量就落在这里：生产级 = 这根轴在生产约束下真的能扫。）

## scaling 的阻碍，拆成三笔具体的账

「重复成本阻碍 scaling」听上去像一句总结。拆开是三笔不同的账，卡在不同的地方：

1. **算力账（推理侧）**：涨容量 → 每 token 激活算力与显存流量跟着涨。稠密模型里参数和每 token 计算绑在一起，容量涨一倍、算力差不多也涨一倍——这是「容量碎片化」在单模型内部的版本，只是从「三个模型分掉容量」变成「容量与算力绑在一起」。
2. **调参账**：换容量 → 超参失效 → 重搜。每往上推一档宽度/深度就要重扫一遍学习率和初始化；扫一轮的成本可能比那一档容量带来的收益还大。
3. **数据账（训练侧）**：涨曝光、涨序列 → 同一段行为被反复编码。请求侧是同一序列被三阶段各编一遍；训练侧是同一用户窗口里的多次曝光各带各的上下文、逐条编一遍。

**哪一笔是决定性的，我给三个备选、不替你收敛**：甲·算力账（容量与算力耦合）→ 关键在 MoE；乙·调参账（换容量的固定成本）→ 关键在 μP；丙·数据账（训练侧重复编码）→ 关键在 SNT。哪一笔是根本性的成因，取决于你站在哪个容量点、受什么工程约束——论文只给了它自己那侧的答案。

下面三个引擎逐个收，最后回到这三笔账上算一次总账。

## 引擎一 · 稀疏 MoE：把「容量」和「每 token 算力」拆开

（research_1 · A，#8，§4.3；research_2 · #12）

做法：**DeepSeekMoE 式的细粒度专家 + SwiGLU + sigmoid 路由 + 常驻共享专家**。

先讲清它解除的是哪一笔账。稠密 FFN 里，「总参数量」和「每 token 要算的参数量」是同一个数——你没法只要前者。MoE 把 FFN 换成一组专家 + 一个路由：每个 token 只被路由到少数几个专家，只有被选中的专家参与计算。于是：

- **总参数量（容量）**：涨上去——专家池可以很大；
- **每 token 激活算力 / 显存流量**：不跟着总容量线性涨——大多数专家这一 token 根本不动（research_2 · #12）。

这是「解耦」的准确含义：不是「算力变小」，是**容量和算力成了两个可以分别转的旋钮**。第三课那句「你可以参数翻倍但每 token 算力几乎不变」，机制就在这儿。

四个配置细节各自的角色（论文给的是配置，逐字的「为什么」材料未展开，以下按标准读法标注）：

- **细粒度专家**：专家切得更小、更多，路由能让不同 token 走不同组合，专业化的粒度更细；
- **常驻共享专家**：每个 token 都会过的几个专家，兜住所有 token 共有的知识，让「专业化」专家去管真正特殊的部分；
- **sigmoid 路由**：给每个专家一个独立的门控分（标准读法：不像 softmax 那样让专家在归一化上互相挤压）；
- **SwiGLU**：FFN 的激活形式。

（边界：MoE 的代价论文没在这门课的材料里展开——专家并行的通信、负载均衡、专家坍缩这些工程问题，research 材料未覆盖；真要落地，这是你必须自己调研的一档，我不替你脑补。同理，专家数/层数/参数量论文都没给，research_1 · R7/Gaps 已列。）

## 引擎二 · μP / Depth-μP：让「换容量」不再等于「重搜超参」

（research_2 · #13，§4.3；第三课已讲过含义，这里只收口）

第三课拆过机制：width-μP 按 ×1/m_d 缩放初始化方差与学习率（m_d = 宽度倍率），Depth-μP 按 ×1/√m_N 缩放残差乘子与学习率（m_N = 深度倍率）；作用是加宽/加深时超参按公式迁移、不用重搜。

本课只补它在 scaling 里的位置：它解除的是第二笔账（调参账）。**没有它，容量轴是「一档一档买」的——每档都付一轮超参搜索；有它，容量轴变成连续可扫的**——小宽度调好的那套超参按公式搬到大宽度。这也正是第三课那句「只有能廉价地扫容量，D=f(C) 才不是一句哲学表态」的工程侧支撑：**MoE 让「涨容量」买得起，μP 让「换容量」试得起。**

同一节还挂了 QKNorm、门控注意力、GQA（research_1 · A，#8）。它们不是容量机制，是大规模下的**稳定性与显存**手段：GQA 压 KV cache、QKNorm 稳注意力数值、门控注意力调信息流。放在这一课的位置很自然——容量推上去之后，先撞墙的往往是数值稳定和显存。

## 引擎三 · SNT：把训练侧的「重复」翻成「复用」

（research_1 · A，#9，§4.4 / §7.9）

前两个引擎管「模型能多大」，这个管「训练要多久、要存多少」。

做法一句话：**按用户窗口分组曝光；一个窗口内的行为序列只编码一次；窗口内每次曝光以「因果视图」复用这份编码；时间信息用请求相对 RoPE 编码。**

拆开看，它正好把第三笔账翻了过来。训练样本的传统形态是「一条曝光 = 一段用户序列」——同一个用户窗口里的 N 次曝光，就有 N 份高度重叠的序列被各编码一遍。SNT 换了组织方式：先按用户窗口分组，序列**每窗口编码一次**；组内每次曝光不再重新编码，而是从这份编码里取一个「因果视图」——它在窗口内的位置决定了它能看见哪些行为（不能看见未来行为，这是因果性），时间上用「相对该次请求」的 RoPE 位置表达，而不是绝对时间。

收益（论文自述，research_1 · A，#9）：**训练提速 4.4×、序列特征存储 −95%**。这两个数字对应的正是那笔账的两个面——算（编码次数少了）和存（同一窗口一份特征，而不是 N 份）。

我的读法（标注为读法，非论文逐字）：SNT 的动作不是「优化」某个环节，而是**改掉了「一条训练样本」的定义**——从「一次曝光配一段序列」变成「一个用户窗口配一份编码 + 组内 N 个视图」。于是「同一窗口内的重复」从成本变成了复用的来源；它在三个引擎里也最轻，因为不动模型结构、只动数据组织。

## 三笔账合起来看，以及一个需要你自己判的张力

机制上，「重复成本阻碍 scaling」是这么被解除的：MoE 让**容量买得起**（算力账）、μP 让**容量试得起**（调参账）、SNT 让**训练付得起**（数据账）。三件都不是「让模型更强」的花招，而是把容量轴的边际成本压下来——成本上先可行，scaling 才谈得上「继续」。

但有一个数字上的张力，材料里没有被解答，摆给你：

- 论文自述：OneTrans-V2 L 版 **662 GFLOPs/请求**；原三模型级联合计 **275 GFLOPs**（research_1 · A，#10，Table 2）。统一之后，每请求算力**涨了约 2.4 倍**。
- 同一篇论文自述：同硬件预算下端到端 **QPS 3.2×**（research_1 · A，#11，§6.3；闭源自述、不可独立复现）。

**算力涨了，吞吐反而更高**——这和「省算力」的直觉是反的。可能的解释是几条不同层面的账，并列摆开、不替你收敛：

- **甲（MoE 侧）**：总容量涨了但每 token 激活算力不线性涨；662 GFLOPs 是「容量载体变多」，不等于「每个 token 都变贵」。
- **乙（共享 context 侧）**：用户序列每请求只编码一次，原来三阶段各编一遍的重复被消掉（research_1 · A，#4/#5）。
- **丙（显存/缓存侧）**：GQA 压 KV cache，显存流量下降，吞吐的受限点从算力挪到了内存。
- **丁（工程侧）**：一个模型一次调度替代三个模型三次调度，服务编排、特征拼接、跨阶段数据搬运都少两轮（这一条是推断——论文只在架构级描述「每请求编码一次」，逐项归因未给）。

（诚实标注：**把 3.2× 归因到哪一条，论文没有逐项拆解**，research_1 也没有；上面四条是按已知机制列的候选解释，不作事实用。GFLOPs 与 QPS 是否同一批请求、同一套硬件口径，材料未明。）

## 这一课带走两样

- **一句可复述的账本**：scaling 的阻碍 = 三笔账（算力/调参/数据）→ 三个引擎分别解除（MoE / μP·Depth-μP / SNT），解除之后容量轴才「买得起、试得起、付得起」。
- **一张你落地时缺的参数清单**：论文给了 GFLOPs（662 / 275）和相对增益，**没给参数量、专家数、层数、序列长度**（research_1 · R7/Gaps；research_2 · D-Gaps 同）。也就是说，这一课能告诉你「容量轴怎么才推得动」，告不了你「推多少」——推多少只能从你自己那条 D=f(C) 曲线上量出来。

## 落点并列（判断权在你）

从「能继续 scaling」到你美团的动作，三条并立，各有代价：

- **甲（按顺序全上）**：MoE + μP 扫容量 + SNT 重组织训练样本。完整，但每一块都是独立工程摊子，MoE 的专家并行/负载均衡尤其重。
- **乙（只挑与你瓶颈对应的那一笔账）**：先测你现在扩容卡在哪笔账——每 token 算力/显存（→MoE）、换规模就要重搜（→μP）、训练里同一用户的序列被反复编码（→SNT）；只上对应那一个。
- **丙（先不上，先量）**：不动架构，先把容量点与边际成本曲线量出来（涨一档容量，算力涨多少、吞吐掉多少、训练时长涨多少），再决定转哪个旋钮。SNT 是三者里最容易先试的——它改数据组织、不改模型结构。

三条不冲突，差别只在「先量还是先上、先上哪个」——这是你的判断。

## 追问（把判断逼出来，不是考你）

（前四课的追问你都跳过、直接推进了；这一课的问恰好是那几问的落点——「你站在 D=f(C) 哪一侧」要答出来，绕不开第 1 问。）

1. 你美团现在的扩容瓶颈落在哪一笔账上——每 token 算力/显存、换规模要重搜超参、还是训练里用户序列被反复编码？你手上现成有哪几个数（显存流量占比、单次扩容后调参的人天、训练集里同一用户窗口的编码冗余度）能支持这个判断？反过来，哪个数会一致地把你推向另一笔账？

2. 三个引擎里 SNT 最轻（只动数据组织）。你判断它在美团的第一个卡点会落在哪——是现有训练样本的切分方式与「按用户窗口分组」的对接成本，还是「窗口按天切」与你们评估口径的兼容性（research_1 · R7 把这条列为未明）？出现什么情况，你会把它从「可以拿一个业务场景先试」改判成「得先做一轮专项调研」？

3. 论文自述里每请求算力涨到 2.4 倍、吞吐却是 3.2×。如果在你自己的系统里也实测出「算力涨、吞吐也涨」，你会把它当成「容量还有空间、继续加专家」的信号，还是「受限点已从算力挪走、去查那处」的信号？你先看哪个指标来分辨这两者，而它反向时会怎么改写你的结论？

4. 第四课留下的问题在这里换了形状：如果召回也并进同一个 backbone（甲路线），scaling 的账会变成什么样——三阶段的容量需求同时在涨（那 MoE 专家池要不要按阶段分），还是召回更吃序列长度、粗精排更吃特征（那容量该往哪边加）？出现什么现象，会让你认为「三个阶段共用一个专家池」这个前提不成立？
