# 第三课 · 级联一致性从哪来

## 承上：共享了 context，不等于品味一致

前两课收口在两句话：改「怎么实现」不改「要不要级联」（第一课）；「谁共享谁隔离」拆成表示层共享、token/特征层隔离、可见性层 mask、权重层半共享半局部（第二课）。但这两课只回答了「架构长什么样」。还有个更刺的问题没碰：三个 stage 现在读同一份 user context，可它们仍然各自打分、各自优化，凭什么对「什么是个好候选」的判断会对齐？

这正是 §1 四类成本里的第三类——孤立优化致跨阶段不一致（research_1 · A，#4）：传统级联里召回找回的东西粗排未必认、粗排留下的精排未必认。合并只把三阶段放进一个 backbone，共享 context 只解决「重复编码」，不自动解决「品味漂移」。这一课只追一件事：级联一致性从哪来——以及你标记过「不懂」的那个「容量函数」（V3）为什么和它绑在一起。

## 作者手里的问题：品味不一致，且不能靠删专用性去解决

三个 stage 的品味为什么会漂？各自独立的模型、各自的目标、各自的候选特征，谁也不会为「另一个阶段认不认」负责。要消除漂移，最省事的办法是让三个阶段共用一个目标、共用一套特征——但那会踩回 V1 的坑：删掉阶段专用性等于删掉级联本身（V1，你已接受）。

所以作者的问题被逼窄成：在保留阶段专用性的前提下，怎么让三个阶段对「好候选」的判断收敛到同一套品味。他的答案有两半，各解决一半。

## 一致性来源一：联合训练，让 context 被迫对三个 task 都好

共享 user context 不是「三个模型共用一个编码器、各训各的」，而是三阶段联合优化、同一个反向传播（research_1 · A，#6，§4.2.2）。含义是：那份 context 的每一次参数更新，都同时收到召回、粗排、精排三个 task 的梯度。编码不再只服务一个阶段，而是被三个 task 一起塑造——这是「世界观」层面的一致性：三个 stage 读的是同一份被三方共同打磨过的用户表示，而不是三份各说各话的表示。

注意「联合训练」和「共享参数」是两回事：共享的是被梯度一起塑造的表示（context），不是把三阶段的打分目标也搅成一个。目标仍各自保留（否则违反 V1），但表示被三方共同收口。

## 一致性来源二：模型内蒸馏，让细的品味反向教粗的

表示一致了，打分还会漂——因为粗排特征贫、精排特征富（V1 保留候选特征的意义），同一个用户表示之上，粗排能用的信息和精排差一截。论文给的解法是模型内蒸馏：精排当 teacher、粗排当 student，把精排的 logit 分布作为粗排的软标签（research_1 · A，#6，§4.2.2）。

为什么 teacher 是精排、不是反着？精排是级联里品味最细的一级——最丰富的候选特征、最细的判别。让细的教粗的，就是把「细品味」反向灌进「粗品味」：粗排不再只学自己的粗目标，还学「精排会怎么判」。配方是 mean-centering + 温度 τ=0.5；mean-centering 去掉 logit 的绝对偏移、只传相对排序，τ=0.5 把分布压平、软化教师信号——这两句是标准知识蒸馏的读法，论文给的是配方，逐字的「为什么」未在材料里展开，如实标注。

真正值得注意的一点：无需独立教师。teacher 和 student 住在同一个 backbone 里，蒸馏是同一反向传播里的一条梯度通路，不是「先训好精排、冻住、再去教粗排」。这是一致性的工程代价被压到极低的原因——它没有引入额外的教师训练/同步成本（research_1 · A，#6，§4.2.2）。

边界（不替你脑补）：论文明说的是精排→粗排这一对。召回是生成式、产出的是 SID 而非打分 logit，它是否也在蒸馏链条内，材料未说，不当作事实。

## 品味一致，到此才算一个整体

把两半拼起来看：联合训练管「世界观」——同一份 context 被三个 task 的梯度一起塑造；蒸馏管「打分品味」——细的精排把判断反向灌给粗的。二者都不删阶段专用性（V1 保住），却把「各训各的、各判各的」收成「共用世界观 + 细教粗」。

到这里可以回答三个阶段的品味为什么会一致：不是因为谁给谁下了条规则，而是因为共享的表示被三方梯度共同收口、且最强的品味顺着蒸馏通路反向流动。一致性是机制的结果，不是口号。

## 但这一整套设计，本身是「容量的函数」——把你标的不懂讲透（V3）

你裁决 V3 时留了一句：认可「设计是容量的函数」，但「什么是容量函数，我不太了解」。这里拆开讲。

先拆三个常被混在一起的量：

- **容量 = 参数量 / 表示能力**。模型能「装下」多少知识、能表示多复杂的映射。涨参数，就是涨它装知识的上限。
- **GFLOPs = 算力**。每请求、每 token 要烧多少乘加。它是推理成本，不是模型「装了多少」。
- **序列长度 = 输入上下文**。喂多少历史给模型看。它是输入规模，不是模型本身的容量。

三个量各自独立地动。你可以「参数翻倍但每 token 算力几乎不变」——稀疏 MoE 干的就是这件事：总参数量（容量）涨上去，但每 token 只激活少数专家，激活算力和显存流量不跟着总容量线性涨（research_2 · #12，§4.3）。所以「容量」和「算力」在 OneTrans 里是解耦的两个旋钮，不能拿 GFLOPs 当容量、也不能拿序列长度当容量。

「容量函数」说的就是一句话：某个设计选择 D 不是固定的，而是容量 C 的函数——D = f(C)。论文 §7.8 的例证：多模态 embedding 直接喂入（raw）vs SimTier 直方图（压缩），「仅在容量充足时」直喂才有利（research_2 · #12，§7.8）。

工程翻译这句：小模型参数少、表示能力装不下高维原始 embedding 里的信号，原始 embedding 对它近似高维噪声，压缩成直方图反而把「有用信号」显式摆出来，所以小容量下压缩赢；大模型参数多，有足够的表示能力自己从原始 embedding 里把信号学出来，此时再压缩就丢信息、成了瓶颈，所以大容量下直喂赢。「哪个设计好」没有绝对答案，只有「在哪个容量点切换」的答案。

于是「设计是容量的函数」的落地含义：你不能把论文在它的大容量下最优的配方，原样搬到你美团的容量点。多模态 embedding 直喂还是压缩、蒸馏要不要加、一致化怎么做，都得先问「我站在 D=f(C) 这条曲线的哪一侧」。

最后补 μP / Depth-μP 为什么在这里出现——它们让「扫容量」这件事变便宜，从而让「D=f(C)」可以被探出来：

- **width-μP（按宽度）**：加宽时，初始化方差和学习率按 ×1/m_d 缩放（m_d = 宽度倍率）。宽度翻倍、每神经元收到的输入翻倍，不缩放则激活/梯度的尺度会漂、老超参失效；缩放后，小宽度调好的超参按公式直接搬到大宽度，不用重搜。
- **Depth-μP（按深度）**：加深时，残差乘子和学习率按 ×1/√m_N 缩放（m_N = 深度倍率）。N 层残差叠起来、信号幅度随深度累积漂移，把残差分支乘 ×1/√N 稳住幅度，超参按公式搬（research_2 · #13，§4.3 scaling 规则表）。

共同点：它们把「换一个容量」从「重新调一遍参」变成「按公式换算」——容量于是变成一根可以廉价扫描的轴。只有能廉价地扫容量，V3「设计是容量的函数」才不是一句哲学表态，而是一条可探、可验证的曲线。

## 落点并列（判断权在你）

一致性可以从哪来、容量切换点落在哪，几条并立摆开，不替你收敛：

- **甲（作者）**：一致性 = 联合训练共享 context（世界观）+ 精排→粗排 logit 蒸馏（细教粗）。
- **乙（你现有）**：你们粗精融合共享算力，但两段品味对齐靠什么——共享特征、人工阈值对齐、还是各自漂着？这条要你自己答，材料里没有你的答案。
- **丙（容量切换）**：美团规模（参数量、行为序列长度、候选规模）落在 D=f(C) 哪一侧，只有你的实验能答；论文只给了它那一侧的证据。

## 追问（把你的判断逼出来，不是考你）

1. 你们现在粗排和精排的品味，靠什么对齐？如果你实测出两段的排序一致性（比如同批候选的序相关）低于某个值，你会补什么机制——蒸馏、共享特征、还是先改目标？什么数字会让你改变现在「靠什么对齐」的选择？

2. 蒸馏方向是精排教粗排（细教粗）。你会不会反向做（粗教细，或者召回教粗排）？在什么证据下（比如粗排特征在某些场景其实比精排更全），你会把 teacher/student 反过来？

3. 你美团现在的「容量点」——参数量规模、序列长度——大概在 D=f(C) 的哪一侧？你判断多模态 embedding 现在是该直喂还是压缩，什么实验（比如把 embedding 从压缩换成直喂后 AUC 的变化方向）会让你改变这个判断？

4. 稀疏 MoE 解耦了「容量」和「每 token 算力」。如果你们现在扩容的瓶颈其实是「每 token 算力/显存」而非「参数」，你会先上 MoE 还是先上别的？什么实测（比如显存流量 vs 参数量的占比）会让你改判扩容瓶颈在哪？
