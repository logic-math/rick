# 第四课 · 召回怎么被统一

## 承上：召回端还是「一个模型管不了那么多目标」的老样子

前三课收口在三处：级联要留、只改实现方式（第一课）；一个 backbone 里「共享表示、隔离 token、半共享权重」（第二课）；品味靠联合训练 + 模型内蒸馏对齐、且整套设计是容量的函数（第三课）。但有一个 stage 前三课都只是路过：召回。第二课的数据流里，召回 task 读 context + recall token、自回归生成语义 ID，那一行下面标着「模块四展开」——今天展开它。

为什么单独开一课？因为召回是美团现状里离「统一」最远的一段——前面几课已经确立：美团召回仍走多通道，而粗排精排你们已融了一部分（judgment 直觉 3）、MTGR 统一了单阶段排序（research_1 · B，#12）。唯独召回还停在「一个业务目标一条通道 / 一套规则路由」的老结构上（论文也未覆盖字节 vs 美团召回通道数的差异，research_1 · Gaps）。所以今天只追一件事：在「统一成一个模型」的约束下，多召回目标这件事，作者是怎么重新安置的——它没被删，也没被塞回独立通道。

## 作者手里的问题：目标本身，该怎么从「通道」变成「预测」

先还原他面对的老结构。召回端传统上要服务多个目标——点击、下单、高客单、发现新鲜、广告供给，各归各的通道：每个目标一个召回通道（或一条规则路由），各配各的模型和工程，请求来了由外部路由决定走哪条。这套结构成熟、可控，但它有两个代价，正好戳中第一课的四类成本：

1. **工程与容量碎片化**：N 个目标 = N 套模型/工程，容量被切碎（research_1 · A，#4 第四类成本在召回端的投影）。
2. **目标被「外置」了**：目标是路由规则写在模型外面的东西，模型自己不知道「这个用户此刻该往哪个目标走」，只能被动接收路由的结果。模型越强越浪费——它学了那么多用户上下文，却没机会参与「该走哪个目标」的判断。

于是作者的问题被逼窄：在统一单模型里，怎么既保住多目标（不能删，删了就丢多样性），又不让目标回到「外部通道/规则」的老路（那会重新碎片化、重新外置）。他给的方向，就是 V6 你已接受的那句：**业务目标不是独立通道，而是决策空间的一个区域；决策是模型预测的结果，不是用户显式选择**（values V6）。

## 他的答案：先让模型自己「预测一个决策」，再在预测上做偏移

（DCGR 机制，research_2 · A / research_1 · #7，§4.2.1）

**第一步 · 四维决策前缀 z：模型自预测，非外部指定。** 作者在召回生成之前，插了一个「决策前缀」z，四个维度（research_2 · #1，§4.2.1）：

- **z_oc 购买等级**：无购买 / 一次 / 多次，3 值。
- **z_aov 消费等级**：每单价值区间，取值「a few」个。
- **z_disc 新颖等级**：候选类目相对用户近期行为的新颖度。
- **z_ad 供给类型**：自然 / 广告，2 值。

关键不在「四个维度」，在于这四个值**是谁给的**：z_oc / z_disc / z_ad 三个并行维度，各由一个轻量 decision head 从 CTX 位置隐态预测，三者 embedding 求和成一个并行决策 token DT^p；z_aov 依赖购买等级（先知道「买不买」，价值区间才有意义），在 DT^p 之后预测成依赖 token DT^d（research_2 · #2，§4.2.1）。随后才自回归生成三级 SID。

这里有一处作者刻意划的界，值得你盯住：决策是**模型从用户上下文预测的结果，不是外部传入**——论文明确把它和 UniR2/UniSGR「外部指定的 task token」区分开（research_2 · #4，§4.2.1）。这就是「目标从通道变成预测」的精确落点：过去是路由在模型外面决定「走哪个目标」，现在是模型自己看着用户上下文，先预测「这个用户此刻落在决策空间的哪个点」，再照着这个点生成 SID。

**第二步 · 三级 SID：决策之后的生成。** 决策前缀之后，自回归生成三级 SID（SID_0, SID_1, SID_2），RQ-KMeans 每层码本 8192（research_1 · #7，§4.2.1）。生成的是语义 ID，不是打分——这是召回从「打分」变「自回归生成」的路线，前几课点到过。今天的重点是决策前缀怎么和这段生成接起来、偏移加在哪。

**第三步 · 训练/推断口径：前缀被折叠成「一个打分步」。** 训练时，决策与 SID 在自回归顺序下用交叉熵，ground-truth 决策在对应位置 teacher forcing——标签直接读日志（research_2 · #3，§4.2.1）。推断时，枚举 z 的全部合法组合、在缓存的用户上下文上一次前向打分，把前缀折叠成单个打分步——业务偏移就作用在这一步（research_2 · #3 + Retrieval Decoding Optimization）。这句是工程落地的关键：偏移不是对每个候选物品去算，而是对「决策前缀」这一个打分步去算。

## β·φ(z)：偏移只加在决策前缀上，不动物品项

到这里是机制的另一半。前面解决了「目标放进模型内」，但业务还要能在线调——今天想多一点 GMV，明天想多一点供给，不能每次都重训。作者给的是 Eq.4（research_2 · #5，§4.2.1）：

**打分 = log P(z|H) + β·φ(z) + Σ_{ℓ=0..2} log P(SID_ℓ | H, z, SID_<ℓ)**

拆开三件事：

1. **β·φ(z) 只加到决策前缀分数**——不动 SID / 物品项那一串（research_2 · #5）。含义：偏移只改变「哪个决策前缀胜出」，给定决策下物品的分布 P(Item|H,z) 不变——模型在那个决策下，仍返回它自己认为最可能的物品（research_2 · #8）。
2. **φ 逐维度、β 单标量**：φ_j 给维度 j 的每个取值一个偏置分，φ(z)=Σ_j φ_j(z_j) 跨维度求和；β 是单一标量，控制整个偏移强度；β 在线可调、无需重训（research_2 · #6）。
3. **它的数学身份**：q(z) ∝ P(z|H)·e^{βφ(z)}，是 max_q E_q[φ(z)] − (1/β)·KL(q‖P(·|H)) 的解——离线 RL 的 KL 正则化 improvement step（引 [26]，类比 Multi-Game Decision Transformer [19] 的单标量版）（research_2 · #7）。φ(z) 扮演「业务价值/优势函数」，β 是逆温度强度。

这三件事合起来，就是 **β 增减的含义**（这一课要带走的头一样东西）：

- **β=0**：q 退化成 P(z|H)，完全恢复模型自身排序，业务偏移归零。
- **β 越大**：KL 约束越松，越偏向让 φ(z) 高的决策胜出，越偏离模型自身排序、越偏业务目标。
- **关键**：无论 β 多大，动的只有「哪个决策前缀胜出」，物品项在给定决策下的相对排序不动。

## 软偏移 vs 硬强制——这一课要带走的第二样东西

β·φ(z) 是「软」的。论文另有一个「硬」的对照组，就是 Table 5 的干预：**解码期把单个决策维度钉死为某值**（forcing one decision dimension to a value at decoding time），其余维度仍自回归解码（research_2 · #9，§6.3/Fig.8(b)）。这是「规则/硬约束」式干预。

两者数字（Table 5，同一模型召回阶段线上 A/B，相对「使用预测前缀」，仅统计 V2 召回名下曝光；research_2 · #10，B 级转载）：

- 强制 z_oc=0（click）：CTR +8.2% / Orders −10.4% / AOV +5.8% / **GMV −5.1%**
- 强制 z_aov 最高档：CTR −8.1% / Orders −33.5% / AOV +38.9% / **GMV −7.7%**
- 软偏移 弱 β：+2.2% / +4.9% / +2.5% / +7.5%
- 软偏移 中 β：−0.9% / −3.0% / +13.9% / +10.4%
- 软偏移 强 β：−5.4% / −1.2% / +28.3% / **+26.7%**

先看准一件事，别被「软就赢」带偏：硬强制在单项上也是赢的——钉死 z_oc=0，CTR +8.2%、AOV +5.8%（这正是 V2 裁决时你看到的「Table 5 硬强制在 CTR/AOV 单项也有正收益」）。所以「软 vs 硬」的差别不在「谁单项更赢」，而在别处。

差别在两处：

1. **硬强制钉死一维，其余维度被迫补偿**：钉死 z_oc=0 等于让全部流量往「点击优先」的决策走，不管这个用户本来有没有下单倾向——结果是 Orders −10.4%、GMV −5.1%。钉死 z_aov 最高档更极端：AOV +38.9% 的代价是 Orders −33.5%、GMV −7.7%。它把决策分布压成一个「角点」，没有中间态。
2. **软偏移是整条分布平滑倾斜，且 β 是一根在线旋钮**：强 β 也损 CTR（−5.4%），但 Orders 只 −1.2%，GMV +26.7%——因为它有 KL 项兜着，q(z) 不能彻底塌到角点（research_2 · #7 的 KL 正则）。更重要的是 β 在线可调、可回退（β=0 一键恢复），在 Pareto 面上找哪一点不用重训。

一句话给你带走：**软偏移是「在决策前缀分布上加一个可调的倾斜」，硬强制是「把决策分布钉成一个角点」；β 是控制倾斜程度的单标量旋钮，β=0 恢复原排序，β 越大越偏业务目标，且无论怎么偏都不动物品项。**

（边界，点到为止）：Table 5 是 DCGR 归因口径、只统计 V2 召回名下曝光，数字里含向其他通道的曝光再分配；Table 6 是第二召回阶段、系统全口径，同样的偏移系统净 GMV 增益小得多（加 z_aov 强 → GMV +3.0%）（research_2 · #11）。这一对口径的张力今天不展开，模块七专门讲。另外「硬强制 ≈ β→∞」是否等价，论文未明说，research_2 列为未收敛（Gaps），我也如实标出，不当结论用。

## 决策空间区域 vs 独立通道——V6 的落点

把前面两条机制合起来，就是 V6 的完整含义（values V6，你已接受）：

- 传统：一个业务目标 = 一条独立召回通道，外部路由决定走哪条。
- OneTrans：一个业务目标 = 决策空间的一个区域，模型先预测用户落在决策空间的哪个点，β·φ(z) 决定这个区域被强调到多重。

多目标没被删——四个决策维度张成一个决策空间，每个目标对应其中一块区域；多目标也没回到独立通道——单模型覆盖整个决策空间，不再 N 通道 N 套模型。这就是「召回被统一」的完整图景：统一的是载体（一个模型覆盖所有目标区域），保留的是目标多样性（决策空间的区域还在），调控从「外部路由」降为「线上偏移」。

## 落点并列（判断权在你）

美团的召回还是多通道。从多通道走到 DCGR，有几条不同深度的落点，并列摆开，不替你收敛：

- **甲（作者的完整方案）**：召回并入统一 backbone，四维决策前缀 + 三级 SID + β·φ(z) 在线偏移。最彻底，也最重——召回要改成生成式、要建 SID 检索索引、要训决策头。
- **乙（只借「决策前缀 + 偏移」的思想，不动生成式）**：召回仍打分式，但把「走哪个目标」从外部路由改成模型预测的一个决策分，加在线偏移调权重。不碰 SID 检索，落地轻，但拿不到生成式召回带来的东西。
- **丙（只借「软偏移」）**：保留现有多通道，只把各通道间的流量分配从硬规则改成 β 式软偏移。改动最小，但目标仍在通道层、没内化进模型。

三条的差别不在「要不要统一」，而在「内化到哪一层」：目标内化到模型内（甲乙）还是停在通道层（丙）；载体换成生成式（甲）还是保持打分式（乙）。哪个先做，取决于你美团召回端的现状与目标组合——这是你的判断。

## 追问（把你的判断逼出来，不是考你）

1. 你美团召回现在的多个目标，是「一个目标一条通道」还是「一条通道内多目标打分 + 路由」？如果要把「走哪个目标」从外部路由改成模型预测的决策前缀，你判断召回端今天最不能丢失的一维是什么（客单、新颖、供给、别的）——什么线上数据（比如某目标通道被并掉后该目标召回占比掉多少）会让你改变这个判断？

2. β 在线可调、β=0 一键回退。你会不会担心运营手里多了一根「看不见的旋钮」——β 调大调小，效果怎么归因、谁负责？如果给你一个「每次 β 改动自动埋点、自动出 DCGR 归因口径 vs 系统全口径两份数」的机制，会不会改变你对「要不要把 β 开放给运营」的判断？

3. 软偏移靠 KL 项兜着、不会塌成角点，硬强制会。你判断美团现在的多目标调控更接近哪一种——是已经在「软偏移」（目标权重可连续调），还是更接近「硬强制」（某目标直接钉死配额）？如果实测出把某条硬规则改成软偏移后，被牺牲的那个目标指标回弹、而主目标没掉，这会不会让你更愿意把硬规则都换成软偏移？

4. 甲/乙/丙三条落点里，你判断美团「召回改生成式」这件事，真正的卡点在哪——SID 检索索引的工程成本、生成式召回的 latency，还是「决策前缀」里美团业务目标（履约、供给、GMV）怎么映射成维度？什么证据会让你把「卡点」从一处改判到另一处？
