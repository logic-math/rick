# 第二课 · 一个 backbone 怎么同时是三个模型

## 承上：四个词，还没落地

上一课收口在一句话——改「怎么实现」，不改「要不要级联」，并给了共享/隔离的边界：共享 user context，隔离 stage-specific token（research_1 · A，#5，§4.1）。但那还只是四个名词。真正的问题是：在一个 backbone 的 token、权重、激活这几层里，「共享」和「隔离」各自精确落在哪一层，怎么从「合并」变成一张能画出来的数据流。

（上一课末的三个追问你还没回，我不打断节奏，只把它们留作线索：这一课的追问会顺着其中两条往下走——你粗精融合里共享的是算力还是表示、召回端最不能放弃的特征。）

## 作者手里的问题，比「合并」更窄

作者要合并三个模型，但他手里有一个不能动的约束（V1，你已裁决）：候选特征不能删。于是「合并成一个 backbone」不能理解成「把三套参数和特征倒进一个池子里搅匀」——那会踩回 V1 的坑。真正的约束是：既要把重复的东西合掉，又要把不重复的东西原样留住。

合掉的是什么？是同一段用户行为序列被召回、粗排、精排各编码一遍的重复（research_1 · A，#4 的第二类成本）。留住的是什么？是三个 stage 各自不同的候选特征与阶段目标（V1）。于是作者的原始问题被逼窄成一句话：**在同一个 backbone 内部，什么必须共享、什么必须隔离，共享与隔离分别落在哪一层。** 这正是你直觉 1 的原话「关键在于谁共享谁隔离」在实现层面的展开（judgment）。

## 他调研时站的两个知识领域

强相关的是因果 Transformer 序列建模——一个因果/自回归的 Transformer 如何把「一段序列 → 一组上下文表示 → 多种不同的读法」；以及生成式推荐里的语义 ID 路线（召回从「打分」变成「自回归生成」）。这两样给他一个关键能力：**一段序列只需要编码一次，之后不同的读法只需要不同的 token 和不同的 mask，而不需要重新编码。** 这与「三模型各编码一次」是同一物理动作的两面——前者把编码的次数从三次压成一次，代价是读法必须显式地管起来。

弱相关的是多目标治理的「决策空间区域 vs 独立通道」（V6）与稀疏 MoE 的容量解耦（§4.3）。这两个是「统一之后怎么继续 scaling」的发散方向，本课只点到，模块四、五接住。

## 作者的答案：四个机制，各管一层

他把「共享/隔离」拆到四个独立机制上，每个只回答一件事（research_1 · A，#5，§4.1）：

**机制一 · 共享 user context —— 消掉重复编码。** 用户行为序列每请求只编码一次，产出「共享 user context」，三个 stage 都读它。共享的是「编码后的表示（激活）」，不是把三阶段的模型参数也共享掉。四类成本里的「重复编码」，落点就在这里被消掉。

**机制二 · stage-specific token —— 隔离阶段专用性。** 每个阶段带自己专用的 token；候选相关特征不共享，各阶段保留自己的候选特征——论文管这叫「混合参数化」（承前作 OneTrans）（research_1 · A，#5，§4.1）。这是 V1「不移除候选特征」在 token 与特征层上的落点：候选特征不进共享池，各自留在各自的 stage。

**机制三 · visibility mask —— 挡住跨阶段互看。** stage visibility mask 隔离各阶段 token：每个 stage token 只能读到共享 context 和自己的 token，读不到别的 stage token（research_1 · A，#5，§4.1）。隔离由此从「模型与模型之间」降为「token 与 token 之间的可见性」——原来靠三套独立模型天然隔离，现在靠一张 mask 显式画出来。

**机制四（你直觉 1 点到的）· 局部权重。** 「混合参数化」的含义是：一部分权重共享、一部分权重按阶段局部化。共享的那部分让三个阶段在一个 backbone 里互相借力（一致性从哪来，模块三展开）；局部的那部分让每个 stage 还能学自己专属的东西——也就是你说的「通过模型中特定的局部权重实现对特定场景任务的学习」（judgment）。

到这里，「谁共享谁隔离」的答案是分层的：**表示层共享（user context）、token/特征层隔离（stage token + 候选特征不共享）、可见性层隔离（mask）、权重层半共享半局部（混合参数化）。** 不是笼统一句「合了」，而是每一层分别决定合不合。

## 一段能画出来的数据流

现在可以画了（每请求编码一次、三阶段各读各 token）：

```
用户行为序列
   │  每请求编码一次
   ▼
[backbone] ──► 共享 user context
                  │  │  │
        ┌─────────┘  │  └─────────┐
        ▼            ▼            ▼
    召回 task    粗排 task     精排 task
    读 context   读 context    读 context
    + recall    + prerank     + rank
      token       token         token
    + 自己的     + 自己的      + 自己的
    候选特征     候选特征      候选特征
        │            │            │
   生成语义 ID    打分(粗)     打分(精)
   （模块四展开）
```

三个箭头读的是同一份 context，但各自只拿自己的 token 和自己的候选特征；mask 保证 recall token 看不到 prerank/rank token，反之亦然。级联的漏斗逻辑——先粗筛、再细筛、最后精判——不再由三个独立模型承担，而由「哪个 stage 读哪些 token、用什么特征」承担（承接上一课）。

## 事实边界：这一课的材料撑到哪

能撑到的（research_1 · A，#5，§4.1）：共享 user context、stage token、visibility mask、混合参数化——这四样「存在且各管一事」是论文事实。

撑不到的（如实标注）：每个 stage 具体几个 token、token 摆在序列什么位置、visibility mask 的具体矩阵形态（哪行哪列置 0）、「混合参数化」具体到「哪几层共享、哪几层局部」的切分——这些 token/权重级细节**论文/材料未给**。上面机制四里「一部分共享、一部分局部」是「混合」二字的自然读法，也吻合你直觉 1 的表述，但论文没有把它展开成结构级细节，不能当作论文白纸黑字的结构事实去照着搭。

## 几条并立的落点（判断权在你）

「共享什么、隔离什么」，作者落在「表示共享 + token 隔离 + 权重半共享」。这不是唯一可落的位置。同一条原则可以落在不同层，几条并列摆出来，不替你收敛：

- **落点甲（作者的方案）**：共享表示（user context），隔离 token（stage token + mask）。重复编码的消除发生在「表示」层。
- **落点乙（你现有的方向）**：共享算力（精排复用粗排部分算力，judgment 直觉 3）。重复的消除发生在「算力」层，表示层未必共享。
- **落点丙（更保守的中间态）**：共享 backbone 权重，但各 stage 各自 head + 各自特征输入，靠训练而非 mask 隔离。

三者的差别不在「要不要合」，而在「合哪一层、隔哪一层」。你的粗精融合现在站在乙，OneTrans 站在甲；哪个更该先做，取决于你场景里重复编码的实测占比、以及阶段专用特征的不可替代程度——这是你自己的判断，下面追问把它逼出来。

## 追问（把你的判断逼出来，不是考你）

1. 你的粗精融合，共享的是「算力」还是「表示」——精排复用粗排算力时，用户序列是被编码了一次还是两次？如果实测出你们现在「重复编码」的算力占比还不到总推理的一定比例，你会重新考虑要不要把共享从算力层推进到表示层——那个比例是多少，什么实测数据会让它改变？

2. 候选特征「不共享」在你的粗精融合里对应什么——粗排和精排现在各自留着哪些对方没有的特征？如果要把召回也并进同一个 shared context，召回端今天最不能放弃的那一类特征是什么——什么证据（比如去掉它之后召回 HR 掉多少）会让你改判「它可以共享」？

3. mask 挡住的是「跨 stage 的 token 互看」，但 shared context 三个阶段都看得到。隔离和共享之间会不会漏一条缝：某个 stage 的专用信息顺着 shared context 反向污染另一个 stage 的读法？你判断这条缝在因果 Transformer 里天然不存在，还是需要额外机制补——什么现象（比如某 stage 指标被另一个 stage 的训练带动）会让你改变判断？
