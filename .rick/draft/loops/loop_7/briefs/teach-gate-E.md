### ②.1 dsh 插件故障的实测数据教学：从「推测」到「下限统计」

**严重度分级的结构**。research-extra-4 在 13 天观察窗（2026-08-13 开源~08-26 基准日）内 web 检索到 ≥35 条插件故障讨论，分三级：**无法启动 21 条**（#535/#1404/#2710 等，典型报错 `plugin tree failed to load`）——插件错误完全阻断宿主启动，用户拿不到任何功能；**部分功能损失 11 条**（#1486/#1515 工具调用全崩、#2851 Windows PTY 损坏）——宿主活着，故障插件关联的能力面丢失；**数据损坏 3 条**（#802/#1538 会话日志不可再加载、#2034 会话永久不可恢复）——最重一级，故障留下不可逆的用户损失。这三级恰是「系统性崩溃」一词的展开：从「功能全失」到「数据全失」，同一条因果链（插件错误→宿主级后果）的不同深度。[research-extra-4 ①，编号清单在案；信源=GitHub Discussions web 检索，计数为下限]

**与机制的对应**。前轮（research-extra-3）已在源码级证实：dsh boot 把整棵插件树作为**一个事务**加载，任一插件失败=全树失败，无单插件故障隔离（唯一合法的 fiber-less 态=显式 entry.disabled；boot 无 skip/降级路径）。35 条案例与机制逐级对得上：无法启动=事务失败的直接表现；部分损失=插件运行期（非加载期）错误；数据损坏=插件写入的文件把宿主状态一并污染（含「卸载入口与坏插件同殁」模式 #4175——想自救卸载，宿主都起不来）。机制与实测互为印证，「插件错误→系统性崩溃」不再是 human 问句中的推测，也不再是 teach-E 时代的 R7 未消解项 2。[research-extra-4 ④-1/④-2；本地 postmortem 4 份均为内部开发期缺陷、0 份第三方插件案例——第一方与第三方故障是两个不重叠的证据池]

**官方响应模式的对照**。dsh：维护者逐帖回应缺失（#1415 标 Unanswered、#535 至今 13 天零回应、响应时距 0 样本）；修复靠发版+社区自救（rc.7 修 pty.node 加载失败；社区工具 dsh-doctor 两版/dsh-loader 兼容层/锁版本/手改 cordis.patch.yml）；changelog 唯一标注的 breaking=SQLite 格式（非插件），实际插件级 breaking ≥2 条未标注（键控插槽致 dsh-codex-connect 崩、node-pty 升级致 #2851）。pi 对照：扩展崩溃级 10-12 条（#2431/#3578/#3595/#4909/#7187/#7731 等）**多数获官方当日~数日修复**（PR#3597/#6343/#4426），加载失败类多为跳过/降级（pi 存活），另有 `pi -ne` 无扩展逃生口；关键例外 #3556（emitToolCall 为 runner 唯一未包 try/catch 的 emit，扩展 tool_call handler 抛错即崩 agent 循环，官方标 not_planned，第三方 07 月证据称仍抛错）——此例外在当前 0.84.x 是否仍存在未复核（R7，与本地源码「emit 有 try/catch」存在张力）。事实陈述：两家差异不在「有没有崩溃案例」（都有），而在**兜底与响应**——pi 有降级路径+快速修复+逃生口，dsh 无降级机制+逐帖响应缺失。[research-extra-4 ①②，leaf-1/leaf-4]

**PoC 未合入的含义**。#4175（08-23，franksong2702）隔离修复 PoC 已落地为 **fork 分支** recoverable-bundle-failures-poc（commit c601d5a861，29 文件，+802/−102）：新增 recoverableBundles 子集+每 bundle 层独立事务（必需层仍 fail-loud），附设计文档，文末 3 问待维护者答——**无官方回应、未转 PR、未合入**。同类提案 #1228（坏 bundle 拖垮整 profile，零回复）、#2920（影子 profile+--recover-optional-plugins）、#1496（倾向安装期防护）均未合并；官方 rc.8→0.1.1-rc.2 无隔离改动；排障页明言 no skip-and-warn。含义分两层：①**今天**的 dsh 上游无隔离机制（29 文件的改动量本身反证这不是小修）；②是否会有，取决于维护者对 3 个未答问题的回应——开放变量，非已关闭事实。[research-extra-4 ③，leaf-3]

**「下限≠发生率」：分母问题**。35 条 ÷ 13 天 ≈ 1.6 条/天——这是**频率下限**（web 检索非穷尽、沉默用户不上 Discussions），不是发生率。发生率=故障用户/全部用户，而 dsh 装机量无公开数据（R7）——分母缺失，率不可算。统计学常识：案例枚举法只能给下限，给不了率；要率必须有分母。易被忽略的对照事实：VS Code（2019 年 800+ 崩溃报告 #79782、官方确认单扩展可拖垮共享扩展宿主 #100413）靠独立进程+自动重启兜底而主编辑器存活；Koishi（cordis 同源）有降级机制但 dispose 抛错仍可崩（#1254）；Eclipse/OSGi 个案跨 20 年无聚合率——**所有对照系统均无公开插件故障率百分比**，数据缺口是行业普遍现状。dsh 的独特性不在缺口本身，而在两点叠加：观察窗极短（13 天即攒出 35 条）+无兜底机制（同构故障在 VS Code 有进程隔离兜底）。另修正前轮一处表述：dshdocs.com 自述「独立社区维护手册」，非官方站——前轮引作官方 changelog 处需打折。[research-extra-4 ④-4/④-5，leaf-2]

### ②.2 pi 扩展的 server 能力与生命周期

**扩展是什么**。pi 扩展=普通 TypeScript 模块，经 jiti 加载进 pi 主进程，**无沙箱、与 pi 同权限**（docs/security.md 原文）——node:http 可用 ⇒ 技术上可起 server、监听端口、接受外部连接。这不是推测：代码+文档已核，且有第三方实证——Firstp1ck/pi-coding-agent-forge 以扩展形态实现 web ui（remote-webui：/remote 开 LAN+PIN 认证+QR 手机接入）。[research-extra-5 ①②；信源=本地源码/官方文档原文，高置信]

**生命周期：会话级 vs 进程级**。扩展生命周期绑在**会话**上，不在进程上：工厂函数禁止启动后台资源（sockets/processes/timers），须 defer 到 session_start；session_shutdown 须幂等清理；/new /resume /fork /clone 及进程退出**均触发 session_shutdown**（extensions.md L222-224+生命周期图）。推论：扩展内起的 server 只活在「宿主进程+当前会话」——会话切换即灭。这不是能力缺陷，是 pi 的生命周期契约：扩展被定义为**会话级参与者**。[research-extra-5 ①]

**长驻需求的三条官方路径**。若 web ui 需要**进程级长驻**（浏览器断开会话存活、多会话并行监督），官方路径不是扩展：①**扩展内 server**（Firstp1ck 形态）——会话级，适合「当前会话的可视化与操控」；②**SDK `createAgentSession`**——独立 Node 进程内嵌 agent，文档明示 web UI 用例；第三方 xiaoyc/pi-web-ui 即此架构（pi SDK in-process+WebSocket 推流；功能含流式聊天/工具调用/内置 terminal/模型与 prompt 管理/skills+extensions 开关）；③**RPC 模式** `pi --mode rpc`——JSON over stdio；hyperdreamer/pi-webui 以进程级长驻实现「断开存活+多会话并行监督」。官方第一方另有 @earendil-works/pi-web-ui（npm 已发版）=复用型聊天组件库（mini-lit+Tailwind，基于 pi-ai+agent-core）。官方立场「自扩展无需 fork」+三架构均有第三方实现 ⇒ **fork 非必要**；但第三方成熟度/维护活跃度未核、工时成本无公开数据（R7）。[research-extra-5 ②；think-E-r2 消解 1]

**架构选择树**（按需求分流，非推荐）：需求=「当前会话的可视化/操控」→ 扩展形态够用；需求含「断开存活/多会话并行监督」→ SDK 或 RPC 架构；两路都无需 fork——架构选择是**模块层决策**，不是设计规则层决策（fork=层 B 事件），二者层级不同，勿混淆。

### ②.3 语义巡检自动化的工业现状

**结构级与语义级的鸿沟**。工业界的 spec 一致性检查**全部是结构/语法级**：Pact 的 matching rules（regex/类型匹配）、oasdiff 的 514 条 OpenAPI 变更规则——它们能判「字段类型变了没」「必填项增删了没」，判不了「这段行为的**含义**一致不一致」。语义级契约检查只存在于学术提案（IJISAE AI-Assisted API Contract Validation），无工业落地。即「判两份文本语义一致」这件事，工业界至今**没有日常化的自动化先例**。[research-extra-5 ③；信源=检索，中置信]

**LLM-as-judge 的可靠性数据**。若用 LLM 做语义判定，其可靠性边界已被量化（均出自 2026 年评测文献，检索摘要级引用、未逐篇核原文——R7）：①重复同一评估，成对偏好平均 **13.6% 翻转**（GPT-4o-mini/4.1-mini，29 任务；arXiv:2606.13685）——同一判官、同一输入，第二次答案变了的频率；②exact-match agreement 会**系统性高估**判别力（21 judges/118 runs；arXiv:2606.19544）；③SummEval 上 33-67% 文档存在偏好 **3-cycle**（A>B>C>A，传递性不一致），被低聚合违规率 0.8-4.1% 掩盖（arXiv:2604.15302）——聚合数字好看不代表个体判断可靠；④54 个 LLM 复现 human 评分用 Cohen's κ 衡量（arXiv:2510.09738），前轮已知 human-LLM κ≈0.46-0.60——κ 粗读法：0.4-0.6=中等一致。可靠化手段（N-of-M 投票、确定性参数）出自**评测文献**，非生产实践。事实性结论：dream 巡检若要自动判「一致」，判据**无先例可抄**——只能自造+自验。[research-extra-5 ③；think-E-r2 消解 2]

### ②.4 契约/制度视角——门禁认定的事实性视角生成

**它是从哪来的**。human 回答 5 原话：「我们应该在 domain 中维护 rick 所有与 pi 的语义对齐的改动点，维护一份协议清单，并且通过 dream 不断巡检以达成最终一致。」门禁（think-gate-E-r1/r2）的**评估**是：这段话事实上生成了一个新视角——**契约/制度视角**——恰好落在 teach-E 问 1 指出的覆盖矩阵空白格（9+3 透镜无一来自法学/制度社会学）。注意标注：这是 think 的认定，视角是否成立=你的确认（见③问题 4）。[think-gate-E-r1「阶段特定产出」；judgment.md 回答 5 原话]

**契约理论的最小骨架**（第一性原理，通识级法学内容）。一份契约把「我指望你」变成「你义务」：①**履约义务**——写明对方承诺什么（pi 的承诺=12 钩子等公开 API 的行为契约）；②**巡检/监测义务**——重要契约不止于签，还要求持续核查对方是否仍按条款行事（协议清单=把口头指望写成条款；dream 巡检=履约监测）；③**违约处置**——对方不履约时我方的行动选项（重谈/补救/解约），解约成本=另觅缔约方的成本。映射：pi 升级=缔约方单方改约（新版 API 变更）；rick 的语义对齐风险=pi 的条款漂移；层 B=解约与重新缔约事件。门禁认定的独立视角立场另有两处隐含来源：回答 2 的上下文主义（行为主义谱系）、回答 3 的行为模式循环论（P2/P7 行为层）。[映射为启发非断言]

**它照亮了什么（新预测）**。契约视角给出一个与现有透镜**不同的可检验预测**：**迁移成本由巡检一致性控制，而非由文档化程度控制**。对照 P3 的预测（迁移成本随未文档化的隐式行为积累而增长——控制手段是文档化）：契约视角说，写了文档但巡检验证不了语义等价，迁移时照样卡壳——因为迁移的瓶颈不是「知不知道」，而是「验不验得出来」。两视角的分歧点可测：若 dream 巡检覆盖度高（一致性可验证）的部分迁移顺利、文档化了但巡检不到的部分迁移照样难，则契约视角的预测胜出；反之 P3 胜出。这是把「协议清单+dream 巡检」从工程机制上升为观察透镜后新得到的预测——也是门禁认定它构成「事实上的视角生成」的理由。判别实验是否立项由你决定。[think-gate-E-r1/r2 转述；非本简报立场]

## ③ 启发式追问

> 追问建立在②之上；每问附「改变判断的证据」。这些问题要求你做判断，不设确认性答案。

**问题 1：loop 重定义是否架空层 B 触发器**。你说「loop 本质是让 ai 行为呈现循环的模式，通过系统提示词实现」——但这假设了「一切改 loop 需求都可由提示词满足、层 B（12 钩子外骨架替换）触发器永不点亮」。②.2 补了一刀新证据：扩展同样改不动系统级结构——只有会话生命周期钩子、无调度控制面，dream 触发时机/job 调度节奏只能由 pi 内核或 fork 改动。即**提示词与扩展两层都触不到调度级 loop**，这类需求必然以 Y1 形态现身（S 终裁语境的「改 loop 需 fork 源码」指的正是这个对象）。两种解读请择一：**兼容解读**——层 B 与 Y1 实为同一触发器的两种表述（系统级 loop 需求归入 Y1「pi 扩展无法满足的功能需求」），层 B 永不单独点亮是设计意图；**架空解读**——按新定义运行后，调度级需求以 Y1 形态**迟到**现身，届时已积累专用性负债（P3/P5 的警告），层 B 定义需现在重写。
改变判断的证据：你确认两词分指且层 B 判据仍指系统级骨架（兼容成立）；或出现提示词+扩展均无法承载的调度级需求（架空已成事实）。

**问题 2：给定「无先例+13.6% 翻转」，「一致」判据与 X6 如何定**。你悬置了语义等价（回答 4「随选择 pi 悬置了」），却上马了依赖语义等价判定的巡检机制（回答 5）——**悬置与依赖直接矛盾**。②.3 已把事实底座钉死：判据无先例可抄、单次判定不可靠。三路请择一：①**自造判据+走 X6**——定义可操作判据（如 N-of-M 投票一致率阈值+spec 单测穷举），且协议清单机制按你已拍板的 X6 规则（「新机制发布前需要实验」）先实验再上马；②**降级 human 终审**——巡检只产出 diff 报告，「一致」由你裁决（回到 teach-E 问 7 的语义）；③**显式接受误判风险**——不设判据，风险记录在案。
改变判断的证据：出现工业级语义一致性巡检先例（推翻②.3 消解）；或你对三路之一显式拍板。

**问题 3：上下文主义的失败模式协议**。你说「一切效果都可通过改变上下文达成=rick 的能力边界，不一定正确但符合目标」——这是显式的信仰声明，却被用作关闭 P2 警报的理由。②.2 又添一证：扩展的代码级效果（起 server/网络监听）就在 12 钩子能力面内——你自己的「语义对齐改动点清单」已承认非上下文依赖面存在。那么「一切」的边界在哪？边界声明需要**失败协议**：当某效果上下文达成不了时，它归入扩展面代码、触发 Y1、还是视为 rick 能力边界外的信号？Ashby 教训：无监测的边界等于无边界——你拒绝了平稳性担忧却未设任何漂移监测。
