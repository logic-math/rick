# think-gate-S 简报

> 阶段:loop_7 S 问题确认(批判门禁)| 主题:pi vs dsh 双 runtime 判断 | 输入:human Q1-Q4 原话 + teach-S 事实基线

## 需 human 回答的问题(top-5)

### Q1 穷举单测:可验证性的数学边界
**问题**:若「所有 spec 都可通过对 runtime 的单测器穷举描述」成立,那么也假设了「spec 的行为空间有限、可被有限测试集完全覆盖」——这真的正确吗?「穷举」只对有限输入空间成立;语义等价不可判定,单测是抽样,「全过」≠「等价」;可穷举的 spec 即成实现描述,与「runtime 无关」自相矛盾——或需降级为高阶定性契约(行为不变式)。
**依据**:切换成本三层结构已量化(templates 方言 128 处/19 文件),但「spec 可验证切换」侧零实验验证;human 自认「语义等价性还不确定」。
**改变判断的证据**:小规模 spec→等价重实现实验成功;或对穷举边界给出形式化论证。
**性质**:判断性(数学论证,human 定夺)。

### Q2 双 runtime「保持等价」的检验机制缺失
**问题**:若「CLI 用 pi、web UI 用 dsh,两 runtime 等价且未来保持等价」成立,那么也假设了「存在可操作的等价性定义与检验机制,且每功能 ×2 实现的成本可被吸收」——这真的正确吗?在等价性无检验机制时(见 Q1),「保持等价」是不可证伪的承诺;每新功能需两套方言实现并保持行为一致,与 Q1「成本最低」直接冲突——除非 spec 可验证层成立,双 runtime 才退化为 spec 的两个具体实现(反而简化)。
**依据**:research 修订方向为「templates 分版本」或「dsh 侧适配层」,成本归属不同;workflowScript→dsh ctx.subagents 等价性未实测(R7-5 未做)。
**改变判断的证据**:R7-5 spike 实测 workflowScript 在 dsh 侧等价可用;或 human 定义等价性检验机制。
**性质**:判断性(必须 human 回答:等价由谁检验、成本归谁)。

### Q3 可量化指标与人机双循环的兼容
**问题**:若「以 human 为核心的人机双循环螺旋进步需要可量化度量」成立,那么也假设了「存在与该质性进步同向的量化 proxy」——这真的正确吗?现成 5 类数据源(artifacts meta、run-history、父会话 JSONL、raw log、tasks.json)全是 agent 侧指标(触发率/延迟/成功率/成本),无一度量「human 投入与反馈」;只测 agent 侧则「以人为核心」落空;加入 human 侧指标(干预频率、返工率、耗时)则 proxy 语义须 human 定义。
**依据**:teach 2.5:基线可离线算出但未运行;「预期派发数」无机器可读定义是度量落地唯一前置。
**改变判断的证据**:human 给出候选 proxy 及语义定义;或度量运行后发现 agent 侧指标与主观感受背离。
**性质**:判断性(proxy 语义必须 human 定义;可 research 辅助设计)。

### Q4 benchmark 的归因设计:测的是 rick 还是 model
**问题**:若「用代表性 benchmark 验证 rick 工程能力足够强」成立,那么也假设了「benchmark 得分可分离 rick 方法/编排的贡献与底层 model/runtime 的贡献」——这真的正确吗?benchmark 分数 = harness×model×配置 的组合(教训:TB2.1 官方 82.70% vs 社区 0.51);同一 rick 换 model 分数即变,无法归因到 rick 本身,除非设计对照(同 model、同任务集、变 rick 方法)。
**依据**:teach 2.6 误区二(分数属组合非 harness 单独);dsh vs pi 直接受控对比不存在。
**改变判断的证据**:出现同 model 同任务集「有 rick 方法 vs 无」对照数据;或 human 明确 benchmark 用途是「agent 能力基线」而非「rick 方法验证」。
**性质**:事实性(具体 benchmark 选型建议 research 澄清)+判断性(归因目的需 human 定)。

### Q5 双 runtime 成本核算与决策时序
**问题**:若「pi/dsh 同时支持可将功能迭代成本降到最低」成立,那么也假设了「双方言维护的复利成本 ≤ 单 runtime 的损失,且 dsh 性能优势可在选择前被度量」——这真的正确吗?模板方言成本复利,双 runtime = 两套方言 + 双产物读回格式 + 双行为假设;而 dsh 的性能理由「灵活性」无度量支撑(dsh vs pi 受控对比不存在、基线未运行)——「先支持后度量」还是「先度量后支持」?
**依据**:research 量化 128 处 pi 触发语法、19/30 文件受染;human 自认性能评估「稀疏且模糊」。
**改变判断的证据**:R7-4 度量脚本运行后定位瓶颈确在 runtime 层;或双方言维护工作量被实际核算。
**性质**:判断性(需 human 权衡时序与成本归属)。

## 门禁观察(阶段特定产出)
- human Q4「都要」实质推翻 loop_6「单一 runtime=pi」——是决策变更非复核,建议 judgment 记录变更理由与撤销条件。
- Q1/Q3/Q4 构成三角张力:Q3 的 spec 可验证性是唯一把 Q4 从「两倍成本」变「两个实现」的支点,却恰是三者中唯一无实验验证的环节——建议该实验列为 gate 通过前置或明确挂起项。
