### top-N 假设的 3 启发性问题

#### 假设 #1:如果 pi 真有良好扩展性,那么 rick 能深度控制模型行为
- **Q1 信念**:关于"rick 能深度控制模型行为",你内心最确信的是 pi 能开放哪些具体控制点(如 prompt 注入/tool 路由/上下文裁剪)?最不确定的是这些控制点是否真比 claude code 现有 `--system-prompt`/`--append-system-prompt`/MCP 多?
- **Q2 前提**:"深度控制"成立需要什么前提?你是否已确认 pi 暴露的扩展接口粒度细于 claude code 的 NDJSON+flag 协议?这些前提你亲验过还是基于官网宣称?
- **Q3 反例**:什么证据会让你改变判断?——若 research 发现 pi 的扩展点仅是 prompt 模板钩子(粒度等同于 claude code `--append-system-prompt`),你还会认为"深度控制"成立吗?

#### 假设 #2:如果深度控制模型行为,那么能获得更好效果
- **Q1 信念**:关于"更好效果",你内心最确信的是哪个维度的"更好"(任务完成率/Token 效率/可调试性/对 rick 三阶段流程的契合度)?最不确定的是"更好"是否可量化?
- **Q2 前提**:"深度控制 → 更好效果"成立需要什么前提?你是否假设了"当前 claude code 的效果瓶颈源于控制不足"而非"prompt 设计/任务分解不足"?这个根因判断你确认过吗?
- **Q3 反例**:什么证据会让你改变判断?——若 research 发现当前 doing 阶段效果瓶颈在 `doing.md` 模板设计而非 agent 引擎,你还会坚持替换引擎能带来更好效果吗?

#### 假设 #3:如果官网/github 称 pi 轻量可扩展,那么实际接入 rick 后也轻量可扩展
- **Q1 信念**:关于"接入 rick 后轻量可扩展",你内心最确信的是什么?最不确定的是 pi 是否依赖特定运行时(Node/Python/Rust)而 rick 是 Go 单二进制?
- **Q2 前提**:接入轻量成立需要什么前提?你是否确认过 pi 提供 Go binding / CLI 子进程模式 / HTTP API?这三条中任意一条不满足,"轻量"是否就破产?
- **Q3 反例**:什么证据会让你改变判断?——若 research 发现 pi 需嵌入 Node runtime 且与 rick 的 `exec.Command` 调用模式有进程管理开销(对比 claude code 单二进制),你还会认为"轻量"成立吗?

#### 假设 #6:如果 pi 扩展机制能与 rick AgentExecutor 接口语义对齐,那么 12 处直接 exec.Command 可被泛化重构
- **Q1 信念**:关于"12 处 exec.Command 可泛化重构",你内心最确信的是接口层抽象可行?最不确定的是 12 处中 plan/easy/dream/learning/human_loop 各自的 flag 差异(--session-id/--resume/--dangerously-skip-permissions)能否被统一抽象?
- **Q2 前提**:泛化重构成立需要什么前提?你是否假设了 pi 能模拟 claude code 的会话续接(--resume/--session-id)和流式输出(NDJSON stream-json)?这两个前提你确认过吗?
- **Q3 反例**:什么证据会让你改变判断?——若 research 发现 pi 不支持会话续接或流式输出协议与 rick 现有 `runner.go` 的 NDJSON 解析强耦合,你还会认为 12 处可被泛化重构吗?

- **#5(最终分 0.20,不可逆 1.0)**:"后续不再支持其他 agent"是单方决策推广为长期策略,若 pi 框架停滞/闭源/破坏性升级,rick 将无 fallback。human 未亲验 pi 的维护活跃度(commit 频率/release 节奏/社区规模)。
