## 正方3：工程能力/运行时成熟度视角

> 立场：在「作为实现 rick 方法（SENSE 五阶段 + think/research/exporter 三 subagent 角色）的运行时载体」上，pi 的工程能力与运行时成熟度**显著高于** deepseek-harness。核心理由：pi 已稳定、机制简单显式、且 rick 已在 pi 上完成迁移；deepseek-harness 仍处 developer preview、无兼容性承诺、subagent 机制碎片化且软性约束。

### 论点（正方立场，含证据出处）

**论点 1：pi 的 subagent 触发机制「唯一且显式」，工程可控性高。**
- pi 触发 subagent 的唯一公开执行面是 `subagent({workflowScript:"..."})`，脚本内用 `runs.run(key,{agent,task})` / `runs.all([...])`（BP-1）。单一入口 = 单一故障面，工程上可精确控制「谁在何时触发谁」。
- 证据：`research-report-S-bestpractice.md` BP-1；pi-subagents `SKILL.md`「Use workflowScript for all execution」。
- 对比：deepseek-harness 的 subagent 是「多个 provider 实现并存、按名注册」的 seam（`ctx.subagents`），一次触发要先选 provider（spawn/fork/acp/claude-code/codex/dsh-sdk）再传 `SubagentStartRequest`——碎片化，工程心智负担更高。证据：`deepseek-harness/docs/subsystems/subagent.md`「multiple provider implementations coexist in one context, registered by name」。

**论点 2：pi 的自定义 agent = frontmatter markdown，声明式、低复杂度，可把 rick 的 think/research/exporter 直接注册为系统级 agent。**
- 一个 agent = 一个 markdown 文件（YAML frontmatter：name/description/tools/model 等 + system prompt），注册作用域 builtin/package/user/project 分级，触发 `runs.run(agent:'think')`（B1/B2/B3）。
- 证据：`research-report-S-reasons-agent.md` B1~B4；`research-report-S-bestpractice.md` BP-2。
- 这意味着「把 rick 方法翻译进 pi 实现体系」（human 已定的逆转逻辑）在 pi 上是**直接可落地的声明式操作**，而非要重写运行时。

**论点 3：pi 已具备成熟的多 agent 编排原语，且 rick 已完成迁移（工程地基已存在）。**
- pi 提供单写者（BP-6）、async 默认（BP-4）、context fresh/fork（BP-5）、编排权在 parent（BP-8）、可复用编排 recipe（BP-7）等已被 rick 侧调研确认的原语。
- rick 已把 runtime 从 claude code 1:1 迁移到 pi（loop_4 RFC；job_30 commit：piagent Executor + pi --mode json JSONL 解析 + 13 个调用点，含 3 项 e2e 测试通过）。**迁移成本已支付**，换到 deepseek-harness 意味着再次推倒重来。
- 证据：`judgment.md`（S/E/N 收敛）+ loop_4 RFC（`rfc/rfc-rick-pi-迁移的价值基础与架构定位-2026-08-10.md`）。

### 对对方（deepseek-harness）的反驳点（缺点，含证据出处）

**反驳 1：deepseek-harness 处于 developer preview，明确「将有不兼容破坏性变更」，工程成熟度不足。**
- README.md：「DeepSeek Harness is currently in _developer preview_ and is iterating rapidly. **THERE WILL BE COMPATIBILITY-BREAKING CHANGES.**」
- package.json 版本 `0.1.0-rc.5`（pre-release，未达首个 tagged release）；AGENTS.md 自述「Remove this section at the first tagged release」。
- 对 rick 这种需要长期稳定承载方法论的载体而言，「破坏性变更」是直接风险。

**反驳 2：无磁盘格式兼容性承诺，会话/数据库格式随时被后端拒绝。**
- AGENTS.md：「Backends reject old on-disk formats. SQLite uses monotonic SCHEMA_VERSION; dsh-session keeps SESSION_FORMAT_VERSION at 0 with no compatibility promise.」
- 意味着 rick 沉淀的会话/doing/learning 产物若落在其存储层，跨版本无迁移保障。

**反驳 3：运行时要求激进（Node ^22.19 || >=24），部署门槛高。**
- package.json `engines`: `"node": "^22.19.0 || >=24.0.0"`；pnpm 11.7、TypeScript 6.0.3 等全套前沿栈，对 rick（Go 实现的轻量 CLI + pi 托管）引入沉重运行时依赖。

**反驳 4：deepseek-harness 的 subagent 触发同样「软性、guidance 而非 enforcement」——并未解决 rick 当前要解决的触发确定性问题。**
- `packages/subagent/tool-subagent-report/README.md`：「The instruction is guidance, not enforcement: the mechanism still accepts zero or many calls in one turn, and no runtime path rejects a child that never reports.」
- 即其子 agent 的「回报」通道仍靠模型自觉，这与 rick 在 pi 上遇到的「软触发词不可靠」是同一类问题；换 runtime 并不自动换来确定性。

**反驳 5：subagent 机制碎片化 + 已披露的投递缺陷。**
- 同一 subagent 能力有 spawn-in-process / fork-in-process / acp / claude-code / codex / dsh-sdk 多个 provider 并存（`docs/subsystems/subagent.md`），选择与心智负担高。
- 已披露限制：「Acceptance is weaker than durable delivery — there is no durable mailbox, idempotency key, delivery receipt, retry protocol, or exactly-once claim.」（tool-subagent-report README「Known Limitations and Deferred Work」）。

**反驳 6：LLM 能力绑定 DeepSeek 提供方，与 rick「运行在 pi 上可用任意模型（deepseek/claude/gemini/gpt）」的需求不一致。**
- AGENTS.md 布局：「llm/ LLM capability: Service Definition/Consumer + DeepSeek providers」——内置提供方为 DeepSeek，模型选择面窄，存在厂商锁定风险。

### 结论（一句话）

pi 以「单一显式触发入口 + 声明式 frontmatter agent + 已完成的迁移地基」在工程能力与运行时成熟度上完胜仍处 preview、无兼容承诺、subagent 机制碎片且软性约束的 deepseek-harness，是承载 rick 方法的更稳选择。
