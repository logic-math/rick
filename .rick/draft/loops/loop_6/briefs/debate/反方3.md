## 反方3：deepseek 原生契合/性能视角

立场：在「用 DeepSeek 模型实现 rick 方法」这一具体场景下，deepseek-harness 对 DeepSeek 模型的原生契合与推理性能适配，优于 pi 的通用 provider 兼容层。

---

### 论点（反方立场，含证据出处）

**1. first-party 血统：deepseek-harness 是 DeepSeek AI 自己开发的 harness**
- 证据：`README.md` 首句「DeepSeek Harness (`dsh`) is an open-source agent harness **developed by DeepSeek AI**」。
- 含义：模型厂商自研的 harness，天然以自家模型的 wire protocol 为「真源」，模型迭代时最先跟进。这是 pi（通用 harness）无法从机制上提供的契合度。

**2. 专用 DeepSeek 适配器 `llm-deepseek` 以官方 API 文档为真源（source of truth）**
- 证据：`packages/llm/llm-deepseek/README.md`「direct `fetch` + SSE … translating the official wire format (source of truth: the API docs — guides/thinking_mode, guides/tool_calls, api/create-chat-completion) into the `StreamChunk` protocol」。
- 证据：同文件「This package owns the `deepseek-official` provider route — deliberately distinct from pi-ai's catalog name `deepseek`」。
- 含义：deepseek-harness 专门维护一条 `deepseek-official` 路由，把 DeepSeek 的 thinking_mode / tool_calls 作为一等公民直接实现，而非通过通用 provider 层间接适配。

**3. DeepSeek 思考（reasoning）的精细化适配**
- 证据：`packages/llm/llm-deepseek/README.md`（README.zh.md 第 44–46 行）——`reasoningEffort: off | high | max`，`high`/`max` 序列化为官方顶层 `reasoning_effort`，`off` 序列化为 `thinking.type: disabled` 并省略 `reasoning_effort`；`thinking: disabled` 是部署级锁定，不支持值在网络 I/O 前即失败。
- 含义：对 DeepSeek 思考模式的 off/high/max 三档做了一对一的 wire 映射，而非通用「reasoning 开关」。

**4. token 节省与缓存复用优化（性能维度）**
- 证据：`README.zh.md` 第 72 行「推理回传规则：对携带工具调用的 assistant 轮次，会将 `reasoning_content` 序列化回历史（思考模式 API 必需）；对不含工具调用的轮次，它会被丢弃（不会使用，可节省 token）」。
- 证据：`README.zh.md` 第 93 行「未更改的已组装前缀可使用 DeepSeek cache 复用，适配器会在 usage 中报告它」。
- 含义：这是针对 DeepSeek 思考模型「哪些推理内容必须回传、哪些可丢弃省 token、哪些前缀可命中 cache」的细粒度性能优化。

---

### 对对方（pi）的反驳点（缺点，含证据出处）

**1. pi 对 DeepSeek 是「通用 provider 兼容层」，而非 first-party 原生适配**
- 证据：`pi-ai/dist/providers/deepseek.models.js` 第 1–2 行「This file is **auto-generated** by scripts/generate-models.ts. **Do not edit manually**」——pi 的 DeepSeek 模型目录是自动生成的一份元数据。
- 证据：`pi-ai/dist/providers/data/deepseek.json` 中 `"api":"openai-completions"`——pi 是通过 OpenAI-completions 兼容 API 承载 DeepSeek，而非直接实现 DeepSeek 官方 thinking_mode/tool_calls 协议。
- 反驳：pi 把 DeepSeek 当作「众多 provider 之一」用兼容层承载，深度适配（思考回传的 token 节省、cache 复用报告）依赖 pi-ai 通用模型层，而非 first-party 协议实现。

**2. pi 的 subagent 编排机制与 DeepSeek 模型 tool-calling 无 first-party 协同优化**
- 证据：pi 的 subagent 触发是通用机制（`workflowScript` + `runs.run`，见 rick 侧 `research-report-S-bestpractice.md` BP-1），它面向「任意模型」设计，不针对 DeepSeek 模型的 tool-call 遵循度做专门调优。
- 反驳：deepseek-harness 的 subagent seam 提供多 provider 后端（`docs/subsystems/subagent.md`：`dsh-subagent-spawn-in-process / -fork / -acp / -codex / -claude-code / -dsh-sdk`）并带 `outputSchema/depthLimit/toolFilter/persona` 能力，对 DeepSeek 原生会话有更细的控制面；pi 在此维度是「通用编排」而非「DeepSeek 原生协同」。

**3. rick 现状恰是「用通用层跑 DeepSeek」的实例**
- 证据：rick 运行产物 `rick/.pi/subagents/artifacts/*_worker_0_transcript.jsonl` 中 `"provider":"deepseek","model":"deepseek-v4-pro"`——rick 通过 pi 的通用 provider 跑 DeepSeek V4 Pro。
- 反驳：这正说明 pi 路径上 DeepSeek 只是「一个 provider」，其推理/思考/缓存的深度优化（如第 3、4 点的 reasoning 回传省 token、cache 复用）不归 rick 控制，而 deepseek-harness 把这些作为 first-party 核心能力内置。

---

### 结论（一句话）

deepseek-harness 作为 DeepSeek AI 的一等公民 harness，对 DeepSeek 思考/工具调用/缓存的 first-party 原生适配（专用 `deepseek-official` 路由 + reasoning 回传省 token + cache 复用）优于 pi 的通用 provider 兼容层，在「用 DeepSeek 模型实现 rick 方法」的性能与契合维度占优。
