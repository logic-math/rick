# 反方1：轻量/简洁/可控视角

> 立场：对「实现 rick 方法」而言，deepseek-harness 比 pi 更轻量、简洁、可控；pi 存在复杂度/黑箱/过度封装问题。

## 论点（反方立场，含证据出处）

### 论点 1.1：deepseek-harness「一切皆插件、无特权核心」，agent-loop 本身可替换
- **证据**：`deepseek-harness/docs/architecture.md`「Cordis」节原文——"Every part of the product is a plugin, including the model adapter, the tool registry, the session log, and the agent loop itself, so every part is replaceable from configuration." 以及 "There is no privileged core to patch: you extend dsh by mounting a plugin beside the others"。
- **含义**：rick 的方法层（SENSE 五阶段 + think/research/exporter 角色）在 dsh 里可被写成**一个插件/能力 seam**，随配置挂载、卸载，**不依赖任何黑箱核心**。对比 pi：核心 agent-loop 是运行时私有实现，rick 只能通过 `pi-subagents` 扩展（npm 包）间接接入，无法替换 loop。

### 论点 1.2：subagent 是「类型化服务 API」，不是模型手写脚本
- **证据**：`deepseek-harness/packages/subagent/subagent/README.md`「Service API」节——`ctx.subagents.start(name, request)`、`startContinuable(spec)`、`followup(...)`、`reportFrom(...)`、`interrupt(...)`、`listChildren(...)` 等均为**强类型服务方法**；model-facing 委托由 `dsh-tool-subagent` 通过 tool schema 暴露（`packages/subagent/README.md` 表格「tool-subagent/ — Exposes delegation to the model — registers on ctx.tools」）。
- **含义**：模型触发子 agent 是调用一个**有 schema 的工具**，参数受静态校验；而 pi 触发子 agent 需模型在工具调用里**手写 JS 字符串**（见下方反驳 2.1）。前者是「可控的契约」，后者是「黑箱里的字符串」。

### 论点 1.3：声明式配置 + 可审计的启动树
- **证据**：`deepseek-harness/docs/architecture.md`「Profiles and bundles」节——profile/bundle/`cordis.patch.yml`/`--patch` 分层组合，`dsh --profile web --dump-config` 可打印实际启动的插件树，"Any row it prints can be replaced by a patch of your own"。
- **含义**：rick 的改造（如注册 think/research/exporter 为子 agent）可表达为**声明式 cordis.yml 补丁**，可版本化、可 diff、可审计；pi 的 agent 注册靠 markdown frontmatter 落盘到发现目录，发现/加载逻辑是运行时私有实现。

### 论点 1.4：源码全开放、MIT、strict TypeScript
- **证据**：`deepseek-harness/package.json`（`"license": "MIT"`、`"type": "module"`）；`deepseek-harness/AGENTS.md`「Type safety and documentation」节——"Everything compiles under `strict: true` with `noImplicitAny`"。
- **含义**：rick 若要「把方法翻译进实现体系」，dsh 允许直接读/改实现源码，可控性最高；pi 的核心运行时（agent loop / tool description 生成）不在 rick 可改范围内。

### 论点 1.5：显式优于隐式、失败要 loud、无硬编码可调项
- **证据**：`deepseek-harness/AGENTS.md`「Conventions」节——"Explicit > implicit at package boundaries"、"Misconfiguration fails loud at load"、"No hardcoded tunables in plugins: deployment-varying choices are validated `Config` fields changeable from cordis.yml"。
- **含义**：这些工程约定使 dsh 的行为**可预测、可静态检查**，对承载 rick 这种强方法论的框架是「可控」的基础设施。

## 对对方（pi）的反驳点（缺点，含证据出处）

### 反驳 2.1：pi 触发 subagent 要求模型「手写 JS 字符串」，是黑箱 + 易错 + 不可静态校验
- **证据**：`rick/.rick/draft/loops/loop_6/briefs/research-report-S-bestpractice.md`「BP-1」——"pi 下触发 subagent 的唯一公开执行面是 `subagent` 工具的 `{ workflowScript: "..." }` 字段；脚本内用全局 `runs.run(key, {agent, task})`"，官方示例为 `subagent({ workflowScript: "return runs.run('main', {agent:'worker', task:'...'})" })`。
- **反驳**：把编排逻辑编码进一个**工具调用的字符串参数**里——模型要正确拼 JS 才能触发，拼错即失败（这正是 rick 现状「触发概率低」的直接根因之一）。这是「过度封装」的反面：表面是"一个工具"，实质是"工具里塞了一段动态脚本"，开发者既无法静态校验、也无法复用编排逻辑。对比 dsh 的 `ctx.subagents.start()` + tool schema（论点 1.2），pi 的触发入口是**反模式的黑箱**。

### 反驳 2.2：模型对 subagent 的认知来源是「运行时注入的固定工具描述」，开发者只能选档位、不能改源码
- **证据**：`research-report-S-bestpractice.md`「BP-9」——"模型能调用 subagent 工具，靠的是工具描述文本 `FULL_SUBAGENT_TOOL_DESCRIPTION`（或 compact/custom）…`toolDescriptionMode` 可配 full/compact/custom"。
- **反驳**：pi 把「模型怎么理解 subagent」锁死在三档固定文本里，rick 无法像改自己源码那样精确控制工具 schema/描述——这是黑箱封装；dsh 的 tool schema 由插件在 `ctx.tools` 上注册、随源码可控（`docs/architecture.md`「Add a model-facing capability — register on ctx.tools; its schema joins prompt assembly」）。

### 反驳 2.3：pi 的运行时约束靠「提示词遵守」而非「源码强制」，导致约束是软性的
- **证据**：`research-report-S-bestpractice.md`「BP-6 / BP-8」——"单写者（one writer per cwd/worktree）"、"编排权在 parent、子 agent 默认不持 subagent 工具"均来自 `constraints-and-recipes.md` 的**约定**；rick 现状 D6「提示词未区分谁触发」正是软约束未被执行的体现。
- **反驳**：这些关键约束在 pi 里是**写给模型看的规则**，而非运行时强制的不变式。dsh 则在源码层强制：`subagent/README.md`「Delegated policy」——"pins the child's approval policy to `'never'`"、"`assertSubagentMaxDepth`"（深度强制）、"Duplicate names fail loud"（`subagent/README.md`「registerProvider」）。同样的「触发权/权限边界」，dsh 是编译/运行时保证，pi 是提示词祈使。

### 反驳 2.4：pi 的「触发确定性」要额外引入 workflowScript/agent 注册/recipe 等多层概念，复杂度更高
- **证据**：`research-report-S-bestpractice.md`「BP-1~BP-9」——为达到确定性触发，需同时掌握 workflowScript 语法（BP-1）、内置/自定义 agent 名（BP-2）、compact contract（BP-3）、async/context（BP-4/BP-5）、单写者（BP-6）、编排 recipe（BP-7）、触发权归属（BP-8）、tool description 对齐（BP-9），共 9 条最佳实践。
- **反驳**：为「让模型触发子 agent」这件本应简单的事，pi 需要 9 条最佳实践 + 手写 JS 才能对齐（rick 现状 D1~D7 七项差距正是没对齐的代价）；dsh 通过「插件 + capability seam + 类型化服务 API」把同一件事收敛为「注册一个 provider + 挂一个 tool consumer」，概念面更简洁。

## 结论（一句话）

deepseek-harness 以「一切皆插件 + 类型化服务 API + 声明式配置 + 全源码 MIT」把子 agent 委托收敛为可静态校验、可替换、可审计的显式契约，比 pi 的「模型手写 workflowScript 字符串 + 固定工具描述 + 提示词软约束」更轻量、简洁、可控，更适合作为承载 rick 方法的实现体系。
