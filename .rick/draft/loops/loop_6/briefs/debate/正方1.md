# 正方1：subagent 编排/触发机制视角（pi 优于 deepseek-harness）

## 论点（正方立场，含证据出处）

### 论点 1：pi 的触发入口「唯一且显式」，rick 三角色可 1:1 确定性触发

- pi 触发 subagent 的唯一公开执行面是 `subagent({ workflowScript: "..." })` + 脚本内 `runs.run(key,{agent:'worker',task:'...'})`。证据：`pi-subagents/src/extension/tool-description.ts` 的 `FULL_SUBAGENT_TOOL_DESCRIPTION` 首句「Run subagents only through { workflowScript }; omit action.」；`references/execution-controls.md`「workflowScript is the sole public execution surface」（引用自 rick 侧调研 BP-1，`research-report-S-bestpractice.md`）。
- rick 的 think / research / exporter 三角色，只需注册为 3 个自定义 agent（`name`+`description`+`tools`+`systemPrompt` 的 frontmatter markdown），然后 parent 用 `runs.run(agent:'think', task:'...')` 按名确定性触发。证据：pi `docs/agents.md` frontmatter reference + `src/agents/frontmatter.ts`（引用自 BP-2 / B1~B3，`research-report-S-reasons-agent.md`）。
- 对比：deepseek-harness 的 subagent 触发面是**多 provider + 多 tool 实例**的集合，模型侧没有单一入口。

### 论点 2：pi 的模型认知来源对齐触发语法，触发确定性高

- pi 模型靠 tool description 认识 subagent 工具，描述内含触发语法 + 内置 agent 名 + 护栏（BP-9）。触发写错 agent 名会被 launch 拒绝（"Unknown agent"，BP-2）——fail loud，模型不会"静默不触发"。
- rick 提示词只需与 tool description 语法/agent 名对齐即可确定性触发（对应 rick 侧已证实缺口 D1/D2/D7 的解法）。
- 对比：deepseek-harness 模型侧 `tool-subagent` 的 schema 是按「每个 provider 实例绑一个 toolName」生成的，触发参数更多（见对方缺点 3），模型出错面更大。

### 论点 3：pi 编排权集中在 parent，契合 rick 的「main agent = sense 复核层」架构

- pi 硬规则：普通子 agent **不接收** subagent 工具、不接收 pi-subagents skill，编排权只在 parent（BP-8）。这正契合 rick sense_loop 里「main agent 派发、subagent 执行、不递归派发」的架构。
- 对比：deepseek-harness 支持子 agent 递归委派（`maxDepth` 默认 3）与 continuable 子 agent 自行继续多轮（见对方缺点 5），对 rick 的「单层派发」是过度能力，且增加失控面。

## 对对方（deepseek-harness）的反驳点（缺点，含证据出处）

### 缺点 1：触发面分散，无单一显式入口

- dsh 的 subagent 是「一个能力 seam，多个 provider 实现共存」：`spawn-in-process` / `fork-in-process` / `acp` / `codex` / `claude-code` / `dsh-sdk` 六个 provider 包，加上 `tool-subagent` / `tool-subagent-control` / `tool-subagent-report` 三个模型侧工具。证据：`deepseek-harness/packages/subagent/README.md` 的 family 表格（Provider 与 Consumer 分列）。
- 模型要触发子 agent，面对的是「选哪个 provider 实例 + 哪个 toolName + 哪些参数」，而非 pi 的单一 `subagent` 工具 + `workflowScript`。触发确定性天然低于 pi。

### 缺点 2：子 agent 角色是「组合出来的」，没有「一个角色 = 一个独立定义」的一等公民

- dsh 的子 agent 角色靠 `applyChildComposition(childCtx, parent, composition)`：先 join 父级 agent-preset 组合，再套 child 的 persona 与 toolFilter。证据：`deepseek-harness/packages/subagent/subagent/README.md`（Capabilities 节）。
- 这意味着 rick 的 think/research/exporter 三角色无法像 pi 那样「各写一个 frontmatter markdown 独立注册」，而是要管理「父 preset 组合 + 子 persona + toolFilter」的叠加，角色边界被稀释，触发与调试成本更高。

### 缺点 3：模型侧触发参数多，出错面大

- dsh 的 `tool-subagent` 模型侧工具要模型处理：`provider`、`run_in_background`、`backgroundMode`（one-shot / continuable）、`maxDepth`、`outputSchema`、`toolFilter`、`persona` 等。证据：`deepseek-harness/packages/subagent/tool-subagent/README.md` 的 Config 表。
- 参数越多，模型「该触发时漏填/填错」的概率越高——正是 rick 当前「提示词要求用 subagent 但触发概率低」所担心的那类不确定性来源。

### 缺点 4：developer preview，破坏性变更风险

- dsh 自述处于开发者预览阶段，明确「**THERE WILL BE COMPATIBILITY-BREAKING CHANGES**」。证据：`deepseek-harness/README.md` 与 `README.zh.md` 的 Developer preview 节。
- rick 需要的是「稳定、可长期依赖的触发协议」。一个明示未来会破坏兼容性的运行时，对 rick 方法层的长期先进性（human N1：3 年后不失去先进性）是显性风险。

### 缺点 5：递归委派 + continuable 多轮，对 rick 单层派发是过度设计

- dsh 支持子 agent 递归（`maxDepth` 默认 3，`0` 禁止委派）与 continuable 后台子 agent（`startContinuable`/`followup`/`interrupt`/`reportFrom` 完整生命周期）。证据：`deepseek-harness/packages/subagent/subagent/README.md`（Service API 表）+ `tool-subagent/README.md`（maxDepth 配置）。
- rick 的 think/research/exporter 是「parent 单层派发、完成后回流」，用不到这些机制；引入它们只会增加编排复杂度与失控面，与 pi「编排权在 parent、子 agent 不递归」的简单约束相比，是负收益。

## 结论（一句话）

pi 以「单一显式触发面 + 简单 agent 定义 + 编排权在 parent」直接支撑 rick 三角色的确定性触发；deepseek-harness 的 subagent 是更通用但更复杂的低层 seam，且处于破坏性迭代期，对 rick 的确定性触发诉求是过度设计 + 不稳定。
