## RFC 架构设计（最终）— human 判断 — 2026-08-14 15:30 CST

**human 重新整体设计 rick（原话）**：

> 重新整体设计 rick
> 1. cli : 路由命令，解析参数等 cli 功能层。
> 2. handler: 接受 cli 路由和解析的命令参数，调用 env，builder，runtime 三个模块完成rick cmd 的功能实现，是一个调度聚合层。
> 3. env: 对 rick 在当前机器上工作环境进行配置，关键依赖检查，下载，安装，配置。pi 及 pi 的各种开源扩展与插件，维护与更新。
> 4. builder: 按不同的 cli 功能拼接不同 cmd 命令触发时创建一组符合 runtime(pi,dsh等) 要求规范的一组产物。
> 5. runtime: 对 pi 或 dsh 等调用逻辑的封装。
> 整个 rick 采用这种金字塔的三层架构：路由层 cli；处理层 handler；执行层 env + builder + runtime。
> 当前实现的 doing 的 dag 调度 agent 的逻辑以及门禁检查的逻辑，我们都应该将其重构为上述三层架构中。利用 pi 的能力直接实现 dag 的调度与门禁，而不是在 rick 中维护。rick 要做薄，做成一个引导程序，是对 sense 方法的落地。
> builder 展开：1. templates（提示词模板，go embed 内嵌二进制，按 cmd 功能拼接）；2. pibuilder（为 pi build 具体提示词文件目录的统一入口，内部组合 plan/doing/easy/human-loop 等子 builder）；3. xxxxbuilder（可扩展，新 runtime 只扩展此 builder）。
> runtime 展开：封装具体 agent runtime 的调用逻辑=参数解析+调用，目前支持 pi runtime。
> 设计原则：暂时不考虑其他 builder/runtime，目标让 rick 在执行层拥有更强控制力，深入 agent runtime 内部，更直接控制 LLM 输入信息，实现上下文熵减；保持单一 runtime（pi），投入所有精力将方法付诸实践，强化一种实现；切换 runtime 前提 = 新 runtime 带来更强大的生态与可定制性。
> 请把这一设计原则作为信息内核写到 rfc 中。后面 easy job 时，会将信息内核以某种形式写入 .rick/domain 中，目标是丢弃一切源码，就可以完全 ai coding 出一个功能等价的 rick，这个信息内核称之为 spec，它是结构化的自然语言描述的工程实现契约。
> 接下来要创造一个 job 实现这几个 O：
> 1. 升级 rick 项目的 domain 描述方法，增加 spec 概念（一份软件的工程实现契约），并改造 rick 项目本身，使其拥有这份 spec。
> 2. 重构当前的 rick 设计，使其符合三层金字塔架构，基于新的模块化设计方案构建后续项目。
> 3. 优化 pibuilder，将当前 rick 方法中非三层金字塔架构部分的功能下沉到 pi 中，基于 pi 的最佳定制化开发实践（扩展，agent，插件，skill 等开放组件），将功能集成进去。

**架构设计要点（human）**：
- 三层金字塔：路由层 cli / 处理层 handler / 执行层 env+builder+runtime。
- builder 三件：templates（go embed 内嵌模板）+ pibuilder（pi 统一入口，组合子 builder）+ xxxxbuilder（可扩展，新 runtime 只扩此层）。
- runtime = 参数解析 + 调用封装（目前 pi）。
- 设计原则：单一 runtime（pi）、深入 agent runtime 内部控制 LLM 输入实现上下文熵减；切换 runtime 前提 = 更强生态+可定制性。
- 信息内核 = spec（结构化自然语言描述的工程实现契约），写入 .rick/domain；目标 = 丢弃源码即可 AI coding 出功能等价的 rick。
- doing 的 dag 调度 + 门禁检查：下沉到 pi（利用 pi 能力直接实现），不在 rick 维护。
- 新 job 三目标：O1 domain 描述方法升级 + spec 概念 + 改造 rick 拥有 spec；O2 重构为三层金字塔架构；O3 优化 pibuilder、非三层架构功能下沉到 pi（基于 pi 扩展/agent/插件/skill 最佳实践）。
