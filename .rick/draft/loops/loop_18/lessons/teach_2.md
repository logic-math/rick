## 0｜从你自己的答案接入：容差设计只答了一半

课前的认知强制你已经答过：同一候选改动，离线 benchmark 重复测 5 次——

| 轮次 | 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|---|
| 结果 | +3.2% | −0.4% | +1.1% | +4.5% | +0.6% |

你的回答：「被视作一个噪声，不被选择保留。是容差设计」。

这个回答把**协议的行为**说对了：均值 +1.8% < 3%，按你们现有协议（小于 3% 视为噪声、达到阈值过 review agent）确实拒绝。但问题还有另一半——**这 5 个数字本身在说什么**——那一半才是今天的课。

先做一步你们协议里没做过的算术（自推导，非引用）：这 5 个数的样本标准差 ≈ **1.9%**，与待判效应 +1.8% 同量级。这组数字同时在说两件事：

1. **散布是噪声地板的免费估计**——不需要新工具，5 次重复已经把「这台机器、这个 benchmark、这个时段的噪声多大」测出来了。你们的协议把 5 个数压成 1 个数（+1.8%），方差信息整个扔掉了。
2. **阈值 3% 是盲设的**——它从未与测得的噪声对过表（后果 §1 展开：单次噪声带可以比阈值还宽）。

还有第三件，同样只靠这 5 个数（自推导）：若协议看单次，5 次里 2 次（+3.2%、+4.5%）超阈值触发 review、3 次不到——**同一改动的命运取决于恰好测的是哪一次**。判均值或判单次，方差都没被协议消费。而「容差设计」这个名字你自己点的，它点中了性质：容差隐含前提——**噪声的界已知且稳定**，否则容差没有依据；你们协议里这个前提从未被检验。

最后接到第 1 课收口的三层分数真假观：第一层**噪声假分**（分数是假的——你机制级会的那层）；第二层**OOD 真分测错分布**（分数真、绑错分布——上一课）；这一课补**第三层：统计不确定**——指标测对了、分布也测对了，但这一次测量里改进与噪声混在一起，你还缺把它们分开的协议。它就长在你刚答的那道题上：+3% 是不是真的，你现在**无法回答**——不是缺数据（5 个数就在桌上），是缺判定协议。

本课装的就是这个协议：三要素，且不是并列清单——先降噪声（环境控制）→ 再测（重复测量拿到分布）→ 再判（方差与显著性）。

## 1｜要素一：重复测量——√n 收缩是全部统计收益

**单次测量为什么不可信**：一台 GPU 上的单次计时叠着至少七层噪声（R2 §⑤ 噪声源清单，机制分属 §3/§4）：

| # | 噪声源 | 一句话机制 |
|---|---|---|
| ① | 频率漂移 / DVFS | 驱动逐时刻选频，每个 kernel 可能跑在不同频率 |
| ② | 功率 / 热节流 | 平均功耗达上限或温度 ~85°C → 降频 |
| ③ | L2 残留态 | 上一轮数据留在缓存，这一轮虚快 |
| ④ | 一次性成本 | JIT 编译、module 首载、建图、首分配 |
| ⑤ | host 侧 | launch 5–15μs、sync 模式、GC |
| ⑥ | 邻居/拓扑 | 同节点他进程、同机房他 GPU 共享功耗/温度；跨 NUMA PCIe 受限 |
| ⑦ | 输入值分布 | 全 0/NaN 位翻转少 → 功耗低 → 测得偏快 |

量级（R2 §⑤，推导标注）：PyTorch 博客实测臂 baseline = 0.09752±0.00218ms（mean±std，逐轮样本）——**CV ≈ 2.2%，单次测量 ±2σ ≈ ±4.4%**。回到 §0 那道题：待判效应 3%，单次噪声带 4.4%——单次测量在结构上不可能把 3% 的改进与噪声分开。

**重复测量做的事**：n 次逐轮计时 → 样本均值的标准误 SE ≈ CV/√n。n≈1800/臂时 SE ≈ 0.05%，4.7% 差异 p 值直接打满（§2）。R2 原话值得记住：**「√n 收缩是重复测量的全部统计收益」**。回看 §0 那 5 个数：√5 把 ±4.4% 压到 ±1.7%（2σ 带，仍与效应同量级——边界情形）——5 次还不够，判真要的是可判定的不确定度，不是「多测几次」的模糊直觉。

**工业协议「测几次」怎么定**（Helion×CompileIQ，A：博客）：两级结构——搜索环 `do_bench(warmup=25, rep=100)`（warmup/rep 是**毫秒时间预算不是次数**，见 §4；0.097ms kernel ≈ 1030 次计时/臂，推导）；**独立验证环**加大预算——每臂 n=1744–1757（baseline）/ 2018–2028（optimized）逐轮样本，且**跑两轮独立复测**（run1/run2）。与你那 5 次的差异不在次数多：两级是「搜索用便宜的测、判真用贵的测」——这个分野在 §5 变成整条流水线的承重结构。

**你来推 ①**：单次噪声带 ±4.4%（CV 2.2%），用 √n 收缩估——要把均值的 2σ 噪声带缩到 1% 以内，需要测多少次？（一行算术。）对 0.1ms 级 kernel，千次重复只花约 0.1 秒——离线加预算近乎免费；§6 会看到在线没有这个奢侈（样本量由流量决定）。

## 2｜要素二：方差与显著性——p 与 d 两把闸的分工

拿到两臂逐轮样本后，判真层算两个数。事实层给满，两处留给你推。

**Welch t 检验**（A：Welch 1947，Biometrika 34(1–2):28–35）。检验的原假设：两臂均值相等。标准误 SE = √(s₁²/n₁ + s₂²/n₂)，自由度用 Welch–Satterthwaite 近似（比 Student 版小）。它取代的是更老的 Student 两样本 t——

**你来推 ②**：Student t 的构造假设两总体**方差相等**（合并方差 s_p、df = n₁+n₂−2）。而这组实测臂：baseline std = 0.00218 vs optimized std = 0.00133（R2：差约 65%），n = 1744 vs 2018 也不等。等方差假设在这个场景下成立吗？用 Student 会引入什么？（提示只需要看论文标题：Welch 1947 的标题原文是 "THE GENERALIZATION OF 'STUDENT'S' PROBLEM WHEN SEVERAL DIFFERENT POPULATION VARIANCES ARE INVOLVED"。）

**p 值含义**（R2 §②）：p = 若原假设为真，观察到当前或更极端均值差的概率；p<0.05 = 5% 水平下拒绝原假设，含义是**每次比较在原假设下期望 ≤5% 假阳性率**。两个易错：p 不是「原假设为真的概率」，也不携带效应大小信息。博客报 p=0.0 属浮点下溢（n≈1800、d≈2.5 下真实 p 极小——解读标注）。

**Cohen's d**（A：Cohen 1988）：d = 均值差/合并标准差——以标准差为尺子的均值差，度量无关。与 p **正交**：p 说差异多不像偶然，d 说差异多大。关键的不对称：

- **p 随 n 缩放，d 不随 n 缩放**（d 只依赖两分布本身）。n≈1800 时 0.1% 级真差异也 p<0.05——但 d≈0.05 的 kernel 改进无工程意义。这就是判真要**双闸**（显著 ∧ 有量）的原因。
- 0.2 阈值出处（R2 §③）：Cohen 1988 约定（0.2 小/0.5 中/0.8 大），自述 "somewhat arbitrary"——**领域约定基线，非数学推导值**。作用：把「虽真实但太小」与「真且有量」分开。
- 实测（A：博客）：4.7% 加速 → d≈2.5（0.2 闸的 12.5 倍）；1.75–2.0% → d=0.78。

**会区锚直引（不重讲）**：你机制级答过的「0.5% 级噪声逐轮接受 → 系统性假阳性（loop 优化噪声而非目标）」——统计形态就在这里：仅 p 闸下，5%/比较的假阳性率随比较数累积（R2 §③ 对照句，综合标注）。双闸 + §5 搜索/判真分离，是对这条会区直觉的协议化回答。

**协议边界如实呈现**（R2 Gaps）：逐轮样本可能自相关（频率漂移有周期性）——独立样本假设是近似，do_bench/Welch 协议均未显式处理，锁频后近似成立、未锁频时存疑。知悉即可。

## 3｜要素三：环境控制——先降噪声，再测量

§1 清单里，①②③⑥不是「多测几次」能解决的——它们是**环境**变量，测量前就该压掉。

**浮频是默认状态**（NVIDIA 官方博客原话）："...change processor core and memory clock rates during application execution. These changes can vary performance, introducing errors in measurements and rendering comparisons between runs difficult"——不锁频时，每个 kernel 可能跑在不同频率上。

**锁频**（B：nvidia-smi 官方 man）：

```
nvidia-smi -pm 1                # 驱动常驻，避免首次初始化惩罚
nvidia-smi -lgc 1350,1350       # 锁 SM 时钟
nvidia-smi -lmc 1215,1215       # 锁显存时钟（-rgc 恢复浮频；-pl 功率上限）
```

triton 测试工具 set_gpu_clock 就是这个顺序，锁完**回读** clocks.current.sm/memory 并断言 |实测−目标| < 10MHz（A：源码）——锁频 + 回读校验的完整闭环。锁后频率固定，除非功率/热节流触发（届时表现同浮频）。

**锁频的代价（官方承认的显式取舍，不替你收敛）**：锁频下平均性能低于浮频。TensorRT 原话："There is no definite recommendation on whether the clock should be locked... It depends on whether the deterministic and stable performance or the best average performance is desired"——**确定性 vs 平均峰值**，判断留给用户。判真场景选确定性（要可比，不要好看），性能验收可能相反——你的设计判断。

**预热挡掉三类瞬态**（R2 §④）：① DVFS 爬升（空闲低频→负载 boost 的过渡期）；② 一次性成本——CUDA module 首载、Triton 首调编译、CUDA graph 建图（~300ms，A100）、allocator 首分配——必须挡在计时区外；③ cache 冷热（下一条）。

**L2 清除**（A：triton 源码）：每次计时前对一块 256MiB 缓冲 `zero_()` 写零——"We maintain a buffer of 256 MB that we clear before each kernel call to make sure that the L2 cache doesn't contain any input data before the run"。256MB > 数据中心卡 L2 容量（H100 = 50MB，B），保证覆写全缓存；不清则第 i 轮依赖第 i−1 轮残留——**轮间不独立、跨 kernel 不可比**。

**隔离**：`-c EXCLUSIVE_PROCESS` 独占进程模式（每 GPU 仅一个进程上下文，B）；邻居干扰是实证的——同数据中心同型 GPU 性能有差异、风冷热点节点严重功率节流（A：arXiv 2208.11035，数字未逐页核）；host 内存与拷贝线程钉在 GPU 所在 NUMA 节点（B）。CompileIQ 的形态：WorkerTypes.ISOLATED——崩溃候选跑隔离子进程，"crashing ACF candidates shouldn't kill the search"（A）。

**锁频也压不住的**：功率节流（短窗测量「within 20ms」尤其不稳）与热节流（~85°C），且恶性耦合——高温→漏电流增→同频更耗电→更易功率节流。

**一个连你主场的结构陷阱**（B：TensorRT）：推理间留空隙（每步同步）→ 平均功耗被拉低 → 频率被抬 → **测出虚高吞吐**；满载连续时实际频率更低、真吞吐达不到——trtexec 为此设计成 kernel 间几乎无间隙。这是你已会的「在线/离线差异」的功耗面，同一差异在 §6 以排队论面再现。

**三要素收拢成因果链**（R2 §⑤ 综合标注）：

```
环境控制（锁频去①②、清 L2 去③、预热去④、隔离去⑥）
  → 压低方差本身
重复测量 → 可估方差 → 可算显著性（p）与效应量（d）
方差越小：同 n 检验越灵敏，同幅度改进的 d 越大
```

三要素不是并列清单，是「先降噪声、再测、再判」的递进结构。这也回答了 §0 为什么不能靠「把阈值调大」解决：调阈值只是把盲区挪位置，噪声地板还在原地。

## 4｜do_bench：三要素的代码级实例

签名（A：triton 源码，python/triton/testing.py）：`do_bench(fn, warmup=25, rep=100, grad_to_none=None, quantiles=None, return_mode="mean")`。

**warmup/rep 是毫秒时间预算，不是次数**：先跑 1 次并同步 → 用 5 次计时（每次前清 L2）估出单次耗时 estimate_ms → n_warmup = max(1, int(25/estimate_ms))、n_repeat = max(1, int(100/estimate_ms))。0.097ms 的 kernel ≈ 257 次预热 + 1030 次计时/臂（推导标注）。

**每轮的结构**（CUDA events 计时）：

```
[清梯度(grad_to_none) → 清 L2 → start.record() → fn() → end.record()] × n_repeat
  → 全部入队后一次 synchronize → times = 各对事件 elapsed_time(ms)
```

两个设计点都踩在 §3 噪声源上：事件时间戳打在 **GPU 侧 stream**，不含 host 启动开销（噪声⑤）；轮间**无 host 同步间隙**——只有清 L2 的写零 kernel 占据 stream，维持 GPU 连续负载——防的正是 §3 那个结构陷阱（空隙→拉低功耗→抬频→虚高）。

**短 kernel 的变体**：do_bench_cudagraph 把 n_repeat 次展开捕获成 CUDA graph 后整体 replay 10 次再除回——消除 CPU 侧 launch 开销；变体代价本身就是噪声面证据：建图 ~300ms（A100）须预热排除、Python GC 会破坏捕获须禁（A：源码注释）。

**返回什么统计量**：return_mode ∈ {min/max/mean/median/all}，**当前 main 默认 "mean"**（旧资料常称 median，系旧版行为，源码为准——R2 R7 注记）；quantiles 返回分位数；"all" 返回原始逐轮列表。

**为什么报分布而非单值**（R2 §①）：逐轮时间本身有分布（频率漂移/温度/缓存态）；单值丢失方差信息 → 下游无法做显著性检验；分布（原始列表或分位数）才供 Welch t / Cohen d 消费。证据链在此闭环：**判真协议的输入必须是分布**——这是 "all" 与 quantiles 存在的原因；Helion×CompileIQ 搜索环取 mean 作目标值，判真消费逐轮样本（§5）。

## 5｜Helion×CompileIQ：三要素组合成工业级判真流水线

这是三要素的工业级组合（A：PyTorch 博客 2026-10-19）。先看 objective 函数里的顺序结构：

```
候选（编译器控制项）
  → 编译
  → 跑一次
  → 对 PyTorch 参考实现做正确性检查
      不过 → invalid score，"dropped from the search before it ever
             contributes a timing measurement"（正确性 gate 严格在计时之前）
  → 过 gate 者 → do_bench(run, warmup=25, rep=100, return_mode="mean") 计时
```

正确性 gate 在计时之前——你已会的两失败模式里「快但错→gate 拦截」的工业版，而且 gate 前置还省钱：错误候选不消耗任何计时预算。

**搜索环**（A：博客代码）：`SearchConfiguration(problem_type="min", generations=8, pool_size=15)`——8 代×15 候选池；`WorkerTypes.ISOLATED`（§3 隔离）；`gpu_benchmark_mode(clock_mhz=...)` 上下文管理器**整场搜索期锁频**；`task_timeout=60`。

**独立验证环（判真环）**——与搜索环分离：胜出候选 "re-measured independently using increased warmup and repetition iterations under fixed GPU clock frequencies"。接受条件是**三条件合取**（博客代码注释原文）：

```
(requiring p < 0.05, cohens_d > 0.2, and optimized.mean < baseline.mean)
  =  p < 0.05  ∧  d > 0.2  ∧  方向闸（优化臂均值更低）
```

**你来推 ③**：p 和 d 都过了、方向闸才拦得住的失败长什么样？（提示：p 说「多不像偶然」，d 说「差异多大」——这两个描述里，谁都没有说差异朝哪边。）

复现性内嵌在协议里：run1/run2 两轮独立复测 "virtually identical within experimental variance"（d=2.501 vs 2.489，均值差 <0.01%）——独立复测是协议一环，不是附加保险。同一套过滤套用在所有目标形态上（A）：occupancy（21.60→21.76%，d=13.17）→ 独立转测 runtime 1.75–2.0%（d=0.78）；多目标 Pareto 6.9% + 4.5pp L1TEX；双 shape 联合 d=67.71 / 4.54。

**机制要义**（R2 §⑥）：统计判真**不在搜索环内逐代执行**——搜索环只需相对排序；判真在「独立、加预算、锁频」的验证环执行。搜索与判真分离，是「训练-验证拆分」的测量版对应。

**你来推 ④**：把三条件合取搬进搜索环逐代执行（8 代×15 候选每次全套）会发生什么？从两面想：成本面（验证环的预算形态×120 次比较）；统计面（回想你已会的 0.5% 逐轮接受——每代多次比较时，被「接受」的噪声往哪去）。

接到第 1 课的差环上：你复述「独立验证集」时的差环是**接受门槛的形态**（每轮候选 gate vs 一次性部署验证）。CompileIQ 给了第三种形态：搜索环内只排序不判真 + 终验环统计判真；你自己的协议（离线 AUC gate → 线上真实流量实验）是第四种（§6 展开）。哪种形态进美团 loop是你的设计判断——本课只把可选项的机制给全。

**为什么值得为 1–2% 建这么重的判真装置**——博客语境（已裁决引用，两层标注）：对象是已高度优化 kernel 的最后一截——naive 基线上的加速声明 "close to meaningless for real-world workloads"（values 待裁决 7，你已裁决接受：「baseline 不能以 pytorch 原生实现对比，这个值没有实际价值」）；而 "Even a few percent at the bottom of the stack... is valuable at that scale"（values 待裁决 6，你已裁决接受：「优化多少要看具体问题」）——作者立场，接受为学习前提 ≠ 接受为美团投入方向。判真协议在此的位置：**它给了小数字以引用权**——没有统计过滤，1–2% 级声明无法与噪声区分，也就无法被引用。这就是钥匙课的意思：第 9 课讲 Helion×CompileIQ 全文时，统计语言直引不再铺垫。

## 6｜桥到你的主场：在线灰度判真与离线差在哪

你的自有协议（第一轮原话）：「我会在大规模的 auc 上离线验证他的正确性，然后在部署到线上，以实际流量开实验观察全链路耗时的变化」——结构上已经是**离线 gate + 独立分布验证**。本节补它缺的统计层，以及两边噪声结构的差异。

**离线结构的本质**（R2 §⑦）：实验者全控——负载自造（固定 batch / 闭式并发 / 背靠背入队）、环境自锁（§3）、同机对照；**唯一随机源是测量噪声**，所以离线判真 = 对抗测量噪声（§1–§3 的全部）。

**在线 A/B 的统计内核与离线同源**（A：Kohavi/Tang/Xu 2020，*Trustworthy Online Controlled Experiments*，Ch.17）：按单元（用户/请求）随机分流到变体 → 每单元业务指标 → CLT → 两均值 t 检验 / 两比例 z 检验；α（0.05）；**样本量由功效分析定（MDE/α/1−β）**；置信区间报效应。你在这套里已经认识的东西：α 就是 §2 的每比较 5% 假阳性率，双臂对照就是 Welch 的两臂——**差别不在统计内核，在噪声结构与混杂控制**：

| 在线特有 | 机制 | 协议对策 |
|---|---|---|
| 时段/周期/漂移 | 流量按小时星期波动、用户构成漂移、外部事件 | 跑满周期、时段分层 |
| novelty/primacy | 新体验初期效应大后衰减 | 勿信首日，跑满周期 |
| 变体间干扰/泄漏 | 共享缓存、双边市场破坏 SUTVA | 干扰控制 |
| 管线自身 | hash 偏置、机器人、重定向丢失 | A/A 实验校准假阳性率 |

**SRM 护栏**（A：同书 Ch.21 + MSR《Diagnosing Sample Ratio Mismatch in A/B Testing》）：对实际分配比例做卡方检验——与配置比例（如 50/50）显著不符 = **实验内部效度已坏**（分流本身被污染），后续任何显著性都不可信，应进每个实验。它是在线版的环境控制：**测量装置本身的正确性 gate**。

**开式 vs 闭式**（会区锚，直引不重讲）：在线是开式（控制到达率、请求独立到达），离线基准多为闭式（控制并发、下一迭代等上一迭代）；开式下队列可增长、延迟分布由**到达过程的方差**决定，两模型由 Little 定律 L=λW 连接。§3 那个「推理空隙→虚高吞吐」就是同一差异的功耗面例证（R2 §⑦）。

**灰度的判真形态**（R2 §⑦）：小流量渐进放量（ramp）+ 护栏指标自动回滚——在线版的「显著 ∧ 有量 ∧ 方向对才接受」；判真时间尺度从分钟级（离线）变天/周级（覆盖周期）；**样本量由流量决定，不可像离线那样加测随意扩**——§1 那个「千次重复只花 0.1 秒」的奢侈，在线没有。

三要素的在线对应（R2 §⑦ 综合标注）：

| 三要素 | 离线（§1–§3） | 在线灰度 |
|---|---|---|
| 重复测量 | n 次逐轮计时 | 样本量功效分析 + 跑满周期 |
| 方差与显著性 | Welch t + Cohen d 双闸 | 同套检验 + SRM 护栏 + A/A 校准 |
| 环境控制 | 锁频/预热/隔离 | 分流一致性 + 干扰控制 + 时段分层 |

**原创视角（本课交棒点）**：离线判真协议的形式化有标准答案（本课这套）；**在线灰度判真协议的形式化没有先例**——R 谱系 Gaps 明载「面向在线推理 infra 的 RSI 无直接先例」（research_1），R2 Gaps 明载美团侧分层实验/流量一致性/护栏清单无公开一手材料——你的实操就是主场。到达分布噪声 + 时段效应 + 混杂因素如何组成在线判真协议，是空白，也是第 21 课美团设计提案的承重件。

## 7｜收尾钩子：探活探针——判真的分布式形态

loop_15 的主题是探活测试，这里留一个跨域钩子（A：kubernetes.io 官方 docs；对照为综合标注）：

| 探针 | 失败的后果 | 检测什么 |
|---|---|---|
| liveness | 超过 failureThreshold → kubelet 杀容器、按 restartPolicy 重启 | 死锁类不可恢复态 |
| readiness | Pod IP 从 EndpointSlice 摘除、不收流量，**容器继续跑** | 临时不能服务（加载/过载恢复等） |
| startup | 启动期专用，未成功前抑制另两探针 | 慢启动保护（官方例 30×10s=300s 后 liveness 接管） |

官方 Caution 反模式①：liveness 探测在高负载下失败（探针端点本身变慢）→ 重启 → 更少副本扛同样流量 → 负载更高——**正反馈重启风暴**（"restarting of container under high load... increased workload on remaining pods"）。依赖检查放 readiness 不放 liveness，也是官方模式（重启修不了依赖，反而放大其负载）。

同构（综合标注，非官方原文）：探针是**二值化的重复测量**——periodSeconds = 采样间隔、timeoutSeconds = 测量窗、failureThreshold = 容忍度（默认 3 连败才判死 = 容忍 2 次噪声假阳，工程形态的显著性水平）；**级联重启 = 噪声假阳在分布式层的放大形态**。判真假阳你在 §2 已见过统计形态（5%/比较），这里的形态是重启风暴——同一个「测量噪声 + 容忍度」命题，换一层放大器。period/timeout/failureThreshold 的检出延迟 vs 探针自身开销权衡留给你——它就是你领域的判真协议调参。

## 8｜本课关键概念清单（自述检验用）

学完这一课，下面 6 条你应该能不看笔记各用一两句自述——它们就是下一轮判档的 expectation 清单：

1. **判真协议三要素**：重复测量 / 方差与显著性 / 环境控制——且是递进结构「先降噪声、再测、再判」，不是并列清单
2. **√n 收缩**：重复测量的全部统计收益；单次测量的 ±2σ 噪声带可以比待判效应还宽（CV 2.2% → ±4.4% vs 3%）
3. **双闸**：p（多不像偶然）与 d（差异多大）正交——p 随 n 缩放、d 不随；n 大时 0.1% 也显著但 d≈0.05 无工程意义；0.2 是 Cohen 自述 "somewhat arbitrary" 的领域约定
4. **环境控制的对象**：频率（锁频 + 回读校验）、瞬态（预热三类）、缓存（L2 清 256MB）、邻居（隔离）——锁频有官方承认的显式代价（确定性 vs 平均峰值）
5. **搜索与判真分离**：搜索环只做相对排序；判真在独立、加预算、锁频的验证环，三条件合取 p<0.05 ∧ d>0.2 ∧ 方向闸，run1/run2 复测内嵌
6. **在线对应**：三要素映射到「功效分析 + 跑满周期 / 同套检验 + SRM + A/A / 分流一致性 + 干扰控制 + 时段分层」——统计内核同源，差别在噪声结构与混杂控制
