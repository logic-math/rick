## [ZPD 冷启动探针轮·第一轮作答] human 判断 — 2026-11-02 13:25

（parent 呈现 4 个校准探针，human 凭记忆作答）

human 原话：
1. 所有的代码维护在一个关系型数据库中，维护一套元数据信息来将进化轨迹记录下来，包括 code 的 git 地址，版本信息，精英格信息等等，精英格本身也被 db 所管理。  LLM 作为 proposer 第一步 启动loop，会从通过采样器选择一个格子，提取这个格子的描述以及 code 代码，然后随机选择相邻岛的格子，汇总他们的代码作为灵感，构建一段提示词，调用 llm 生成代码 diff 并把代码 diff 应用于 code db 成为一个新的分支，在这个过程中，会通过评估器跑性能优化的正确性与 benchmark 验证，只有得分大于精英格本身已有 code 的时候，才会将其替换保留下来，成为新的精英。 逐一执行这一循环，直到得到一套完整的精英格，保留了在不同优化方向上的进化轨迹。 维护岛模型，周期迁移，多样性重播本质上都是为了保证进化过程中有足够的多样性，其目的是为了跳过局部最优解，同时我们得到的是一副精英地图，在不同方面上我们得到了不同工作负载下不同解决方案的性能档案，多样性的引入帮助模型跳出局部最优解，长期来看避免陷入低水平的竞争中。 如果没有多样性机制，搜索行为会退化为纯利用问题，对某个有效方法会一直优化陷入死胡同。 
采样生成优化计划需要更强的模型，但写代码并不需要，这样做可以节约成本，使得进化能够规模化发展，多个指标联合优化同样是将目标视为一种约束，可以启发 LLM 再选择优化方案的时候直接考虑约束目标以提高生成优秀代码的效率。
2. harness 是指 除了 LLM 模型之外的一切构建 agent 的基础设置的总称，通常是指agent=llm+harness，使得 LLM 能够对物理实际感知并产生成作用的组件，包括 loop，tools，env，等等子系统，以及基于这些子系统衍生出来的各种封装组件，例如 sunagent， dag，moeromoy 等等。 
典型可编辑的组件有， loop，skill， model，agent 的扩展或插件， proposer 在 loop 中负责生成解决方案， verifiler 负责检查这个生成的解决方案是否满足目标需求。  因为正确性与性能是两个相互依赖但彼此正交的指标，先检查正确性在验证性能，通常成本更低。OOD 这个概念我不理解。
3. 精度验证 作为 正确性信号，在线延迟或吞吐作为性能信号。 二者是分离的，如果合一那就是 auc，大规模验证排序模型打分能力，即验证正确性也能验证吞吐能力，性能越好完成 auc 验证的时间越快，但这么做成本很高。 因此正确性和性能分离验证是一个降低成本的工程选择。  在线指标是端到端的但噪声太大，无法形成明确的反馈路径。  比如 过于考虑精度误差对性能的影响，使用过高的精度标准错失优化机会。
4.  我会在大规模的 auc 上离线验证他的正确性，然后在部署到线上，以实际流量开实验观察全链路耗时的变化。 会有不同离线压测和真实流量会受排队论的影响，即单卡 GPU 对于请求的消费能力存在上限，即如果在线请求和离线测试 请求到达时间的分布不遵循相同的分布，那么测试的差异会比较大。  没有容差会导致无效进化，无效进化的表现就是，多轮迭代下不会取得明显的性能收益，无法将 token 转换为实际的性能收益。
