# Chapter 10: Asserting Expectations — 事实总结

## 核心概念

- **Assertion（断言）**：在程序中嵌入的可执行的正确性检查，当条件不满足时程序立即终止并报告位置
- **Precondition（前置条件）**：函数调用前必须满足的条件
- **Postcondition（后置条件）**：函数返回后必须满足的条件
- **Invariant（不变量）**：在程序的特定执行点始终应该成立的条件（如循环不变量、对象不变量）
- **Design by Contract（契约式编程）**：Bertrand Meyer 提出，将前置/后置条件/不变量作为正式接口规约
- **Fail-fast（快速失败）**：在错误发生时立即终止，而非让错误传播到远处后才暴露
- **Reference run（参考运行）**：已知正确的程序执行结果，用于与当前运行对比

## 主要内容

### 10.1 自动化观测
断言是将"观察"自动化的手段：不需要人工检查每个变量，程序自动在关键点检查是否满足预期。

书中的核心主张：**观察 + 比较 = 断言**。断言将"期望的状态"编码进程序本身。

### 10.2 基本断言

**C 语言 `assert.h`**：
```c
assert(condition);  // 若 condition 为 false，打印位置信息并 abort()
```

**Java `assert` 关键字**（JDK 1.4+）：
```java
assert condition : message;  // 需要 -ea 启动参数启用
```

**Python `assert`**：
```python
assert condition, message  // -O 优化模式下禁用
```

**关键原则（书中 Section 10.2）**：
- 断言不应有副作用（`assert x++ > 0` 错误）
- 断言失败时应立即终止，而非继续（fail-fast）
- 断言是文档的一部分——读代码时断言说明了作者的假设

**干扰问题（Section 10.2）**：
- 断言本身可能改变程序行为（如断言中的函数调用有副作用）
- 书中原则：**断言必须是纯观察，不能改变程序状态**

### 10.3 不变量断言
循环不变量示例：
```c
// 循环不变量：a[0..i-1] 已排序
for (int i = 1; i < n; i++) {
    assert(is_sorted(a, 0, i-1));  // 在循环开始时检查
    // ... 排序操作
    assert(is_sorted(a, 0, i));    // 在循环结束时检查
}
```

### 10.4 正确性断言
对复杂数据结构的完整性检查：
- 链表：检查 null 指针、循环引用
- 二叉树：检查 BST 性质、高度平衡性
- 哈希表：检查负载因子、桶分布

### 10.5 断言即规范
书中（Section 10.5）的重要观点：**断言是可执行的规范**。
- 传统规范：自然语言，不精确，不可执行
- 断言规范：代码，精确，可在运行时自动验证
- 意义：断言将"这段代码应该做什么"从注释变成可检查的约束

### 10.6 从断言到验证
断言可以构成完整的验证体系：
- 每个函数的前置/后置条件
- 每个循环的不变量
- 程序的全局不变量
→ 如果所有断言都通过，程序正确性有一定保证（不是完全保证）

### 10.7 参考运行（Reference Run）
对比两次运行的状态差异：
- 一次已知正确的运行（参考运行）
- 一次怀疑有问题的运行（当前运行）
- 在关键点对比程序状态
- 差异处即为 infection 发生的位置

### 10.8 系统断言（四类）

**10.8.1 内存断言**
工具链：
- `MALLOC_CHECK_`：检查 double-free、越界写
- `ELECTRICFENCE`：在分配内存前后放置不可访问页，越界立即 segfault
- `VALGRIND`（Memcheck）：使用 shadow memory 机制，V-bit（有效位）+ A-bit（可寻址位）
- `PURIFY`：商业版内存检查工具
- `CYCLONE`：类型安全的 C 变体，编译期防止野指针

**VALGRIND shadow memory 机制**：
- 每个字节维护 V-bit（该字节的值是否已初始化）和 A-bit（该地址是否可合法访问）
- 读取未初始化值时报告
- 访问已释放内存时报告
- 性能代价：10x-50x 速度降低

**10.8.2 线程断言**
- 检测数据竞争（data race）：两个线程同时访问同一内存位置，至少一个是写操作
- 工具：ThreadSanitizer（TSan）、Helgrind（VALGRIND 组件）

**10.8.3 类型断言**
- 运行时类型检查（动态类型语言）
- 类型强制（C 的 `static_assert`）

**10.8.4 规格断言**
- 使用形式化规格语言（如 JML for Java）
- 自动生成运行时断言

### 10.9 生产代码中的断言
**两种策略**（书中 Section 10.9）：
1. **关闭断言**（性能优先）：`NDEBUG` 宏，`-O` 标志
2. **保留断言**（可靠性优先）：NASA、航空航天软件的做法

书中引用 A320 飞机软件事故（Section 10.4/10.9）：规范与意图偏差导致的失败——规范本身正确，但未捕获完整意图。

## 对四个追问的回答

**1. 「实验报告」vs「解决问题」**
断言是将"期望状态"编码进程序的机制（Section 10.5）——断言失败即是实验报告（报告了哪个不变量被违反）。断言服务于问题解决，两者不对立，但本章侧重自动化检查而非人工记录。

**2. 「探针不影响系统状态」**
书中 Section 10.2 明确原则：**断言必须是纯观察，不能改变程序状态**（"Assertions must have no side effects"）。Section 10.10 进一步指出违反此原则会导致 Heisenbug。这是书中对"探针透明性"最直接的设计规范。

**3. 「学习、设计、验证正交」**
Sections 10.5-10.6 的断言→验证链接，以及 Chapter 11 开篇明确引出"从断言到异常检测"——三者不独立，断言（设计）产生的验证结果驱动下一轮学习（异常定位）。

**4. 「理解状态转移是否足以覆盖所有bug」**
Chapter 11 开篇明确引文 + A320 事故（规范与意图偏差）：即使所有断言都通过，程序仍可能违反未被断言覆盖的意图。状态转移的理解是必要条件，但不充分。

## 关键引用

- "Assertions are executable specifications." （Section 10.5）
- "Assertions must have no side effects." （Section 10.2）
- "Fail fast: when an assertion fails, stop immediately."
- VALGRIND："uses shadow memory with V-bits and A-bits to track memory validity"
- A320 事故：规范与意图偏差的真实案例

## 与AI Agent调试的关联

- **AI 版断言**：在 AI Agent 工具调用后，自动检查输出是否满足预期格式/内容约束——这是 AI 版的后置条件断言
- **不变量对应**：rick 的测试脚本相当于任务级断言，检查"任务完成"这个不变量
- **副作用问题**：向 AI Agent 输出中添加的"检查指令"可能改变 AI 的行为（副作用），对应书中"断言必须无副作用"的原则
- **参考运行**：记录一次成功的任务执行作为"参考运行"，后续执行与其对比，快速定位 infection 点
