# AI Coding Agent 的调试困境：从盲目重试到科学调试

> 当 AI Agent 遇到 bug，它会怎么做？把错误信息贴进去，再试一次。再失败？再贴一次。这就是当前大多数 AI Coding 框架处理调试的方式——**盲目重试**。这篇文章分析这个问题的根源，并提出一个系统性的解决方案。

---

## 一、AI Coding 框架的调试困境

Rick 是一个 Context-First AI Coding Framework，核心公式是：

```
AICoding = Humans + Agents
Agents = Models + Harness
```

其中 `doing` 阶段负责让 AI Agent 循环执行任务直到测试通过：

```
对每个 task：
  重试最多 5 次：
    1. 生成测试脚本
    2. 调用 Claude Code 执行任务
    3. 运行测试脚本
    4. 通过 → git commit，标记 done
    5. 失败 → 写入 debug.md，继续重试
  超过限制 → 退出，等待人工介入
```

这个循环在 Job 1（文档生成）中表现出色：9 个任务，零重试，100% 完成率。但当任务涉及真实的代码 bug 时，问题暴露了——重试不收敛，Agent 陷入无效操作的漩涡。

这不是 Rick 特有的问题。Microsoft 的 debug-gym 也面临同样的困境。这是当前所有 AI Coding 框架调试能力的系统性缺陷。

**明确调试边界**：Rick 调试的对象不是 Rick 本身，而是用户用 Rick 开发的**业务代码**的 bug。Rick 在这里扮演的角色是协调者和记录者——通过提示词同时控制「如何调试」和「如何记录」。产品设计类 bug（跳脱系统之外存在的问题）超出 Rick 调试能力的范围。

**调试终止条件**：调试流程有且仅有两个合法的终止状态——修复成功，或论证该 bug 在当前约束下无法修复。对无法修复的 bug，输出「论证无法修复的原因」是可接受的终止条件，而不是无限重试。

## 二、问题的物理本质：状态机视角下的 Bug

要理解为什么盲目重试不 work，先要理解 bug 的物理本质。

**软件是状态机**。程序执行就是状态转换序列：输入触发初始状态，每条语句执行一次状态转换，直到输出最终状态。

```
正确执行路径：
S0 → S1 → S2 → S3 → ... → Sn（预期输出）

有 bug 的执行路径：
S0 → S1 → S2' → S3' → ... → Sm（实际输出：失败/异常）
                ↑
            感染点：某个缺陷引起状态分叉
```

**Bug 的物理本质**：某个缺陷（defect）在特定输入下引起状态序列分叉，分叉后的错误状态沿调用链传播（感染），最终表现为可观测的失败（failure）。程序故障的三层结构——缺陷→感染→失效——是递进关系，后者依赖前者，不可跳步。

感染链的传播可能非常长：

```
缺陷（代码层）
    ↓ 引发
错误状态（内存/变量）
    ↓ 传播
错误中间结果（函数返回值）
    ↓ 扩散
错误输出（用户可见）
    ↓ 表现为
测试失败（可观测）
```

这就是为什么「看到错误信息」不等于「找到 bug」——错误信息是感染链的末端，缺陷在链的起点，两者之间可能隔着几十层状态转换。

状态机视角不只是一个比喻，它是概念地图的中心节点。在状态机的解释下，状态的转移存在绝对确定的因果关系，因此导致 bug 的可能因素会构建出一个集合，通过逐步缩减这个集合，就可以简化复现过程直到解决问题。TRAFFIC 七步调试法（追踪/复现/自动化/定位感染源/聚焦/隔离/修正）本质上就是在状态机框架下沿感染链反向追溯：

```
TRAFFIC 状态机视角：

Track       → 追踪失败症状，确认感染链末端
Reproduce   → 稳定复现，固定感染链入口
Automate    → 自动化验证，构建感染链探针
Find        → 定位感染起点（最难的一步）
Isolate     → 聚焦最可疑的感染源
Focus       → 隔离感染链，排除无关状态
Fix         → 修正缺陷，消除分叉根因
```

科学调试法（观察→假设→实验→分析）就发生在第五步「聚焦感染源」——通过实验逼近缺陷位置，引入了观察、假设、实验、分析的科学方法论。

Delta Debugging 是科学调试法的一个特例：通过试图复现一个没有 bug 的系统，然后与存在 bug 的系统进行 diff，逐渐消除二者之间的差异性状态，通过增加共性、减少差异，逐步逼近缺陷。如果所有变更是被序列化的，就可以应用二分查找以 logN 的代价定位问题，因此**二分查找是 Delta Debugging 的一个特例**。

**关于探针效应**：向状态机注入观察工具（打印语句、断点、调试器）本身就是一次状态转换，不可能完全不影响系统。但可以加一个限定条件：如果探针没有处于错误传播路径上，或者不会改变错误传播路径本身，那么这个状态转移是自闭环的，不影响失败的表现——这种意义上的「不影响」是可以做到的。探针效应真实存在且不可完全消除，Rick 应将其纳入分析而非假装可以规避。

## 三、现有方案的根因诊断：为什么盲目重试不 work

明白了 bug 的本质，再看盲目重试为什么失效就很清楚了。

**现状：Rick 的 debug.md 只记录「发生了什么」**

```markdown
# debug1: 测试失败

**问题描述**
运行测试脚本，输出：
  Error: cannot read property 'xxx' of undefined
  at line 42

**解决状态**
未解决

**解决方法**
（空）
```

这种记录有三个根本缺陷：

**缺陷1：只有感染链末端，没有感染链分析**

错误信息 `cannot read property 'xxx' of undefined` 是感染链的末端表现，不是缺陷位置。Agent 下次执行时拿到这条信息，不知道该去哪里找真正的问题，只能「在附近随机修改」。

**缺陷2：没有假设，没有已排除的方向**

盲目重试的本质是：每次都是全新的 Agent 实例面对全新的问题。没有「上次试了 A 没用，这次应该试 B」的推理链。每次重试都在重复相同的信息，产生相同的（错误）尝试。

**缺陷3：没有运行时观察能力**

感染链在程序运行时展开，但 Agent 只能看到源代码和测试输出。它无法回答：「这个变量在第 23 行执行后的值是什么？」这相当于让医生只看病历，不让做任何检查就开刀。

## 四、恶性循环的系统分析

这三个缺陷叠加，形成一个恶性循环：

```
                    ┌─────────────────────────────────┐
                    │                                 │
                    ▼                                 │
             Bug 未解决                               │
                    │                                 │
                    ▼                                 │
         无效操作积累（随机修改）                      │
                    │                                 │
                    ▼                                 │
        上下文混乱程度 ↑                              │
        (debug.md 堆积无效信息)                       │
                    │                                 │
                    ▼                                 │
        错误信息干扰下一次 Agent                       │
                    │                                 │
                    ▼                                 │
           调试能力 ↓                                 │
                    │                                 │
                    └─────────────────────────────────┘

核心变量：上下文混乱程度
恶化方向：随时间单调递增（每次失败都追加信息）
系统特性：正反馈，无自我纠正机制
```

**核心变量是上下文混乱程度**。

盲目重试的每次失败都会往 debug.md 追加更多错误信息，但这些信息大多数是无效的：重复的错误消息、无效的修改记录、相互矛盾的推测。随着重试次数增加，混乱度单调递增，Agent 面对的是越来越嘈杂的上下文，反而越来越难找到真正的问题。

这个循环没有自我纠正机制。它会一直恶化，直到达到重试上限，触发人工介入。

**两个可能的介入点**：一是提升写入上下文的信息质量（接近真实 + 调试规范），二是主动清理已写入的混乱信息。但这两者不是并列关系——提升信息质量是根本性的，因为没有它，即使清理了旧信息，新写入的仍然是混乱的。清理机制是补充，不是替代。

## 五、与 debug-gym 的对比

Microsoft 的 debug-gym 是目前最接近「AI 调试框架」的研究项目，值得单独分析。

**debug-gym 做对的地方**：

```
唯一的关键信息保护机制：
  eval 结果始终注入系统提示（而非对话历史）
  
核心洞见：测试结果是「当前假设是否正确」的真相锚点，
          不能被上下文压缩机制丢弃
```

这是非常小但非常关键的设计。它保证了 Agent 始终知道「现在的代码跑出来是什么结果」，而不是依赖可能被截断的对话历史。这也是「关键信息优先保护」思路的最小实现。

**debug-gym 没做的地方**：

1. **没有内嵌假设-验证循环**：Agent 的行为还是「看到错误→修改代码→跑测试」，没有引导 Agent 先建立假设再验证。这不是 debug-gym 特有的缺陷，而是当前所有 AI 调试框架真实存在的空白。

2. **token 超限时直接丢弃最旧步骤**：除了 eval 结果，其他信息都按时间顺序被截断，没有按「重要性」保护。一条早期发现的关键线索可能因为时间久远被丢掉。

3. **交互式调试器是对的方向**：debug-gym 用 pdb 等工具让 Agent 观测中间状态，这是重要的设计——让 Agent 能沿感染链追溯，而不是只看最终输出。

**对比总结**：

| 维度 | Rick 现状 | debug-gym | 理想状态 |
|------|----------|-----------|----------|
| 假设-验证循环 | ❌ 无 | ❌ 无 | ✅ 内嵌 |
| 运行时观察 | ❌ 无 | ✅ pdb | ✅ 有 |
| 关键信息保护 | ❌ 无 | ✅ 最小实现 | ✅ 分级保护 |
| 上下文清理 | ❌ 无 | ❌ 仅时间截断 | ✅ 按重要性 |

## 六、解决方案：四要素架构

**主要矛盾**：信息质量（A）与上下文混乱（B）之间的张力。

提升 A 需要记录更多推理过程，但这会增加 B；控制 B 需要压缩信息，但可能丢失重要的 A。这个张力不能靠单点优化解决，需要系统性的架构应对。

**主攻方向**：「接近真实 + 调试规范」——让 AI 能观察运行时状态（接近真实），并遵循调试方法写入结构化信息（调试规范）。这条路是根本性的、决定性的，原因有三：

- **根本性**：触及上下文混乱的根源，防止错误信息写入
- **全局性**：对所有技术 bug 有效（产品设计类 bug 超出范围）
- **决定性**：没有它，即使清理了旧信息，新写入的仍然是混乱的

**控制手段的优先顺序**：方法在前，工具在后。因为方法决定了以何种视角观察运行时状态，哪些状态是值得观察的——视角先确定，才知道需要什么工具。

四要素按优先级排列如下：

---

### 要素一：debug_skill — 三阶段调试 SOP（第一优先）

这是最高杠杆的改进，核心思路是**将调试能力完全内聚到一个 core skill 文件中**。任何加载了 `debug_skill` 的 Agent（doing / learning / plan 均适用），都会在自己规范的工作目录下，将所有调试记录集中存放到 `debug/` 目录，每个 bug 一个独立 md 文件。

**设计原则：职责内聚**

调试方法论、记录格式、SOP 步骤全部收进 `debug_skill.md`，`doing.md` 模板只负责加载这个 skill 去做事，不再冗余定义任何调试格式。好处：维护单一来源，任何 Agent 只要声明加载此 skill，即可获得完整调试能力。

---

#### 准备阶段

加载 `debug_skill` 后，遇到 bug 时必须先完成准备：

1. 在当前工作目录（`.rick/jobs/job_{n}/[doing|learning|plan]/`）下创建 `debug/` 目录
2. 确定本次 bug 的编号：读取 `debug/` 目录下已有文件，取最大编号 +1（从 1 开始）。编号是 job 内全局递增的，不按 task 重置。
3. 在 `debug/` 目录下为当前 bug 创建独立文件：`bug{n}-{简要描述}.md`，后续所有调试记录均追加到此文件

---

#### 阶段一：源码推理法

**适用场景**：零运行成本的快速路径，基于静态源码阅读推断根因。大多数常见 bug 在此阶段即可解决。

**职责分工**：主 Agent 负责执行改动、验证、回滚和记录；subagent 的唯一职责是大范围阅读源码后输出「假设列表」（每条假设包含：观察到的代码证据 + 推断的根因 + 建议验证的改动），输出后即退出，不执行任何改动。

**执行步骤**：

1. 主 Agent 启动 subagent，subagent 基于 SENSE 方法对源码进行大范围深度阅读，输出假设列表后退出
2. 主 Agent 选取优先级最高的假设，执行对应的源码改动
3. 主 Agent 依据 SPEC.md 的要求运行测试，验证 bug 是否修复
4. 若未修复，主 Agent **必须回滚所有改动**，恢复到改动前的状态（可用 `git diff` 确认干净）
5. 在 `bug{n}-xxx.md` 中追加记录：

```markdown
# 源码推理法

## 尝试1
- 观察: 源码中存在 A、B、C 逻辑
- 假设: xxx 导致了 bug 的产生
- 验证: xxxx 改动后观察 bug 是否解决
- 结论: 已解决，现象是 xxxx / 未解决，现象是 xxxx，已回滚变更
```

6. 最多尝试 3 次。每次尝试前代码必须处于回滚后的干净状态（`git diff` 无输出）。3 次均未解决则进入阶段二

**尝试 vs 实验的区别**：尝试是基于源码的静态推理，不运行程序，代价低；实验需要运行程序观察真实状态，代价高但结论可靠性高。源码推理法属于尝试，后两个阶段属于实验。

---

#### 阶段二：增量调试法（Delta Debugging）

**适用场景**：存在可对比的基线运行时——即与当前版本行为不同的历史版本或最小配置。核心思路是找到 Pass 集合与 Fail 集合，通过逐步消除差异缩小根因范围。

**执行步骤**：

1. 寻找复现 bug 的最小测试集：最简测试用例，最低复现成本
2. 选择基线运行时（与当前版本最接近、行为正常的系统）。判断标准：git log 中存在某个能稳定通过最小测试集的历史 commit，或存在去掉某个配置/环境变量后 bug 消失的最小配置——满足任一即可构建基线。若穷举后两者均不存在，跳过本阶段直接进入阶段三
3. 寻找基线运行时与 bug 运行时之间的差异：请求参数、配置项、环境变量、代码版本等均可
4. 选定一种差异，消除它，实际运行程序观察 bug 是否消失
5. 逐一消除差异，定位复现 bug 的最小差异集合（即 Delta）
6. 若某次消除差异后 bug 未修复，回到步骤 3 继续循环
7. 若差异集合无法进一步缩小，进入阶段三

每次循环在 `bug{n}-xxx.md` 中追加：

```markdown
# 增量调试法

## 实验1
- 最小复现步骤: 最简测试用例，最低复现成本
- 基线运行时: 构建一种可对比的基线运行方法
- 差异复现集: 选择基线与 bug 之间的差异点
- 实验记录: 消除该差异后，bug 的表现变化
```

---

#### 阶段三：科学实验法

**适用场景**：前两个阶段未能定位根因，需要深入观察运行时状态，沿感染链反向追溯缺陷。

**循环上限：最多 5 次实验循环。** 超过 5 次仍未修复，停止所有尝试，升级人工介入，在 bug 文件中输出「论证无法修复的原因」作为终止记录。

**执行步骤**：

1. 进一步简化复现方法：用更少数据、更少步骤、更少组件缩小复现范围
2. 选择合适的运行时观察工具：添加日志、监控信息、gdb/pdb 等交互式调试工具、profile 工具等；**禁止使用 mock，mock 会遮蔽真实的感染链**
3. 基于观察到的事实，给出错误传播链的解释模型（至少 3 个候选，按可能性排序）：
   - 失败（可观测）→ 异常（中间现象）→ 缺陷（根本原因）
4. 对最可能的解释设计验证实验：「如果假设成立，改动 X 应使 bug 消失」
5. 实际运行程序，以统一的复现方法验证
6. 若 bug 未修复，**回滚改动**，回到步骤 1 重新执行（计入循环次数）
7. 若 bug 已修复，思考：是否是最小改动？是否符合全局架构规范？确认后结束调试

每次循环在 `bug{n}-xxx.md` 中追加：

```markdown
# 科学实验法

## 实验1
- 简化的复现方法: 进一步缩小复现范围，让复现过程更高效
- 观察记录: 观察到何种信息，关键结论记录在此
- 错误传播链: 解释缺陷→异常→失败的逻辑链路（列出至少3个候选）
- 验证方法: 如果缺陷是 xxx，改动 xxxx，若 xxx 则说明 bug 已修复
- 结论分析: 若 bug 已修复则结束并思考最小性；若未修复则回滚改动
```

---

#### 完整 bug 文件结构示例

```markdown
# bug1: 并发场景下数组越界

## 源码推理法

### 尝试1
- 观察: handleRequest 函数中 arr[i] 访问，i 由外部传入，无边界检查
- 假设: 调用方传入的 i 超出了 arr 的实际长度
- 验证: 检查所有调用点的传入 i 值范围
- 结论: 调用方 i 均在 0-3，arr 长度为 5，假设不成立。已回滚（未改动代码）

### 尝试2
- 观察: initArray() 在多个 goroutine 中被调用，无锁保护
- 假设: 并发初始化导致 arr 长度不稳定
- 验证: 代码审查确认 append 在并发下无保护会触发 slice 重新分配
- 结论: 假设可能成立，需要运行时观察验证，进入阶段二

## 增量调试法

### 实验1
- 最小复现步骤: 并发数≥2，运行 TestConcurrentAccess 100 次
- 基线运行时: 单线程串行调用 initArray() 100 次，全部通过
- 差异复现集: 并发 vs 串行 → 并发是唯一差异
- 实验记录: 注释掉并发调用后测试全部通过，确认差异即为根因

## 科学实验法

### 实验1
- 简化的复现方法: `go initArray(); go initArray(); time.Sleep(10ms); assert len`
- 观察记录: 日志显示 `index out of range [5] with length 3`，高并发时段集中出现
- 错误传播链: 缺陷=append 无锁 → 异常=arr 长度不稳定 → 失败=index out of range
- 验证方法: 在 initArray() 加 sync.Mutex，若测试 1000 次全通过则 bug 修复
- 结论分析: 加锁后 1000 次全通过，bug 修复。进一步优化为 RWMutex，性能损耗降至 8%，符合最小改动原则，结束调试

## 结论
- **根因**: initArray() 并发竞态，append 非原子操作
- **修复**: sync.RWMutex 保护，写用 Lock()，读用 RLock()
- **验证**: 并发 1000 次通过，性能损耗 8%（可接受）
- **状态**: ✅ 已解决
```

#### 三阶段的递进关系

```
阶段一：源码推理法（静态，零运行成本）
    上限：3次尝试，每次尝试前 git diff 必须干净
    ↓ 3次未解决
阶段二：增量调试法（有基线对比时优先，缩小差异空间）
    跳过条件：git log 和最小配置中均无法找到可用基线
    ↓ 无法构建基线 或 差异无法继续缩小
阶段三：科学实验法（运行时观察，沿感染链追溯缺陷）
    上限：5次实验循环，超限即停止
    ↓ 修复成功
结论：最小改动 + 符合架构规范
    ↓ 超出总上限（3+5次）仍未修复
升级人工介入：在 bug 文件中论证无法修复的原因，等待人类决策
```

### 要素二：运行时观察工具（第二优先）

方法论决定视角，视角决定需要观察什么，工具提供观察能力。阶段三「科学实验法」的核心能力依赖于此。

没有运行时观察工具，Agent 只能靠推理猜测感染链，而不是真正追踪它。

**实现方向**：

```
科学实验法阶段，允许 Agent 选择观察工具：
  - 在特定位置插入打印语句（临时，commit 前必须清理）
  - 用 delve（Go）/ pdb（Python）等交互式调试器观察中间状态
  - profile 工具分析性能类 bug
  - 执行最小复现脚本验证感染链节点
```

**关键约束**：

- 观察工具必须绑定到具体假设验证，不得随机添加打印语句
- 临时调试代码必须在 commit 前清理
- **禁止 mock**：mock 会遮蔽真实的感染链，debug_skill 明确禁止

### 要素三：关键信息架构（第三优先）

信息不是平等的。`debug/` 目录的设计本身就是对信息架构的优化——每个 bug 独立文件，避免单文件堆积导致上下文混乱。

**信息分级**：

```
不可丢弃（永久保留）：
  - 真实测试运行的输出（实验结果）
  - 已确认有效的线索（「这条线索导致了进展」）

可压缩（保留摘要）：
  - 推理过程（「我认为是Y原因」）
  - 已排除的假设（只需保留结论，不需要完整推理）

可丢弃（清理）：
  - 重复的错误信息
  - 无效的修改记录（已被推翻的假设的操作记录）
```

**存储策略**：

- 真实日志（测试输出、运行时观察结果）→ 完整保留，但在上下文中存**文件路径引用**，不展开内容本身，防止上下文膨胀
- 假设推理 → 存结论（已验证/已排除），不存推理过程
- 每个 bug 文件路径：`debug/bug{n}-{描述}.md`，Agent 加载上下文时通过路径按需读取

---

### 要素四：双层清理机制（第四优先）

单靠记录规范不够——需要主动清理机制，防止混乱度累积。

**设计原则：职责不重叠，时间尺度不同**

```
双层架构：

  ┌─────────────────────────────────────────────┐
  │         dream（战略层，跨 job）               │
  │                                             │
  │  对整个 doing agent 行为轨迹全局反思          │
  │  调整 prompt，提升后续 job 的执行效果         │
  │  时间尺度：跨 job（job 结束后触发）           │
  └─────────────────────────────────────────────┘
                        ↑
              跨 job 模式调整
                        
  ┌─────────────────────────────────────────────┐
  │       review agent（战术层，job 内）          │
  │                                             │
  │  5次实验未解决时触发                          │
  │  基于真实日志反馈判断哪条线索有效             │
  │  压缩无效推理，代码评审禁止 mock              │
  │  时间尺度：job 内（单个 task 调试过程）        │
  └─────────────────────────────────────────────┘
```

两个不同时间尺度的分工：review agent 是战术层，在单个 job 内自动完成，约束 5 次实验还未解决时触发；dream 是战略层，跨 job 全局性地对整个 doing agent 行为轨迹进行反思。两者职责不重叠，也不应混用。

**review agent 的触发逻辑**：

```python
# 伪代码
def run_task_with_review(task):
    for attempt in range(MAX_ATTEMPTS):
        result = run_agent(task, debug_context)
        if result.success:
            return commit_and_done(result)
        
        debug_context.append(result.debug_record)
        
        if attempt == REVIEW_THRESHOLD:  # 例如第5次
            # 触发 review agent
            review = run_review_agent(
                task=task,
                debug_history=debug_context,
                actual_logs=result.actual_test_outputs  # 关键：真实日志
            )
            debug_context = review.compressed_context  # 用清理后的上下文替换
    
    # 超出限制，升级到人工
    human_handoff(task, debug_context)
```

**review agent 的职责**：

```markdown
## Review Agent 输入
- 完整的调试历史（debug.md）
- 所有实验的真实输出日志
- 原始任务描述

## Review Agent 任务
1. 基于真实日志（不是推理），判断哪些线索有实质进展
2. 压缩无效推理：删除已被实验结果推翻的假设
3. 保留感染链模型：维护当前对 bug 位置的最佳估计
4. 代码评审：确保调试过程没有引入 mock（mock 遮蔽真实问题）
5. 输出：精简的调试上下文，供下一轮 Agent 使用

## 终止条件
- 成功：修复通过所有测试
- 失败：论证该 bug 在当前约束下无法修复（边界说明）
  - 技术约束：无法获取足够的运行时观察
  - 设计约束：问题是产品设计缺陷，超出技术调试范围
```

review agent 的核心是：基于真实的实验反馈信息来判断哪条线索是有效的。因此，对真实的日志反馈信息要进行全面的上下文记录，不能丢弃——这是 review agent 进行决策的原材料。真实日志完整保留，但在上下文中存的应该是路径，而非内容本身。

## 七、实现路径与优先级

四个要素的实现成本和收益如下：

```
优先级 | 要素                    | 实现成本 | 预期收益 | 风险
-------|-------------------------|---------|---------|-----
P0     | debug_skill 三阶段 SOP   | 低       | 高       | 低
P1     | 运行时观察工具            | 中       | 高       | 中
P2     | 关键信息架构（debug/ 目录）| 低       | 中       | 低
P3     | 双层清理机制              | 高       | 中       | 中
```

**第一步（立即可做）**：创建 `debug_skill.md`，内聚三阶段调试 SOP（源码推理法 → 增量调试法 → 科学实验法）和 `debug/` 目录记录规范。修改 `doing.md` 模板，将原有工作日志中的 debug 格式替换为加载 `debug_skill`。成本：写一个新 skill 文件 + 修改一个模板文件。

**第二步（一个 sprint）**：设计并实现 review agent。这需要在 `doing` 循环中增加一个中间层，逻辑相对清晰。review agent 读取 `debug/` 目录下的所有 bug 文件，基于真实日志判断有效线索，压缩无效记录。

**第四步（长期）**：dream 机制对调试的优化（当前 dream 已有框架，需要扩展调试反思维度，读取 `debug/` 目录生成跨 job 的调试模式分析）。

## 八、核心假设与风险

**假设一：快速路径假设**
「前3次直觉尝试能覆盖大多数常见 bug 类型」——这依赖于 LLM 的代码理解能力和领域经验积累。对于复杂的并发 bug 或深层架构问题，3次可能远不够。

*风险*：如果 LLM 的直觉尝试质量低，3次快速路径变成了「3次垃圾记录」，科学调试法的输入质量反而更差。需要在实践中观察。

**假设二：假设记录质量假设**
「LLM 能够真实记录自己的推理过程，而不是事后合理化」——LLM 有倾向于「找借口」而非「真实记录」。如果记录的假设是虚假的，整个框架的信息质量前提崩溃。

*风险*：需要设计验证机制——实验结果与记录的假设之间是否一致。这是最高风险项之一。

**假设三：感染链可观察假设**
「通过插入调试语句能够以合理成本定位感染链」——对于某些 bug（Heisenbug、时序 bug），观察行为本身可能改变 bug 的表现（探针效应）。

*风险*：需要 review agent 识别「这个 bug 可能是 Heisenbug」的模式。

**假设四：review agent 清理质量假设**
「review agent 基于真实日志能够有效识别有效线索 vs 无效记录」——如果 review agent 的判断质量低，可能压缩掉真正有用的信息。

*风险*：review agent 本身需要质量保证。可以通过「只压缩已被实验明确推翻的假设」的保守策略降低风险。

**假设五：边界识别假设**
「系统能够正确识别什么是技术调试边界，什么是产品设计问题」——如果系统把产品设计问题也当成技术 bug 来调试，会陷入无法终止的循环。

*风险*：需要在 review agent 中增加边界识别逻辑，或依赖人工介入触发条件。这是最难验证的假设（定义本身模糊）。

**最脆弱假设**：「测试脚本能作为有效质量门禁」——测试脚本有效性假设横跨整个框架。如果测试脚本本身不能准确验收任务，doing 循环的所有自动化都运行在错误的基准上。这是下一个需要建设的执行方向，当前可以悬置，但要意识到它的存在。

## 结语

AI Coding Agent 的调试能力，是整个框架可靠性的核心挑战。

盲目重试的失效不是因为 LLM 能力不足，而是因为框架没有给它提供正确的调试方法论和工具。一个没有接受过调试训练的人类工程师面对复杂 bug，也会陷入同样的无效循环。

核心洞见是：**方法论优先于工具**。先让 Agent 学会「提假设-验证-更新模型」的调试思维，再配合运行时观察工具和上下文清理机制，才能构建真正有效的 AI 调试能力。

最小可行改进只需要一件事：修改提示词，让 Agent 在每次修改前记录「改动了 X，因为我认为是 Y，但结果是 Z」。这一条改动，就能打破盲目重试的恶性循环。
