# skill:super-event-autopsy（super 环境事件流深读法）

## 触发场景

当 super 环境跑完、跑挂、或跑出「看起来很差的统计」时使用。信号词：产出率/invalid 率异常（如「20% 产出率」「93% invalid」）、成本失控、迭代大量空转、`session_ended` 带异常、收尾复盘不知道问题出在哪。

**为什么需要**：job_47 env_11 实证：表面统计「562 迭代 / 20% 产出率 / 93-99% invalid」→ 深读事件流后发现 **68% 迭代是 API 配额空转**（零 token 空跑计入 invalid）——真实工作轮产出率 ≈61%。**不重校准口径，优化方向会指错对象**（把基础设施故障当 agent 失败治）。

## 预期效果

- 一次深读产出：重校准的度量口径 + 失败分类占比 + 结构性根因清单（每条带量化浪费）+ 修复优先级
- 把「诊断」从跑完后看聚合统计，升级为「分析前置」——job_47 后半程单位产出最高的单一实践（一次分析挖出 5 项根因，其中 1 项占 68% 迭代）

## 核心内容

### Step 1：重校准度量口径（先分类，再看数字）

对 `agent_ended` / `iteration_ended` 全量分类，**infra 失败与真实失败分开计**：

```python
# 分类判据（按此顺序判，先 infra 后真实）
# ① infra（配额/断网）：usage.total_tokens==0 且 wall_ms 短（<2000ms）
#    且 summary 匹配配额/网络报错文案
# ② turn_truncated：truncated==true 或 summary 含 [turn-budget-exceeded]
# ③ no_output：tok>0 但无产物（final_message 空 + workdir 无新文件）
# ④ agent_failed：有产出但门禁/契约失败（其余 invalid）
# ⑤ delivered：有候选入格
```

产出**重校准账目**：`真实工作轮 = 总迭代 − infra 空转轮`，然后算真实轮的产出率——这是所有后续结论的分母。**警惕**：跨机器时间线推算可以交叉验证（如「11.8 分钟推进 258 轮 = 2.7s/轮，只有零 token 空转才可能」；决策台账/实验记录里的自述文本是独立证据链）。

### Step 2：失败分类统计 + 每类的「损失当量」

对每个分类不只数次数，还要算**代价**（tokens/cost/wall）——排序修复优先级的依据是代价不是次数：

| 分类 | 统计 | 损失当量 |
|---|---|---|
| infra 空转 | 轮数 × 占比 | 0 token 但污染台账（每个空转轮仍走完整 agent 链 = 纯调度浪费） |
| turn_truncated | 每次截断的 usage 总和 | 截断前烧掉的 token（job_47：单次截断 1.4-2.2M tokens/$1.4-1.7） |
| 代偿链 | 「A 被截断 → B 从头重做」的连锁 | ≈ 2×（同一份工作两份 token） |

### Step 3：结构性根因挖掘（不满足于「agent 失败了」）

对每个高代价分类问「为什么」，直到挖到**结构性**原因（机制级，可修）：

1. **预算 × 协议失配**：回合预算装得下任务吗？——用产物复杂度算术验证（job_47 R2：coding 要「1 文件 + 14-31 测试 + 3 脚本」，24 回合装不下是**算术问题不是纪律问题**）。判据：数典型任务的文件×动作数 ÷ 每回合动作数 = 预算下界。
2. **触发条件是否为「想象中的行为」**：修复逻辑的触发条件在真实事件流里出现过吗？（job_47：JSON 修复条件含 `final_message 非空`，但截断时 final_message=None → **0 次触发**——条件对着想象写，没对数据写。验证法：抓真实 agent_ended 样本看条件字段的分布。）
3. **台账完整性**：阴性结果/同码重测是否被当成新纪录入账？（md5 等价检查缺失 → 幻影 elite。）排序键的方差 vs 要区分的差异（job_47：ref 漂移 ±20.6% > 头三名差异 4.4%——排序不可信。）
4. **知识回写滞后**：决策依赖的快照落后实际几个代次？（处方-基座相位差 → 高权重格按过期处方空转 30-60min。）
5. **停止判据锚在哪**：预算跑道还是「剩余空间 < 测量分辨率」？（近极限区继续迭代 = 期望收益为负。判据：已识别杠杆合计增益 < 同会话噪声带。）

### Step 4：修复建议排序（按 ROI：代价 × 出现频次 / 修复成本）

输出五元组清单：`根因 | 量化浪费 | 修复（机制级） | 预期收益 | 验证方法`。验证方法必须可机器执行（事件流断言，如「outcome=infra_noop 的迭代归零」「json_repair 触发率 >0」）。

### 执行纪律

- **分析独立派发**（researcher subagent / fresh 上下文），不复用跑环境的主会话——主会话有「自己的实现」的立场偏见
- 数据源优先级：`events.jsonl`（唯一真相源）> 决策台账/实验记录（独立证据链交叉验证）> 聚合统计（最后看，只做 sanity）
- 结论必带 **caveat**（样本量/未触发路径/归因不确定性）——job_47 成本对比的归因 caveat（2 迭代未触发 adjust，保守估计）是范例

## 真实案例（job_47 env_11）

- 输入：562 迭代 / 18140 事件 / 表面 20% 产出率。
- Step 1 重校准：≈380 轮（68%）是配额空转 → 真实轮 ≈180，产出率 **61%**。
- Step 3 根因五项：R1 熔断缺失（68% 空转）/ R2 预算×协议失配（截断→JSON 修复不触发→debug 全量代偿 2×）/ R3 幻影 elite / R4 处方-基座相位差 / R5 停止判据锚错。
- 修复全部落地（task57-59，outcome 五态分类 + 产物抢救 + md5 等价 + method_stale + 噪声标定），gate29 全绿验证。
- **配套框架钩子**：修复后调度器在每个 `iteration_ended` 带 `outcome` 五态字段，`cost_report.py --workdir <ws>` 直接按分类分列——让下一次深读不用重写分类逻辑。
