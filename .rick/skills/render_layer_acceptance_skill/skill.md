# skill:render-layer-acceptance（渲染层改动的真渲染验收纪律）

## 触发场景

前端**渲染层结构性改动**（虚拟化/列表重写/Provider 提升路由层）完成 gate 检查、准备提交或 release 前使用。信号词：
- gate（typecheck+build+静态断言）全绿，但改动涉及运行时组件协议/DOM 结构/Context 拓扑
- 改动是「重写渲染路径」而非「加样式/加文案」
- 项目无前端运行时测试（无 Playwright/单测），gate 只能做静态断言

## 预期效果

- 拦截「静态断言绿但运行时崩」类 P0 于 dev 阶段（job_43 实证：Virtuoso Scroller 丢 props，gate4 七项断言全绿，上线即全空白——用户报告才发现）
- 渲染层改动的事故率从「用户发现」前移到「dev 验收发现」

## 核心内容

**验收清单（渲染层改动 → dev UI 真渲染 → 才能 release）**：

1. dev 实例起最新构建：`rick tools dev-web restart`，curl 首页确认新 bundle 文件名（`index-*.js` 已变）
2. **打开真实页面走一遍主路径**（不是 curl 200 就完）：
   - 列表/消息类：内容真的渲染出来（非空白）、滚动可用、展开/收起可用
   - 交互类：点击产生预期状态变化
   - Context 提升类：原入口与新入口都触发同一目标
3. 静态断言的边界写进 gate 注释：「本 gate 不覆盖运行时协议破坏」——让下一个迭代者知道必须补真渲染验收
4. 事故模式（供对照）：用户报告「页面空白/点了没反应」+ 刚上线的渲染层改动 = 第一嫌疑就是它，立即 diff 该层最近 commit

**为什么 curl 不够**：SPA 首页 200 只证明 bundle 可达，不证明 React 树能挂载——渲染协议错误发生在 JS 运行期，只有真渲染能暴露。
