# skill:super-debug-protocol（debug：复现 → 用户手册调研 → 三假设验证）

> 服务对象：**debug agent**（super 调度的修复者/复验者）
> 加载方式：debug 提示词声明路径 + 触发条件；进入 debug 时 `read` 本文件
> 方法论 canon：`internal/prompt/templates/skills/debug_skill.md`（六阶段调试体系）——**必须按需 read 该文件**；本文件规定 super 场景的落地方式

## 触发场景

四类触发（任一命中即进入 debug）：

1. **自检失败**：coding 的自检未通过（同 agent 内循环，attempt 1..M）
2. **框架门禁失败**：`gate_check` 拒（stage2 正确性 / stage3 性能 / soft_gate）
3. **异常收益复验**：门禁通过但 perf 提升 ≥ `debug_policy.gain_threshold_pct`（默认 20%）——防作弊/误测的结论进精英地图被遗传
4. **容差带复验**：软门禁容差带内（无明显收益）且 `debug_policy.recheck_tolerance_band=true`——避免有潜力的解被过早扼杀、无收益解混入

信号：ctx 有 `gate_failure`（failure_stage/metrics/details）或 `perf_gain_pct`/`recheck_reason`。

## 预期效果

- **真失败**：给出根因 + 最小修复（复跑门禁验证通过），或确认「当前技术路线下无法修」
- **假失败/潜力解**：给出反证（实验实际上成立，如之前是测量噪声/参数误用），`verdict: keep_original`
- **异常收益**：确认真实性（排除作弊/测量偏差）或揭露作弊
- 结论全部**回写实验记录**「执行过程与结论」段——让 adjust 下一轮能看到「这里失败过、根因是什么」

## 核心内容

### 流程（canon 六阶段的 super 落地）

#### 第 1 步：复现

- 用 env 的 `verify` / `benchmark` / `gate_check`（ctx 的三要素命令）**复现失败读数**；至少 2 次读数确认非测量噪声
- 记录：失败阶段、读数、与基线（`perf_baseline`）的差距
- 若无法复现（时过境迁/噪声）→ 直接进第 4 步的判断（`keep_original` 的候选结论）

#### 第 2 步：research 用户手册（关键组件是否正确使用）

- 按 ctx `research_brief`（focus=该域关键组件的用户手册与正确用法）检索：**参数含义 / API 约束 / dtype 转换 / 派发条件 / 已知坑**
- 目标：确认「工具是否被正确使用」——**很多「性能差/正确性错」其实是误用 API 或参数没调好**
- 把「可能是误用」写成候选（进入第 3 步）

#### 第 3 步：三假设法（禁止只给一个）

提出**三个最可能的失败原因**，每个写明：

```markdown
### 假设 {1/2/3}（优先级 高/中/低）
- **假设**：<一句话根因猜测>
- **若成立应观察到什么**：<可验证的观察——具体读数/现象>
- **验证方式**：<跑什么命令 / 改哪一处做对照 / 看哪个日志>
```

然后**逐一验证**（不是一次性全改）：每次只验证一个，记录观察结果：

- 观察符合「若成立应观察到什么」→ 根因锁定
- 不符合 → 排除，进下一个
- 三个都排除 → 见第 4 步

#### 第 4 步：修复 / 维持

- **根因锁定** → 最小改动修复（不改实验意图、不改 env 定义）→ 复跑 `gate_check` 验证 → 通过则交付修复后的候选
- **三假设都排除** → 说明「失败结论可能不可靠」：
  - 若失败源于测量噪声/环境抖动 → `verdict: keep_original`（保留原候选，附证据：两次以上读数波动范围）
  - 若确认为真实失败但无法修 → 如实汇报 `final_self_check.passed=false` + 根因结论（让调度器记录失败，比硬修一个错方向更有价值）

#### 第 5 步：回写实验记录

在 ctx 的 `experiment_record_path` 指向的实验记录文件「## 6. 执行过程与结论」追加：

```markdown
### debug 记录（attempt {N}，触发：{自检失败|门禁失败|异常收益|容差带}）
- 复现：<读数×2+基线对比>
- 三假设与验证：<假设1→观察→结论；假设2→…；假设3→…>
- 根因：<…>
- 处置：<修复内容 / keep_original + 理由>
```

### 异常收益场景的特别提示

收益异常高（如 >2× 参考实现）**首先怀疑作弊/测量偏差**，按顺序排查：

1. 预存结果（硬编码/查表/缓存返回）
2. 篡改计时（计时窗口外计算/异步返回/改 benchmark 逻辑）
3. 降精度换速度（超容差的精度损失）
4. 拖慢参考实现（后台忙循环抢 CPU / 污染 ref 缓存）

用 `gate_check` 与 env 的 exploit 注册表口径复核；确认作弊 → 拒绝并记录证据。

### 纪律（canon 铁律）

- **没有根因调查，不得提出任何修复方案**；症状修复是失败，随机修改是制造新 bug
- 一次只改一处（保持归因）；修复后必须复跑门禁
- 不改 env 定义（门禁脚本/容差/特征空间）；不改实验假设（那是 builder 的职责）
- 三个假设必须**真的不同**（同一根因的三种说法 = 无效）
