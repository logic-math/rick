## 二、逐项评估

### ① 冗余动作

**R1：白名单三层设计（task10）→ 两轮后被整体拆除（task13）——本次最大流程冗余**

事实链：research-I5 的 F1 推荐是「白名单加入 dev worktree」（最小扩展）；实际 task10 做成了「全注册 workspaces + ~/.rick + ExtraFileRoots（组合根注入+env 覆盖+cwd 推导）」三层机制；迭代 6 human 一句「不要搞特殊逻辑」整体推翻。

冗余分析：
- **设计期**：F1（最小改动）与 task10（三层机制）之间有一次未与 human 确认的复杂度跃迁——research 推荐的是「加一个根」，task 做成了「根列表机制 + 注入管线」。若当时按 F1 最小方案做，迭代 6 的拆除面缩小 70%。
- **裁决期**：「要不要路径白名单」本质是**安全边界的产品裁决**（涉及部署模型：单用户局域网 vs 多租户），不是实现细节。它在迭代 5 的 S4 呈批中以「安全面变化：文件读取从当前工作区扩展到所有已注册工作区」一句带过——human 批准时未必意识到自己在给「白名单范式」背书。直到迭代 6 human 主动问「后端白名单是什么」才发现根本分歧。
- **可预防**：grilling 阶段（增量 5 的需求澄清）应把「读取范围的安全模型」作为显式判断节点上呈（两案：白名单根列表 vs 开放读取+token 认证，各附安全面与复杂度对比），而不是默认沿用现状（已有白名单）做增量扩展。**判断节点吞没**的典型样例——实现者惯性选择了「在既有范式内做最小合理改动」，而用户的心智模型是「简单直接」。

**R2：dev UI 真渲染验收通道的建立时机**

迭代 2 的 task7 上线前只验证了 typecheck+build+静态断言——dev 实例（8414）当时已在跑（S1 restart 过），但**没有要求 human 在 dev UI 上看过消息渲染**。真渲染验收纪律在 P0 之后才建立（迭代 3 起每次执行）。这是一次「流程纪律滞后于风险等级」：虚拟化是「重写渲染层」的高风险改动，本应在 task7 的 plan 阶段就标注「验收必须含 dev UI 真渲染」。

**R3：release.md 头部三行两次丢失（L5/L7 小冗余）**

两次都是「python 字符串切片重构 release.md 时把头部三行（version=/rollback_point=/released=）切掉」——rsi_check 的 rsiVersionRe 取第一个 version= 行，头部丢失即红。低级但重复两次，说明：证据文件的结构性依赖（头部三行）没有模板化保护，靠记忆维护。

### ② 可预防错误

**E1：P0（L1）——gate4 静态断言的盲区 + 验收流程缺口的复合**

- gate4 断言了「import Virtuoso / followOutput / computeItemKey 存在」——这些是**存在性断言**，测不到「props 转发缺失」这类**协议性破坏**（自定义 Scroller 只解构 {style, children} 在类型上完全合法、在静态上完全无痕）。
- 缺口位置精确定位：**S1 收尾（dev-web restart 后）到 S3 演练之间**——正确插入点是「层检查点（level_complete）通过后、S4 呈批前」，由 parent 在 dev UI 上做一次会话消息渲染冒烟（或要求 human 验收前先看 dev）。当时流程直接从 gate4 绿 → commit → S3 → S4。
- 修复成本对比：dev UI 上人眼看一次消息列表 = 30 秒；实际代价 = 用户遭遇生产全站故障 + 热修复 + 额外 release + 信任成本。
- **同类风险的预防面**：任何「第三方库接管渲染/滚动/事件」的改动（虚拟化、拖拽库、路由迁移）都有 props/事件协议破坏风险，静态 gate 天然测不到——这类 task 的验收标准必须含运行时冒烟。

**E2：gate7 的 RICK_STATE_DIR 环境穿透（L6）**

- 根因：gate 以 `subprocess` 继承 pi 会话完整环境跑 `go test`，而 `internal/cmd` 的 4 个 web 单例测试用 `t.Setenv("HOME", t.TempDir())` 隔离——但 `RICK_STATE_DIR`（pi 会话环境里存在）优先级高于 HOME 推导，穿透隔离读到真实 `~/.rick/web.pid` 撞生产单例。
- 可预防点：gate 设计期（写 gate7.py 时）若预见到「测试进程会继承宿主环境」就该统一净化；实际上 gate1-gate6 都没踩中纯因运气（那些测试此前未与生产实例同时激活过——不，实际是 gate1 跑过 internal/cmd 且当时生产也在跑……差异在 RICK_STATE_DIR 是否在环境里，pi 会话的 env 不是稳定集）。
- 改进：**所有 gate 的 go test/npm 调用统一剥离 RICK_* 前缀变量**（已作为 gate7 的修正落地）；更彻底的做法是在测试代码内 `t.Setenv("RICK_STATE_DIR","")` 固化（遗留清单第 6 条）。

**E3：ACL 权限重置的重复应对（环境类，非流程错误）**

两次权限重置（job_43 doing 目录、dev HOME）用同一招（父目录可写 → rename + 重建）处理，第二次已经是「按剧本执行」——这属于环境风险的模式化应对，建议提炼为 skill（见 Step 3 输入）而非视为错误。

### ③ 更短路径

**S1：迭代 2+3 可合并——虚拟化 task7 若初始就含 Footer，省一整轮迭代（L3）**

- 事实：task7 重写 MessageList 时，旧实现的滚动容器 `py-3`（上下 12px padding）随重写消失——Virtuoso 自管滚动区，容器 padding 不进其计算。贴底间距在迭代 3 才由 task8（Footer spacer 12px）补回。
- 更短路径：task7 的「实现要点」若包含一项**视觉等价清单**（「旧渲染的 px-4 横向 padding / py-3 上下间距 / 空态样式在 Virtuoso 布局下的等价实现——间距可走 components.Footer/Header」），worker 一次做对，迭代 3 整轮（task+gate+release+挂起恢复）可省。
- 泛化：**重写类 task 的 plan 应附「行为/视觉等价清单」**——重写的风险恰恰在「无声丢失旧行为」（本例：间距；另一个近似例子：task6 的第 5 处 blur 也是首轮盘点漏项）。

**S2：迭代 5+6 可合并——若 grilling 问透安全模型（R1），task10 直接做成 task13 的形态**

- 若增量 5 的需求澄清阶段把「读取范围安全模型」作为判断节点上呈（白名单 vs 开放读取），human 在当时就会说出「不要搞特殊逻辑」——task10 的三层机制、gate7 的白名单断言、相关测试全都不必写，迭代 6 整轮（含 release）并入迭代 5。
- 节省估计：1 个 task 的实现+测试（task10 约 150 行 Go+测试）、1 轮 gate 设计、1 次 release 周期、human 一次「理解白名单是什么」的认知成本。

**S3：次要短路径**

- release.md 的维护若用「头部三行 + 正文追加」的固定模板（或每次 append 而非 rewrite），L5/L7 两次返工可免。
- job_43.locked 误提交：`git add -A` 前先 `git status` 复核（或 add 指定路径），L7 可免。

## 三、损失最大的 2 个点——具体改进建议

### 改进建议 1（对应 L1/E1/S2）：「高风险渲染层改动的运行时验收」硬门禁化

**问题**：P0 事故的根因不是技术（props 转发是常识级疏漏），而是**流程缺口**——高风险改动走了与普通改动相同的验收路径（静态 gate + 构建产物检查）。

**具体改进**（三层，按落地成本递增）：

1. **task plan 模板增加「风险分级」字段**：task 文件头部标注 `风险: 渲染层重写|数据层|样式|文案`。渲染层/滚动接管/事件代理类 task 的「测试方法」节**必须**包含「dev UI 真渲染冒烟清单」（本例：会话打开/消息可见/滚动/贴底/展开/间距 6 项，30 秒人眼可完成）。
2. **S4 呈批模板增加前置条件**：凡本轮含「渲染层重写」级 task，S4 呈批文案必须附「human 已在 dev UI 完成冒烟验收」或明示「本轮跳过真渲染验收」——把跳过变成显式决策而非默认遗漏。
3. **Step 3/4 沉淀为 skill/loop**（本次 learning 产出）：`dev-ui-verification` skill（渲染类改动的冒烟清单模板 + 各检查项 30 秒操作指引）与（可选）`web-feedback-iteration` loop 中把「渲染冒烟」写为 S4 前的固定步骤。

### 改进建议 2（对应 L2/R1/S2）：「安全边界/范式类产品决策」的 grilling 强制上呈

**问题**：白名单建了又拆暴露的不是代码问题，而是**判断节点识别失败**——「读取范围受不受限」是产品范式决策（部署模型的一部分），实现者惯性地在既有范式内做增量，用户范式认知不同，一轮后才暴露。

**具体改进**：

1. **grilling 提炼判断节点的分类词表**：涉及「权限/范围/安全边界/数据流向/范式（白名单 or 开放、配置 or 硬编码、抽象层级）」的决策点，**不得**作为实现细节自行选择——必须以两案对比（各自复杂度+安全面+可逆性）上呈 human。本次的教训句式：「在既有范式内做最小合理改动」不等于「用户认同该范式」。
2. **research 简报的修复方案（F1/F2/F3…）每条标注「范式保持 or 范式变更」**：F1 是范式保持（白名单内加根），「开放读取」其实是未列出的第四选项——方案清单未覆盖范式空间，用户只能在给出的子集里选。研究阶段就应把范式轴展开。
3. **S4 呈批的「安全面变化」条目升级为显式问句**：本轮涉及安全面变化时，呈批文案改为「本次将读取范围从 X 扩到 Y（范式：白名单）——您要的是白名单还是不要限制？」——把范式确认前置到放行点。

## 四、对 Step 3/4 的输入建议（可提取的技能/循环）

基于上述评估，Step 3 的 skill 候选优先级：
1. `dev-ui-verification`（改进建议 1 的核心，P0 教训的流程化）
2. `security-paradigm-decision`（改进建议 2 的核心，判断节点分类词表+两案上呈法）
3. `render-rewrite-equivalence`（S1 的核心，重写类 task 的行为/视觉等价清单法）
4. `acl-permission-recovery`（E3 的模式化应对：rename+重建法，两次实战验证）
5. `rick-release-lan-ops`（release 实操：RICK_RELEASES_DIR 布局/detach/跨休眠/生产接管对齐）

Step 4 的 loop 候选：`web-feedback-iteration`（human 验收反馈 → grilling 增量澄清 → task/gate → dev UI 验收 → S4/S5 → 挂起恢复的 6 轮实战模式，含上述两个改进建议的固化步骤）。

## 五、结论

本次 job 的 13/13 task 成功率与 6 次 release 的交付节奏是「流程正确性」的成功；但 P0 事故与白名单往返暴露的是「流程**完整性**」的两处系统性缺口：**高风险改动未匹配高强度验收**（改进建议 1）、**范式决策未被识别为决策**（改进建议 2）。两者都已具备低成本、可模板化的修正方案，建议全部沉淀进 Step 3/4 产出。
