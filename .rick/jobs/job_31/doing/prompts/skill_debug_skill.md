# skill:debug-skill（diagnosing-bugs 六阶段调试体系）

## 铁律

```
没有根因调查，不得提出任何修复方案。
症状修复是失败。随机修改是制造新 bug。
```

**声明触发**：遇到任何非预期行为，必须先声明：
> "I will use skill:debug-skill."

声明后，严格按照准备阶段 → Phase 1 → Phase 2 → Phase 3 → Phase 4 → Phase 5 → Phase 6 顺序执行，**不得跳过**。

---

## 准备阶段：debug/ 目录与文件约定

### 目录创建

在**当前工作目录**（项目根目录）下创建 `debug/` 目录：

```bash
mkdir -p ./debug
```

### Bug 编号规则

- **全局递增**，不按 task 重置
- 扫描 `./debug/bug*.md` 找到最大编号 N，下一个用 N+1
- 文件命名：`bug{n}-{简要描述}.md`（例：`bug3-concurrent-race.md`）

### bug*.md 文件格式规范

每个 bug 文件**第一行**必须是 YAML frontmatter，正文用以下七个 `##` 二级标题分节：

- `## Phase 1: 构建反馈回路`
- `## Phase 2: 复现最小化`
- `## Phase 3: 可证伪假设`
- `## Phase 4: 插桩观察`
- `## Phase 5: 修复回归`
- `## Phase 6: 清理事后分析`
- `## 结论`

**必填字段**：
- `summary`：一句话描述根因 + 最终状态（例：`"nil pointer dereference in parseTask，已通过空值检查修复"`）
- `status`：当前状态

**合法状态值**：
- `"✅ 已解决"` —— bug 已修复，测试全部通过
- `"🔄 进行中"` —— 调试进行中（仅临时状态，最终必须转为已解决或无法修复）
- `"❌ 无法修复"` —— 有扎实论证说明 bug 在当前约束下无法修复，需要人类决策

**终止状态约束**：任何 bug.md 最终必须以以下两种状态之一结束，**不得悬置**：
1. `status: "✅ 已解决"` —— bug 已修复，测试全部通过
2. `status: "❌ 无法修复"` —— `## 结论` 章节包含扎实论证，不可空置

---

## Phase 1: 构建反馈回路

**目标**：初次复现 bug，追求最小化复现路径，获得秒级可重复运行的测试。

### 触发 review debug agent：建立假设时

在 Phase 1 建立假设时，启动 **review debug agent**（subagent）：
- 输入：相关源码 + 测试输出 + 已有 debug 记录
- 任务：大范围读取源码，输出假设列表（每条包含观察证据 + 推断 + 建议）
- **角色约束**：只输出分析，不执行任何改动，不写文件，输出后即退出
- 详见下方「review debug agent 协议」章节

### 执行步骤

```
1. 运行失败的测试，记录完整错误信息
2. 构造最小可复现路径（最少依赖、最短代码路径）
3. 确认：该测试可在 <5 秒内稳定复现
4. 记录复现步骤到 ## Phase 1 章节
```

---

## Phase 2: 复现最小化

**目标**：基于 Phase 1，进一步裁剪到最小可复现单元。

### 执行步骤

```
1. 检查 git log 历史：是否存在"当前 bug 不存在"的最近提交？
   → 找到：该 commit 为基线，运行 git bisect 或手动 checkout 确认
2. 无历史基线：能否构造"最小配置"让 bug 消失？
   → 找到：该最小配置为基线
3. 记录最小复现单元到 ## Phase 2 章节
4. 若无法进一步最小化，直接进入 Phase 3
```

---

## Phase 3: 可证伪假设

**目标**：生成 3-5 个有优先级排序的可证伪假设。

### 触发 review debug agent：生成假设时

在 Phase 3 生成假设时，启动 **review debug agent**（subagent）：
- 输入：测试输出 + 源码 + Phase 1-2 记录
- 任务：产出 3-5 个有优先级的可证伪假设（每条包含观察证据 + 推断 + 建议验证方法）
- **角色约束**：只输出分析，不执行任何改动，不写文件，输出后即退出

### 假设格式

```
### 假设 {N}（优先级 {高/中/低}）
- **观察证据**：[从源码/错误信息中观察到的事实]
- **推断**：[基于证据的逻辑推断]
- **验证方法**：[最小可证伪步骤]
```

### 执行步骤

```
1. 触发 review debug agent，收集假设列表
2. 按优先级排序（最可能根因排第一）
3. 记录到 ## Phase 3 章节
4. 进入 Phase 4 逐一验证
```

---

## Phase 4: 插桩观察

**目标**：log/gdb/delve/pprof 等均视为桩，选最合适的插入关键路径。

**上限：3 次尝试**；超过 3 次进入 Phase 5 前置修复或升级观测手段。

### 运行时观察工具

**AI 自行安装使用，禁止 mock**：

| 语言 | 工具 | 安装方式 |
|------|------|----------|
| Go | delve | `go install github.com/go-delve/delve/cmd/dlv@latest` |
| Go | pprof | 内置，`import _ "net/http/pprof"` |
| Python | pdb | 内置，`import pdb; pdb.set_trace()` |
| Python | py-spy | `pip install py-spy` |
| 通用 | strace/ltrace | 系统工具，`sudo apt install strace` |

### 执行步骤

```
FOR each attempt (max 3):
  ASSERT: git diff == clean
  1. 基于 Phase 3 优先级最高的假设，选择观测工具
  2. 明确声明："我将验证假设 [X]，使用 [工具+手段]"
  3. 在关键路径插入桩（log/断点/pprof）
  4. 运行测试，收集观测数据
  5. 判断：
     - ✅ 确认根因 → 进入 Phase 5
     - ❌ 假设排除 → git checkout . 回滚，记录，尝试下一个假设
  6. 3 次仍未确认 → 升级观测手段或触发 review debug agent 重新分析
```

---

## Phase 5: 修复回归

**目标**：基于确认的根因，最小改动修复，全量测试通过。

### 执行步骤

```
1. 确认根因（基于 Phase 4 观测数据）
2. 明确声明："根因是 [X]，修复方案是 [Y]"
3. 做最小代码改动（不引入额外逻辑）
4. 运行全量测试：
   - ✅ 全部通过 → 进入 Phase 6
   - ❌ 部分失败 → 检查是否引入回归，返回 Phase 4 继续观测
5. 记录修复过程到 ## Phase 5 章节
```

---

## Phase 6: 清理事后分析

**目标**：移除临时桩，写 bug*.md 结论章节，提炼防范模式。

### 执行步骤

```
1. 移除所有临时插桩（log 行、断点注释、调试代码）
2. 运行测试确认清理后仍然通过
3. 完善 bug{n}-xxx.md：
   - 更新 ## Phase 6 章节（清理了什么）
   - 写 ## 结论 章节（根因 + 修复 + 防范模式）
   - 更新 frontmatter status 为 "✅ 已解决"
4. 提炼本次 bug 的防范模式（如有），供后续参考
```

### 超限处理（Phase 4 超过 3 次 + Phase 5 仍失败）

**停止所有尝试**，执行以下操作：

1. 在 `## 结论` 章节写入（不可空置）：
   - **已尝试的方法**、**已排除的假设**（含排除依据）
   - **当前约束与边界**、**建议人类决策的方向**

2. 更新 frontmatter：`status: "❌ 无法修复"`，`summary` 写明根因无法定位的原因

3. 向人类呈现 bug 文件路径，等待人类决策。

## review debug agent 协议

### 定义

review debug agent 是在调试特定触发点由主 Agent 启动的 subagent，职责是**深度分析**，不执行任何修改。

### 启动时必须加载 SENSE 方法

agent 启动后**立即**读取：

```
{{sense_skill_path}}
```

按 **S → E → N** 三阶段结构化分析 bug 信息后再输出假设，保证假设有 SENSE 方法论支撑：
- **S（Subject）**：还原问题现状、期望、差距
- **E（pErspective）**：多视角分析根因候选，逆向追踪数据流
- **N（judgmeNt）**：为每个假设提供可证伪的验证方法

### 输入

- 相关源码片段（调用链上的关键文件）
- 测试输出（完整错误信息和堆栈）
- 已有 debug 记录（`./debug/bug{n}-xxx.md` 已记录内容）

### 输出格式

每条假设包含三个字段：

```markdown
### 假设 {N}
- **观察证据**：[从源码/错误信息中观察到的事实]
- **推断**：[基于 SENSE S→E→N 的推断]
- **建议验证方法**：[最小改动或最小复现步骤]
```

### 角色约束

- ✅ 只输出分析和假设列表
- ✅ 可以读取文件（源码、测试输出、已有 debug 记录）
- ❌ 不执行任何改动
- ❌ 不写入任何文件
- ❌ 不运行测试
- ✅ 输出假设列表后即退出

## 反模式（遇到立即停止）

| 反模式 | 正确做法 |
|--------|----------|
| 没形成假设就随机修改代码 | 先触发 review debug agent，再基于假设改动 |
| 叠加修复：第一个没用直接加第二个 | 一次一个假设，失败则 git checkout . 回滚 |
| 修复症状（捕获异常/加 if）而不是根因 | 追踪到根因再修复 |
| 每次尝试前不检查 git diff | 每次尝试前必须确认 git diff 为空 |
| bug.md 不写 frontmatter | frontmatter 是 Rick 框架读取的唯一来源，必须写 |
| bug.md 以 "🔄 进行中" 状态结束 | 必须转为 ✅ 已解决 或 ❌ 无法修复，不得悬置 |
| 超限后继续尝试 | 超过 Phase 4 的 3 次上限立即停止，写结论，等人类 |
