## 1. 前端产物投放（只改前端可不重启）
**结论**：可行，且已是现机制。StaticHandler 每请求判断覆盖层优先级（`internal/web/static.go:63-71`：`os.Lstat(overrideDir/index.html)` 存在则整树用覆盖层，否则 embed baseline；注释 `:25-27` 明确 all-or-nothing）。watchFrontend 每 2s 轮询（`internal/web/watcher.go:33` watcherInterval）、稳定 500ms 后发 frontend_reload（`:36`），抖动 >5s 强发（`:85-90`）。前端收到即 `window.location.reload()`（`web/src/api/sse.ts:422-427`，按 seq 去重防重放循环 `:339-348`）。实测覆盖层正生效：`md5sum ~/.rick/web/dist/index.html` = `web/dist/index.html` = 4bea9323…，而 `bin/rick` 内嵌 baseline 只在重编译时更新（`web/embed.go:35-36` go:embed all:dist）。
**回滚**：`rm -rf ~/.rick/web/dist`（即时回内嵌 baseline）；勿依赖 `/api/web/reset`——它走 env.ResetWebCustomization 且会连 src/与根配置一起删（`internal/cmd/web.go:180-210`）。confidence 0.95。待验证：覆盖层被删除期间浏览器是否停在旧 assets（index.html no-cache，`static.go:44-46`，理论无影响）。

## 3. 门禁现状
gate1-6 均为 python 脚本，逐层查「go build ./... + 该层包 go test -run Xxx + 文件存在性 + 前端 tsc/npm run build」，gate1 额外查 Makefile 含 web-dist（`gate1.py` 尾），gate2-4 查 `pgrep -f '[m]ode rpc'` 残留 pi 进程，gate4 查 dist 有 manifest，**gate5 唯一做 `go build -o bin/rick ./cmd/rick` 并跑 `bin/rick web --help`/customize/reset**，gate6 是真 E2E：以 `HOME=<tempdir>` 起真实服务（--port 16374 --token e2etest-token），验 401/静态/SPA fallback/工作区注册/jobs/SSE server_info/SIGINT 后 web.pid 清理。输出统一 `{"pass":bool,"errors":[...]}` + exit code。tasks.json 字段：version/created_at/updated_at + tasks[]{task_id,task_name,task_file,status,dependencies,attempts,created_at,updated_at,commit_hash}，job_36 全 15 个 task `status:"success"`。仓库无统一 test 入口：`Makefile` 只有 web-dist/web-dev，`web/package.json` scripts 仅 dev/build/typecheck。实测 `go test ./...` → 全 ok，EXIT=0（本次约 60s，多为 cached）。confidence 0.95。

authWrap = `TokenAuth(token)`（`internal/web/routes.go:62-64` → `auth.go:29-50`）：`Authorization: Bearer`，无 header 时回退 `?token=`（EventSource 用，`routes.go:904-905`）；token 来源 flag>config.web_token>自动生成（`internal/handler/web.go:153-172`，现 config 值 `c2f268ce…`）。**豁免仅 `/api/health`（无 authWrap）与 `/` 静态**（`routes.go:849,908-909`）。**全仓无任何 approve/approval 语义**（`grep -rni approve internal/` 无命中；前端无 `window.confirm`，grep 无命中）。最接近的现有模式：CLI `rick web reset` 的 `[y/N]` 交互（`internal/cmd/web.go:192-210`）与 `POST /api/web/reset|customize`（`routes.go:901-902`，无确认体、仅 token）。→ 提升确认建议做成「需 approval token 的一次性 POST」而非复用现有模式。confidence 0.9。

## 5. 端口与状态隔离（最关键）
**无任何 --state-dir/隔离开关**：`rick web` 仅 `--port/--listen/--token`（`internal/cmd/web.go:65-67`）。状态全按 HOME 解析：WebStateDir=`$HOME/.rick/web`（`internal/web/web.go:25`）、WebConfigPath=`$HOME/.rick/web.json`（:34）、SessionsPath（:44）、PidPath=`$HOME/.rick/web.pid`（:63）；`internal/env/web.go:32` 同款。单例只靠 pid 文件 + `kill(pid,0)`（`internal/handler/web.go:117-149`），**pid 文件不与端口绑定**，且是「建议式」锁（无 flock）。
**实测异常**：`ls -la ~/.rick/` 无 web.pid（`find ~/.rick -maxdepth 1 -name '*.pid'` 空），而 pid 172761 在跑 → **当前单例判活是失效的**（文件缺失时 checkSingleton 直接放行，`handler/web.go:132-134`）。原因未定（推测：曾有一次启动竞争删了 stale pid 文件，或当前进程的 pid 写在别处），confidence 0.6，待验证。
**同 HOME 双实例冲突点**：① sessions.json 双写互相覆盖（`registry.go:102-125` 全量 save）；② 新实例 ReconcileOnStart 把所有 active/running 会话改成 error 并落盘（`sessions.go:158-173`）→ 会污染生产会话态；③ overlay 是 HOME 级共享（static.go 每请求读 `$HOME/.rick/web/dist`）→ dev 构建/git 产物直接改到生产前端；④ watcher 双份轮询同 workspace 的 tasks.json，各自向各自 hub 发 jobs_update（不互相污染，但重复 IO）。唯一现成的隔离手段 = **HOME 覆盖**（gate6.py 用的就是这招，`e2e_home=tempfile.mkdtemp()` + 显式 --token），代价是工作区注册表、pi agent dir、config token 全部另起一套。confidence 0.9。

## 6. 后台任务（doing/dream）
doing 会话 = 服务进程内 goroutine 跑 `handler.DoingIn`（`sessions.go:464-470,482`，默认实现 `:108-111`），状态直接置 `running`（:474）；重启时进程死 = goroutine 死，ReconcileOnStart 一律标 error「server restarted: background task lost」（`sessions.go:162-167`），且 **SessionResume 明确拒绝 doing**（`sessions.go:1018-1020` 409 "monitor-only; re-run via a new doing session"）。tasks.json 状态取值实测只有 `success`（job_36 15 个），代码/测试隐含 `pending|running|success`（`internal/handler/core_test.go:223-229`；`doing.go:160,357` 以 `!= success` 判未完成）。重启后的不一致体现在三处：① sessions.json 里 doing=running→error；② tasks.json 若被中断会留下 running（确定性门禁把它叫 "zombie running"：`.rick/skills/rick-gates/helper.py:47-49`，doing.go:227 注释同款语义）；③ **孤儿 pi 进程**：doing 的 pi 用 `exec.Command` 启动、无 Setpgid 也不绑 ctx（`internal/runtime/runtime.go:140-158`，`cmd.Wait()` 阻塞），而 ShutdownWorkers 只收 supervisor 的 rpc worker（`server.go:130-137` → `sessions.go:1745-1752`），所以 `job` 的 pi 子进程在服务死后仍会继续跑并写 tasks.json/commit。confidence 0.85（③ 的 pi 侧 EPIPE 行为待实测）。
