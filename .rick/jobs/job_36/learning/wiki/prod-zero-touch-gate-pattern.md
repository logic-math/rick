# 生产零触碰门禁模式（prod-zero-touch gate pattern）

**适用场景**：任何会在「与生产共存」的机器上跑的自动化验收（门禁/E2E/演练）——尤其当被测系统本身就是生产系统的一部分。

## 模式

1. **只读生产**：测试的一切写操作都发生在 `t.TempDir()` / 临时端口 / 临时 HOME；生产只做**读**（API 查询、指纹）。
2. **首尾指纹断言**：门禁开始时记录生产关键状态文件的 md5（如 `web.json`、`sessions.json`），结束时比对 —— 不变才算过。
3. **健康断言**：结束前 `GET /api/health` 必须 200（防「测试成功但把生产搞挂了」）。
4. **模拟生产**：需要验证「会改动生产」的路径（如 release/重启/换链）时，用 `t.TempDir()` 造一个结构等价的假生产（repo+home+端口+start 脚本+假健康端点），**参数化注入**（如 `--prod-repo/--prod-home/--port`），绝不在真实生产上跑。
5. **无副作用断言**：「安全演练」类命令（dry-run）要显式断言它没写生产树（如 `bin/releases` 不得出现）。
6. **实现里禁写字面量**：生产端口/路径不得硬编码在被测实现里（门禁 grep 检查），强制参数化。

## 本模式的实证（job_36）

- 14 道门禁全部带「prod 指纹 + 健康」断言；两份 E2E 输出 `prod_touched:false`。
- 该模式抓到 3 个真实缺陷：dry-run 把构建产物写进生产树（F3）、隔离守卫在真实启动形态下没装（F1 的暴露依赖它）、release 未 --detach 的事故后的恢复验证。
- 反例教训：门禁若只按「实现者以为的形态」构造，F1 这类缺口会一路绿着通过 3 道门禁——**按真实调用路径构造**是模式的前提。
