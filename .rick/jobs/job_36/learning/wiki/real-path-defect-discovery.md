# 真实路径暴露缺陷法（real-path defect discovery）

**命题**：单元测试与「按实现分支构造」的门禁，测不到只在**真实调用路径**下出现的缺陷。job_36 的 4 个真缺陷（F1-F4）全部由后者暴露，前者全部漏过。

## 方法

在验收时**逐个回答**：「这个功能的真实调用路径是什么？」——包括：
1. **谁执行**（宿主形态：被生产托管的会话？用户终端？cron？）
2. **在哪执行**（cwd 是哪：生产仓库？dev 树？任意目录？）
3. **用什么形态执行**（启动形态：--flag？换 HOME？默认？）
4. **执行前后生产有什么变化**（副作用边界）

然后按答案构造测试（而不是按实现的 if 分支）。

## 实证（job_36）

| 缺陷 | 真实路径 | 为什么单测/分支门禁测不到 |
|---|---|---|
| F1 守卫没装 | `dev-web` 用**换 HOME** 启动（不是 --state-dir） | 门禁只测了 --state-dir 分支 |
| F2 dry-run 被拦 | 由**生产托管**的会话跑 dry-run | 拦截顺序在实现内部，单测无此宿主 |
| F3 dry-run 写生产树 | dry-run 后**核对生产树** | 无副作用断言就不会看生产树 |
| F4 树解析错 | **cd 进 dev 树**执行命令 | 单测的 cwd 都是构造好的 |

## 落地

- E2E 必须用**真实命令**（`go run ./cmd/rick …` 而不是调函数）、**真实启动形态**（和产品入口一模一样）、**真实宿主**（在生产托管的会话里跑一次）。
- 「按真实路径暴露」应成为 E2E 设计的默认问题清单（4 问）。
