## Step 1a：bug1 debug 闭环分析

**根因链完整闭环？——是。** 排查符合 S→E 结构且证据等级高：
- 症状定位（web 报错 → 会话 active 但无 worker 进程）→ 环境继承路径（AgentEnv 继承 web env）→ 模型链路（catpaw-proxy → mcli.sankuai.com）→ **对照实验铁证**（同 proxy 下仅改 no_proxy 即可复现/恢复）→ 根因判定为「环境反转」（老机器经验在跨机迁移后失效）。
- 修复已验证落地（start-web.sh 追加 no_proxy + 重启 web pid=95589 + pi --print 实测「通」），且 worker 同款 env 复测通过。

**亮点**：用「proxy 能转发 github 但不转发 mcli」的差异排除了「proxy 整体故障」假设，把根因钉死在「内网域名路由」单点上；这是本轮排查最可复用的手法。

**遗留项状态——未闭环，风险真实存在。**
- prodEnv 透传调用方 proxy 变量：若 release 从旧 no_proxy 的 shell 执行，新起生产实例会复发（S5 实例 89800 实际中招，被 start-web.sh 重启修复覆盖——**修复是环境级而非源码级，属于「覆盖」而非「根治」**）。
- 候选源码级修复（catpaw-proxy.ts 用 no-proxy dispatcher）在 pi 侧定制层，非 rick 源码树，本 job 无法落地。
- 结论：此遗留项应转为持续监控项——每次 release 后对生产实例做一次 pi 链路连通性探针（对照实验脚本已具备，成本极低）。

## Step 2：改进评估（三环节）

### 环节 1：worker 两轮失败后 parent 接手——更早的信号与接手时机

**信号清单（可更早识别「中途思考截断」模式）**：
1. 迭代 1 回执已呈现「分析完整、结论正确、但 3 红未收敛」+ 截断——第一轮结束时截断信号就已在场；
2. 迭代 2 回执「只有失败分析、无代码改动」——这是**第二独立信号**：预算被消耗在重读/重析而非修复；
3. 两轮呈同构模式（都以「输出思考即结束」收尾）——模式匹配比单轮失败更具接手判别力；
4. 任务体量前置可估：778 行实现+多包测试本就是大任务，fork 上下文 worker 预算紧张可预判。

**接手时机结论**：应在**迭代 2 回执到达时立即接手**（而非再做第三轮尝试）——判据为「同模式截断×2 且第二轮零代码产出」。实际上本轮 parent 也是在迭代 2 后接手的，时机不算迟；真正的改进点是：**迭代 1 回执若附带截断标记，可建立「截断一次→缩短任务粒度重派，截断两次→直接接手」的干预阶梯规则**，避免迭代 2 那 60 分钟的确定性空转。

### 环节 2：gate2 三轮环境构造失败——哪些可一次性避免

三轮失败逐项评估：
1. **缺 go.mod（可预先避免）**：gate2 意图是演练 release 对「生产形态仓库」的校验——「校验会拒绝什么」恰是测试点本身，但作为**环境构造**它本可在写 gate2 前用 checklist 一次性确认：fake prod repo 需满足 release 的仓库形态前置（go.mod 存在）。属「未先枚举被测对象对环境的全部前置假设」。
2. **空 start script 不启动服务（可预先避免）**：同因——脚本需要真实可执行且起服务，写 gate2 时应把「服务起来→端口可探测」列为构造完成判据，而非先写脚本再发现。
3. **端口残留（不可预先避免，且是收益）**：上轮 probe 残留占用 6199 属迭代间状态泄漏，通用 checklist 难覆盖；且它意外实证了端口认领链收割跨 state-dir 残留的行为——**这是免费的判别力验证**。

**更短路径**：gate2 动工前写一份 10 行「演练环境构造清单」（仓库形态/脚本可执行性/起服务判据/端口初始状态检查），1/2 两轮可省；第 3 轮保留并在事前加「端口占用预检」即可转为有意探针而非事故。

### 环节 3：S2 门禁设计发现两个既有 bug——「主动安全实验」的普适性

**机制分析**：门禁的「判别力验证」要求构造「修复前红/修复后绿」的受控场景，本质是**主动构造受害场景**——这迫使设计者站到故障方视角，把平时「跑绿即过」的路径推到边界。B1（lsof 字段错，快照断言空转）与 B2（cwd 断言过宽会误杀 agent 会话）都是「代码一直绿但语义错」的潜伏 bug，常规测试无法暴露，只有构造「快照必须采到 cwd」「生产树上有非 rick 进程」这类受害探针才现形。

**普适性评估：高，但有前置条件**。
- 适用面：一切有「认领/断言/状态判定」语义的系统（进程认领、锁、快照、健康检查）——这类代码的错误模式恰是「假阳性/假阴性静默」，天然需要受害场景探针；
- 不适用面：纯数据变换、无外部状态交互的逻辑，受害场景构造不出来，强行做是浪费；
- 前置条件：设计者需先枚举「谁会被这个判定误伤/漏掉」（B2 的「误杀 agent 会话」来自先想清楚 claim 判定的受害面），这一步是人工判断，无法自动化兜底；
- 成本收益：本次 25min S2 中连带修掉两个潜伏 bug（其一可致 release 误杀 human 终端），边际成本近零——**建议固化为门禁设计模板的一节：「对每个判定点构造一个受害方探针」**。
